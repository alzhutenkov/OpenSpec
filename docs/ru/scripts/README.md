# Скрипты OpenSpec

Служебные сценарии для обслуживания и разработки OpenSpec.

## update-flake.sh

автоматически обновляет хеш зависимостей pnpm `flake.nix`.

**Когда использовать**: После обновления зависимостей (`pnpm install`, `pnpm update`).

**Использование**:
```bash
./scripts/update-flake.sh
```

**Что он делает**:
1. читает версию из `package.json` (динамически используется `flake.nix`).
2. автоматически определяет правильный хэш зависимости pnpm.
3. обновляет хэш в `flake.nix`.
4. проверяет успешность сборки.

**Пример рабочего процесса**:
```bash
# после обновления зависимостей.
pnpm install
./scripts/update-flake.sh
git add flake.nix
git commit -m "chore: update flake.nix dependency hash"
```

## regen-parity-hashes.mjs

пересчитывает эталонные хеши,
закрепленные в `test/core/templates/skill-templates-parity.test.ts` .

**Когда использовать**: после любого запланированного изменения шаблона рабочего процесса и
после перебазирования ветки, которая редактирует шаблоны — две ветки, соприкасающиеся с
разными шаблонами, сталкиваются на одной и той же хэш-карте, и
при ручном редактировании 64-символьных хешей во время конфликта возникают ошибки транскрипции.

**Использование**:
```bash
pnpm build && pnpm regen:parity-hashes
pnpm vitest run test/core/templates/skill-templates-parity.test.ts
```

**Что он делает**:
1. отказывается запускаться, если `dist/` отсутствует или старше `src/` — хэши берутся из
   сборка, в то время как тест четности считывает `src/`, поэтому регенерация против
   устаревшая сборка записывает хэши теста, а затем отклоняет его.
2. пересчитывает каждый закрепленный хэш из встроенного `dist/`.
3. перезаписывает карту на месте и печатает, какие записи были перемещены.
4. завершает работу с ненулевым значением, ничего не записывая, если не может учитывать каждый закрепленный хэш:
   метка без соответствующего экспорта (переименованный или удаленный шаблон) или хеш.
   линии, эти шаблоны не распознаются. В противном случае оба остались бы устаревшими.
   хотя запуск сообщил об успехе, `nothing to update` всегда означает это.

Окончания строк туда и обратно не изменились, поэтому проверка CRLF безопасна —
`test/**` не имеет атрибута `text eol=lf` , поэтому файл поступает с CRLF в Windows.

тест на четность пересчитывает одни и те же хэши независимо,
поэтому этот сценарий не может молча выдавать неправильное значение. Всегда запускайте
тест после этого; именно он, а не этот сценарий, является авторитетом.

Перезапись находится в `parity-hash-shared.mjs` , поэтому ее защиту
можно применять против сфабрикованных входных данных — см. `test/core/templates/parity-hash-shared.test.ts`
. Тест, который запускал бы этот сценарий по-настоящему, переписывал
бы собственный файл теста четности репозитория в середине пакета.

## двоичный/

собирает автономные исполняемые файлы `openspec` (Node.js не требуется), способ
установки OpenSpec по умолчанию. `.github/workflows/binaries.yml` кросс-компилирует каждый ресурс в Linux,
тестирует каждый на своей собственной ОС и процессоре и прикрепляет
их (`SHA256SUMS`, `install.sh` и `install.ps1` ) к каждому опубликованному выпуску.

|Файл|Что это такое|
|---|---|
|`build.mjs`|встраивает ресурсы в `dist-bin/` (сначала запустите `pnpm build`).|
|`entry.mjs`|Точка входа в двоичный файл: встроенные схемы, советы по обновлению.|
|`install.sh` / `install.ps1`|пользователи запускают установщики (macOS/Linux, Windows).|
|`smoke.sh`|Быстрая проверка одного двоичного файла.|
|`e2e.sh`|каждый тест CLI выполняется для одного двоичного файла вместо узла.|

```bash
pnpm build
bun scripts/binary/build.mjs                    # эта машина
bun scripts/binary/build.mjs --all              # каждый актив выпуска.
bash scripts/binary/smoke.sh dist-bin/openspec-<asset>
bash scripts/binary/e2e.sh dist-bin/openspec-<asset>
```
