<a id="contributing"></a>
# Участие в разработке

Спасибо за помощь в улучшении OpenSpec.

Каждое предложение начинается с issue в GitHub. Там обсуждается проблема. Если команда решает заняться ею, сопровождающий реализует изменение или приглашает вас к работе. Pull request создают сопровождающие и приглашённые участники. Причины описаны в статье [Обновление правил участия в OpenSpec (английский)](https://openspec.dev/blog/openspec-contribution-policy/).

<a id="1-open-an-issue"></a>
## 1. Откройте issue

[Выберите форму (английский)](https://github.com/Fission-AI/OpenSpec/issues/new/choose): ошибка, возможность или документация.

- **Ошибка:** что вы пытались сделать, что произошло, чего ожидали и кратчайшие шаги воспроизведения в новом проекте. Полезнее всего сообщения ошибок, журналы и минимальный пример. Команда не может исправить то, что не удаётся воспроизвести.
- **Поведение агента:** укажите агента и модель; приложите запись сеанса, если она есть. Обычно причину помогают сузить прочитанные файлы, вызванные инструменты и повторяемость поведения в разных сеансах.
- **Новая возможность:** опишите проблему, кого ещё она затрагивает, какие обходные решения вы пробовали и оправдывает ли результат усложнение сопровождения. Готовое решение не требуется. Иногда наблюдаемое поведение является осознанным компромиссом, который и нужно обсудить.

В рабочем проекте команда `openspec feedback "what happened"` создаёт сообщение об ошибке с заполненными версией и платформой либо выдаёт ссылку на заполненную форму.

Если issue подготовил агент, перечитайте текст и отредактируйте от своего имени. Знать все ответы необязательно, но из текста должно быть видно, что вы разобрались с проблемой.

<a id="2-we-discuss-it-on-the-issue"></a>
## 2. Обсудите проблему в issue

Команда уточняет проблему, возможные подходы и соответствие приоритетам OpenSpec. Продукт работает с разными агентами, моделями и процессами: полезное для одного процесса изменение может нарушить другой.

При согласии продолжить сопровождающий добавляет метку `approved`, затем реализует изменение или приглашает вас к работе. Сообщите в issue, если хотите написать исправление. Команда не обещает реализовать каждое предложение.

Создание pull request ограничено сопровождающими. Дождитесь приглашения в issue, прежде чем начинать PR.

<a id="3-open-the-pr-invited-contributors-and-maintainers"></a>
## 3. Откройте PR (приглашённые участники и сопровождающие)

**Ошибка или документация:** один PR с исправлением. Укажите `Closes #123` в описании. Не меняйте `openspec/`: спецификации предназначены для новых возможностей.

**Новая возможность:** два PR после согласования изменения в issue.

1. **Предложение:** только `openspec/changes/<name>/`. Укажите `Part of #123`, чтобы issue оставалось открытым.
2. **Реализация:** после слияния предложения добавьте код и обновления изменения, например отметки в `tasks.md`. Укажите `Closes #123`.

<a id="development-setup"></a>
## Настройка среды разработки

Требуются Node 20.19+ и pnpm.

```bash
pnpm install
pnpm build              # тесты используют результат сборки
pnpm test
pnpm exec tsc --noEmit
pnpm lint
```

Последние четыре команды выполняются в CI. Успешный локальный запуск означает успешный запуск в CI.

Если изменение затрагивает пользователей, выполните `pnpm changeset` и добавьте созданный файл в коммит.

<a id="keep-the-clis-startup-fast"></a>
### Сохраняйте быстрый запуск CLI

Редакторы, агенты и OpenSpec Desktop вызывают CLI многократно. Каждый вызов оплачивает загрузку всех модулей до выполнения команды. До введения этого правила `openspec --version` загружал 485 модулей, что занимало около 0,5 с на Windows. Поэтому команда загружает только определения команд и собственную реализацию:

- **Определения** (имя, параметры, справка) размещаются в `src/cli/index.ts` или `src/cli/commands/<name>.ts`. Не импортируйте туда тяжёлые зависимости: zod, yaml, tinyglobby, ora и код других команд.
- **Реализация команды** размещается в `src/commands/<name>.ts` или `src/core/` и загружается внутри обработчика через `await import()`.

`test/cli-e2e/startup-modules.test.ts` проверяет модули, загружаемые каждой командой, и завершается ошибкой, если определение начинает импортировать реализацию. Добавляя команду, включите её в список этого теста.

<a id="pr-checklist"></a>
## Список проверки PR

- Создавайте ветку от `main` в своём форке.
- Оформляйте заголовок как conventional commit: `type(scope): subject`, например `fix(archive): keep authored Purpose`.
- Если код написал агент, укажите агента и модель и подтвердите, что проверили результат. Сгенерированный ИИ код принимается после проверки.

Список сопровождающих: [MAINTAINERS.md](MAINTAINERS.md).
