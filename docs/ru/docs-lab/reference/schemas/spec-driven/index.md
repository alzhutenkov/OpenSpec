<a id="spec-driven"></a>
# spec-driven

> Артефакты рабочего процесса по умолчанию: их порядок, форматы и папка изменений, которую они создают.

`spec-driven` — это встроенная схема OpenSpec по умолчанию. [schema.yaml](../schema-yaml.md) определяет устанавливаемые поля.

<a id="artifacts"></a>
## Артефакты

В рабочем процессе создаются четыре артефакта:

|Артефакт|Файл|Назначение|
|---|---|---|
|[`proposal`](#proposalmd)|`proposal.md`|Почему необходимы изменения|
|[`specs`](#delta-specs-specmd)|`specs/<capability-path>/spec.md`, по одному на каждую возможность.|Какие изменения в поведении|
|[`design`](#designmd)|`design.md`|Как это построить|
|[`tasks`](#tasksmd)|`tasks.md`|Контрольный список реализации|

<a id="drafting-order"></a>
## Порядок составления

```text
             ┌─ спецификации ──┐
предложение ────┤ ├── задачи ── применить
             └─ дизайн ─┘
```

Предложение стоит на первом месте. Спецификации и дизайн следуют в любом порядке, а задачи требуют обоих. Реализация ([apply](#apply)) начинается после установки `tasks.md`.

можно пропустить два артефакта:

- **`design`**: когда ни одно из [его условий](#designmd) не применимо, агент игнорирует его и все равно составляет `tasks`.
- **`specs`**: установите [`skip_specs: true`](../../configuration/change-metadata.md#skip_specs) в `.openspec.yaml` изменения.

<a id="example-change-folder"></a>
## Пример папки изменения

изменение под названием `add-user-auth`, в котором собраны все артефакты:

```text
openspec/changes/add-user-auth/
├── .openspec.yaml      метаданные изменения, записываемые при создании изменения.
├── proposal.md
├── specs/
│   └── аутентификация пользователя/
│       └── spec.md одна дельта-спецификация на каждую возможность
├── design.md
└── tasks.md
```

<a id="delta-specs-specmd"></a>
## Спецификации Delta (spec.md)

определяет, какое поведение изменяется, с одной разностной спецификацией для каждой возможности, указанной в предложении.

Каждая дельта-спецификация представляет собой `spec.md` внутри своей папки возможностей. `openspec validate` и `openspec archive` отклоняют дельта-разделы, записанные в любом другом файле под `specs/`, например `specs/user-auth.md`, поскольку архив никогда их не объединяет.

<a id="structure-1"></a>
### Структура

шаблон, который агент получает в качестве выходного формата ([templates/spec.md (английский)](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/templates/spec.md)):

```md
# Дельта спецификации

## Purpose
<!-- Только новые возможности: одно или два предложения (более 50 символов) о том, для чего нужна эта возможность. Удалите этот раздел для существующей возможности. -->

## ADDED Requirements

### Requirement: <!-- имя требования. -->
<!-- текст требования -->

#### Scenario: <!-- имя сценария. -->
- **WHEN** <!-- состояние -->
- **THEN** <!-- ожидаемый результат -->
```

## design.md

объясняет, как реализовать изменение. Составляется только тогда, когда изменение необходимо.

<a id="instructions-2"></a>
### Инструкции

инструкция, отправленная агенту при создании черновика этого артефакта (из [schema.yaml (английский)](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml)):

```md
Создайте проектный документ, в котором объясняется, КАК реализовать изменение.

Когда включать design.md (создавать, только если применимо):
- сквозное изменение (несколько служб/модулей) или новый архитектурный шаблон.
- новая внешняя зависимость или значительные изменения модели данных.
- безопасность, производительность или сложность миграции.
- Неопределенность, которая достигается за счет технических решений перед кодированием.

Разделы:
- **Контекст**: для объяснения подхода необходимо только текущее состояние и ограничения. Ссылайтесь на предложение для мотивации, а не повторяйте его (например, «Смотрите proposal.md – Почему»).
- **Цели/нецели**: то, что этот дизайн достигает и что явно исключает. Не переутверждайте объем предложения — добавляйте только границы на уровне проекта.
- **Решения**: ключевые технические решения с обоснованием (почему X, а не Y?). Включите альтернативы, рассматриваемые для каждого решения.
- **Риски/компромиссы**: известные ограничения, проблемы, которые могут пойти не так. Формат: [Риск] → Смягчение
- **План миграции**: шаги по развертыванию, стратегия отката (если применимо).
- **Открытые вопросы**: неизвестные, на которые можно безопасно ответить позже, не
  изменение спецификации, подхода или разбивки задач. Пропустите, если нет.

Открытые вопросы касаются действительно отложенных неизвестных, а не решений, которые вы можете принять.
пропущено. Если вопрос может изменить спецификации, выбранный подход или
разбивка задачи, решите ее сейчас — спросите пользователя, а не гадайте.

Сосредоточьтесь на архитектуре и подходе, а не на поэтапной реализации.
В предложении говорится, почему и что; дизайн охватывает то, как. Ссылка на
предложение по мотивации и, как только оно будет написано, спецификации требований -
если в разделе требуется только переформулировать их, вместо этого укажите на них.

Хорошая проектная документация объясняет, «почему» лежат в основе технических решений.
```

## tasks.md

разбивает реализацию на проверяемые задачи. [apply](#apply) отслеживает прогресс здесь.

<a id="structure-3"></a>
### Структура

шаблон, который агент получает в качестве выходного формата ([templates/tasks.md (английский)](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/templates/tasks.md)):

```md
# Задачи

## 1. <!-- Имя группы задач -->

- [ ] 1.1 <!-- Описание задачи -->
- [ ] 1.2 <!-- Описание задачи -->

## 2. <!-- Имя группы задач -->

- [ ] 2.1 <!-- Описание задачи -->
- [ ] 2.2 <!-- Описание задачи -->
```

<a id="instructions-3"></a>
### Инструкции

инструкция, отправленная агенту при создании черновика этого артефакта (из [schema.yaml (английский)](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml)):

````md
Создайте список задач, в котором разбивается работа по реализации.

Прежде чем писать задания, проверьте design.md на наличие открытых вопросов. Если кто-либо из них
будет изменено то, что создается, сначала решите их с пользователем - не делайте этого.
включить невысказанное предположение в список задач.

**ВАЖНО. Для отслеживаемых задач следуйте приведенному ниже шаблону.** Анализ фазы применения
формат флажка для отслеживания прогресса. Коробка, содержащая только `x`, считается готовой.
верхний или нижний регистр и с любым интервалом, поэтому `- [ x]` тоже делается. Каждый
другой маркер, включая `- [~]`, `- [-]` и пустой `- []`, читается как
незавершенный. Строка без флажка вообще не отслеживается.

Рекомендации:
- Группировать связанные отслеживаемые задачи под пронумерованными заголовками ##.
- для каждой отслеживаемой задачи MUST должен быть установлен флажок: `- [ ] X.Y Task description`.
- задачи должны быть достаточно маленькими, чтобы их можно было выполнить за один сеанс.
- Упорядочить задачи по зависимости (что нужно сделать в первую очередь?)
- Отслеживайте работу по внедрению и проверке, которую можно выполнить до
  архив. Если запрошенный рабочий процесс включает архив или работу, требующую
  это изменение необходимо заархивировать, сохраните эти шаги в виде простых маркеров в
  необязательный раздел `## Workflow follow-up` в конце tasks.md. Эти
  маркеры представляют собой справочную информацию вне отслеживаемого хода выполнения задачи.
- В каждой задаче MUST указано, как проверить завершение (тест, команда,
  наблюдаемое поведение или доставленный артефакт). Поставьте проверку
  описание флажка этой задачи. Используйте только отдельную задачу проверки
  когда он проверяет более широкую интеграцию или поведение системы, охватывающее
  несколько задач реализации.
- каждая группа задач MUST проводит тесты и документирует свою собственную работу.
  требует. НЕ собирайте тестирование или документацию в финальную группу.
  когда поздняя группа впервые выполняет упражнения с ранней, неудачи
  каскадно пройти через каждую промежуточную группу и принудительно переработать. Группа
  чья работа не требует ни того, ни другого, например, создания строительных лесов или установки зависимостей,
  не содержит ни того, ни другого. Последняя группа предназначена только для проверок интеграции, а не для
  тесты и документы, которые должна была получить предыдущая группа.

Пример:
```
<a id="tasks"></a>
# Задачи

<a id="1-setup"></a>
## 1. Настройка

- [ ] 1.1 Создайте новую структуру модуля и проверьте наличие ожидаемых файлов.
- [ ] 1.2 Добавьте зависимости в package.json и убедитесь, что установка пакета прошла успешно.

<a id="2-core-implementation"></a>
## 2. Основная реализация

- [ ] 2.1 Реализовать функцию экспорта данных и проверить прохождение теста экспорта.
- [ ] 2.2 Добавьте утилиты форматирования CSV и убедитесь, что модульные тесты охватывают кавычки и разделители.
- [ ] 2.3 Задокументируйте экспорт API в docs/export.md и убедитесь, что документированная команда выполняется так, как написано.
```

When applicable, append workflow follow-up as plain bullets, for example:
```
<a id="workflow-follow-up"></a>
## Отслеживание рабочего процесса

- заархивируйте изменения после того, как требования проверки проекта будут выполнены.
- проверьте заархивированный результат.
```

Reference specs for what needs to be built, design for how to build it.
````

<a id="apply"></a>
## Применить

переход от планирования к реализации. Apply — это этап, который работает через `tasks.md`, а не артефакт.

- **Запускается**: как только `tasks.md` существует и содержит хотя бы одну задачу.
- **Дорожки**: флажки в `tasks.md`. Отметить их — это запись прогресса.
- **Заканчивается**: отмечены все флажки. Затем OpenSpec предлагает заархивировать изменение.

<a id="settings"></a>
### Настройки

настройки применения (из [schema.yaml (английский)](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml)):

```yaml
apply:
  requires: [tasks]
  tracks: tasks.md
  # инструкция: показана ниже
```

### Инструкции

инструкция, отправляемая агенту при запуске реализации (из [schema.yaml (английский)](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml)):

```md
чтение контекстных файлов, работа с ожидающими задачами, пометка завершенных по ходу выполнения.
делайте паузу, если нажимаете блокирующие или вам нужны разъяснения.
```

<a id="schemayaml"></a>
## schema.yaml

Полный [schema.yaml (английский)](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml) с опущенными телами инструкций. Каждый из них показан полностью в соответствующем разделе выше.

```yaml
name: spec-driven
version: 1
description: Рабочий процесс OpenSpec по умолчанию — предложение → спецификации → дизайн → задачи.
artifacts:
  - id: proposal
    generates: proposal.md
    description: документ с первоначальным предложением, описывающий изменения.
    template: proposal.md
    # инструкция: полностью показана в файле proposal.md выше.
    requires: []

  - id: specs
    generates: "specs/**/*.md"
    description: Подробные характеристики изменения.
    template: spec.md
    # инструкция: полностью показана в характеристиках Delta выше.
    requires:
      - proposal

  - id: design
    generates: design.md
    description: Технический проект с подробностями реализации.
    template: design.md
    # инструкция: полностью показана в файле design.md выше.
    requires:
      - proposal

  - id: tasks
    generates: tasks.md
    description: Контрольный список внедрения с отслеживаемыми задачами.
    template: tasks.md
    # инструкция: полностью показана в файле tasks.md выше.
    requires:
      - specs
      - design

apply:
  requires: [tasks]
  tracks: tasks.md
  # инструкция: полностью показана в разделе «Применить» выше.
```
