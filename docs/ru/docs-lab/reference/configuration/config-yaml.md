# Конфигурация проекта (config.yaml)

> Все поля openspec/config.yaml: схема, контекст и правила планирования проекта.

<a id="location"></a>
## Расположение

Каждый проект OpenSpec хранит конфигурацию в `openspec/config.yaml` в корне проекта.

<a id="fields"></a>
## Поля

| Ключ | Тип | Обязательно | Действие |
| --- | --- | --- | --- |
| `schema` | строка | Да | Схема рабочего процесса изменений проекта |
| `context` | строка | Нет | Добавляется в инструкции каждого артефакта, apply и archive |
| `rules` | словарь: ID артефакта → список строк | Нет | Дополнительные правила к встроенным инструкциям одного артефакта |
| `operations` | словарь: операция → список указаний | Нет | Рекомендации по выполнению apply и archive |
| `store` | строка | Нет | Запасной корень OpenSpec, когда эта папка openspec/ содержит только конфигурацию |
| `references` | список | Нет | Хранилища, индекс спецификаций которых добавляется в инструкции |

Невалидные поля не останавливают команду. Каждое проверяется отдельно; неверное значение отбрасывается с предупреждением.

Что записывать в эти поля, описано в [конфигурации проекта](../../customize/project-config.md).

### schema

Схема рабочего процесса каждого изменения проекта. Значение: `spec-driven` или имя схемы проекта. Команда [`openspec schemas`](../cli.md#openspec-schemas) перечисляет доступные имена.

### context

Произвольный текст, добавляемый в инструкции каждого артефакта и передаваемый apply и archive. Ограничение: 50 КБ. Более длинное значение игнорируется с предупреждением.

### rules

Дополнительные правила одного артефакта, дополняющие встроенные инструкции схемы:

```yaml
rules:
  proposal:
    - Ограничивай предложения 500 словами
```

Идентификаторы артефактов не ограничены встроенными именами: артефакты пользовательских схем тоже можно использовать как ключи.

### operations

Рекомендации по выполнению apply и archive, отдельные от правил артефактов:

```yaml
operations:
  apply:
    guidance:
      - Сохраняй отчёты о тестах краткими
```

Читаются только `apply` и `archive`.

### store

Идентификатор хранилища, используемого как корень OpenSpec, только если эта папка openspec/ содержит одну конфигурацию, без specs/ и changes/. Это запасной вариант, а не переопределение. Полный порядок описан в [выборе корня](../../multi-repo/stores.md#where-artifacts-get-created-when-using-stores).

### references

Идентификаторы хранилищ, на чьи спецификации опирается проект. Индекс спецификаций каждого хранилища (ID, краткое описание, команда получения) добавляется в вывод инструкций. Содержимое спецификаций не вставляется; выбор корня не меняется. Запись может быть идентификатором или словарём с `id` и необязательным источником клонирования `remote`:

```yaml
references:
  - platform-specs
  - id: billing-specs
    remote: git@github.com:acme/billing-specs.git
```

<a id="example"></a>
## Пример

Заполненный config.yaml:

```yaml
schema: spec-driven

context: |
  Технические решения и задачи должны охватывать Windows, macOS и Linux
  Пиши все артефакты на испанском языке

rules:
  proposal:
    - Ограничивай предложения 500 словами
    - Всегда указывай, что не входит в область работы
  tasks:
    - Разбивай задачи на части длительностью не более 2 часов

operations:
  apply:
    guidance:
      - Сохраняй отчёты о тестах краткими
  archive:
    guidance:
      - Перед завершением подведи итог архивирования
```

<a id="legacy-names"></a>
## Прежние имена

`openspec/config.yml` читается как альтернативное имя, если `config.yaml` отсутствует. Если существуют оба файла, используется `config.yaml`, а `config.yml` игнорируется. `openspec init` создаёт `config.yaml`.
