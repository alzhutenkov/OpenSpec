# Метаданные изменения (.openspec.yaml)

> Поддерживаемые поля и правила проверки метаданных каждого изменения.

<a id="location"></a>
## Расположение

Изменение хранит метаданные в `openspec/changes/<change-name>/.openspec.yaml` рядом с артефактами. При создании изменения файл записывается с заполненными `schema` и `created`.

<a id="fields"></a>
## Поля

| Ключ | Тип | Обязательно | Действие |
| --- | --- | --- | --- |
| `schema` | строка | Да | Схема рабочего процесса изменения |
| `created` | строка YYYY-MM-DD | Нет | Дата создания изменения |
| `goal` | строка | Нет | Цель изменения |
| `affected_areas` | список строк | Нет | Области, которые изменение планирует затронуть |
| `initiative` | словарь: `store` и `id` | Нет | Инициатива, к которой относится изменение |
| `skip_specs` | логическое значение | Нет | Явно указывает отсутствие изменений спецификаций; проверка допускает ноль таких файлов |
| `retire_capabilities` | логическое значение | Нет | Разрешает архивированию удалить возможность, опустошённую этим изменением |

### schema

Схема рабочего процесса изменения. Задаётся при создании и имеет приоритет над конфигурацией проекта. Изменение сохраняет схему, даже если затем поменяется `openspec/config.yaml`. Команда [`openspec schemas`](../cli.md#openspec-schemas) перечисляет доступные имена.

### initiative

Инициатива изменения: идентификаторы хранилища и инициативы, оба в kebab-case:

```yaml
initiative:
  store: platform-specs
  id: unify-billing
```

Другие ключи, кроме `store` и `id`, отклоняются. В настоящее время ни одна команда не использует эту связь.

### skip_specs

Явно указывает, что изменение не содержит изменений спецификаций: например, только рефакторинг, инструменты или документация. Проверка допускает ноль файлов изменений требований, а артефакты, которые должны были создавать спецификации, считаются завершёнными. Если при этом файлы спецификаций существуют в specs/, проверка завершается ошибкой.

### retire_capabilities

Разрешает архивированию вывести возможность из использования. Если операции REMOVED удаляют последнее требование возможности, архивирование удаляет её основную спецификацию вместо остановки. Флаг нужен потому, что удалённое можно восстановить только из Git: решение остаётся за автором.

<a id="extension-keys"></a>
### Ключи расширения

Ключ верхнего уровня со строчным префиксом `x-` предназначен для ваших данных: например, ID задачи или владельца, которые команда или другой инструмент хранит рядом с изменением:

```yaml
schema: spec-driven
x-tracker: SB-5497
x-jiraKey: ABC-1
x-owner:
  team: payments
```

- **Имя:** после строчного `x-` должен идти хотя бы один символ; пробелы запрещены во всём имени. После префикса допустим любой регистр, поэтому `x-jiraKey` и `x-trackerID` подходят. `X-Tracker`, отдельный `x-` и `x- tracker` не подходят и считаются неизвестными ключами.
- **Значение:** любое значение YAML. OpenSpec не читает и не проверяет его; поведение не меняется.
- **Область:** только верхний уровень. Внутри `initiative` ключ `x-` отклоняется, как и любой другой дополнительный ключ.
- **Проверка:** ключи расширений не считаются неизвестными, поэтому `openspec validate --strict` проходит для изменения с такими ключами.
- **Архивирование:** файл перемещается вместе с изменением без изменений, включая ключи расширений.

<a id="example"></a>
## Пример

Заполненный .openspec.yaml:

```yaml
schema: spec-driven
created: 2026-08-14
goal: Добавить вход по ссылке magic-link в API
affected_areas:
  - auth
  - api
```

<a id="validation"></a>
## Проверка

Файл проверяется при каждом чтении или записи командой. Невалидная запись вызывает ошибку и ничего не записывает. Чтение завершается ошибкой при невалидном YAML, нарушении контракта поля или недоступной схеме. Отсутствующий файл не считается ошибкой: изменение обрабатывается без метаданных.

В отличие от [config.yaml](config-yaml.md), неверные значения не отбрасываются с предупреждением. Ошибка метаданных останавливает команду.

- **Неизвестные ключи верхнего уровня:** OpenSpec игнорирует их. `status`, `instructions`, `validate` и `archive` сообщают, что они не действуют. Вывод JSON содержит предупреждение в структурированном результате. [Ключи расширения](#extension-keys) не считаются неизвестными и не вызывают такого предупреждения.
- **Строгая проверка:** `openspec validate --strict` трактует предупреждение о неизвестном ключе как ошибку. Изменение, у которого дополнительные ключи являются только расширениями, проходит проверку.
