## openspec init

Инициализирует OpenSpec в проекте.

```bash
openspec init                        # текущий каталог, интерактивный выбор инструментов.
openspec init --tools claude,cursor  # настройка определенных инструментов, без подсказок.
openspec init --tools none           # только структура openspec/, без файлов инструментов.
```

Без `--tools` init предложит вам выбрать инструменты в интерактивном терминале. За пределами одного он настраивает инструменты, обнаруженные в проекте. Если ничего не обнаружено, он выходит из 1 и выводит список действительных идентификаторов.

**Репозитории только для хранилища**

Если `openspec/config.yaml` содержит строку `store:` и в репозитории нет локальных спецификаций или изменений, запустите init из корня репозитория:

```bash
# установите файлы интеграции Claude Code в репозиторий кода.
openspec init --tools claude
```

- **Файлы интеграции**: записаны в репозитории кода.
- **`openspec/config.yaml`**: сохраняется побайтно.
- **`openspec/specs/` и `openspec/changes/`**: не созданы в репозитории кода.

запуск init из подкаталога приводит к выходу из 1 и указывает на необходимость запуска его из корня репозитория. `--language` также выходит из 1, поскольку язык принадлежит конфигурации внешнего хранилища. Запустите init в корне хранилища или отредактируйте эту конфигурацию напрямую.

**Аргументы**

|Аргумент|Что это такое|
|---|---|
|`path`|каталог проекта для инициализации. По умолчанию: текущий каталог. Создается, если отсутствует.|

**Параметры**

|Флаг|Эффект|
|---|---|
|`--tools <tools>`|идентификаторы инструментов, разделенные запятыми, `all` или `none`. Пропускает сборщик. Идентификаторы указаны в разделе [Поддерживаемые инструменты](supported-tools.md).|
|`--language <language>`|добавьте языковую инструкцию в новую конфигурацию проекта. Отклоняется, когда строка репозитория `store:` указывает на внешнее хранилище.|
|`--force`|удаление файлов из старых макетов OpenSpec без запроса. В противном случае интерактивные прогоны сначала подтверждают очистку.|
|`--profile <profile>`|переопределить профиль глобальной конфигурации для этого запуска: `core` (стандартный набор рабочих процессов) или `custom` (рабочие процессы, сохраненные в глобальной конфигурации).|
|`--no-animation`|отображать статический экран приветствия вместо анимированного.|

**Вывод**

Каждый выбранный инструмент получает навыки и команды OpenSpec в своем собственном каталоге:

```
▌ OpenSpec structure created
✔ Setup complete for Claude Code

OpenSpec Setup Complete

Created: Claude Code
6 skills and 6 commands in .claude/
Config: openspec/config.yaml (schema: spec-driven)

Getting started:
  Start your first change: /opsx:propose "your idea"

Restart your IDE for the new commands to take effect.
```

[Русское пояснение подписей и сообщений](../../EXAMPLE_NOTES.md#example-010).


`--tools none` создает только `openspec/config.yaml`. В уже инициализированном проекте init переписывает установленные файлы на место, и в сводке читается `Refreshed: Claude Code` с `Config: openspec/config.yaml (exists)`.

**Коды выхода**

- `0`: установка завершена.
- `1`: недопустимое значение `--tools` или `--profile`, неинтерактивный запуск без обнаруженных инструментов и `--tools` или недопустимый вызов только для хранилища.

## openspec update

обновляет установленные файлы инструкций OpenSpec.

```bash
openspec update             # обновить инструменты, файлы которых старше CLI.
openspec update --force     # перезаписывать файлы, даже если они актуальны.
openspec update --dry-run   # перечислить, что изменится в обновлении, и ничего не менять.
```

обновление находит настроенные при инициализации инструменты и сравнивает сгенерированные ими файлы с версией CLI. Когда существует более новая версия OpenSpec, она сначала предлагает обновить CLI, а затем повторно запускается с обновленной версией. Настройте `OPENSPEC_NO_UPDATE_CHECK=1`, чтобы пропустить проверку.

**Аргументы**

|Аргумент|Что это такое|
|---|---|
|`path`|каталог проекта для обновления. По умолчанию: текущий каталог.|

**Параметры**

|Флаг|Эффект|
|---|---|
|`--force`|перезапишите файлы каждого настроенного инструмента, даже если они обновлены.|
|`--dry-run`|Сообщать о каждом файле, который обновление добавит, изменит или удалит, и ничего не писать. Нет проверки обновления CLI, нет подсказок. Объедините его с `--force`, чтобы просмотреть принудительное обновление.|
|`--json`|с помощью `--dry-run` распечатайте план как JSON. Без `--dry-run` происходит выход 1.|

**Предварительный просмотр обновления**

`--dry-run` планирует обновление, которое будет выполнено при неинтерактивном запуске: тот же путь кода, при этом каждая запись и удаление записывается, а не выполняется. В списке перечислены все файлы, которые затронет реальное обновление, включая:

- перемещение файлов OpenSpec из прежнего каталога инструмента (`.kimi/` в `.kimi-code/`, `.windsurf/` в `.devin/`, `.codex/` и `.agent/` в `.agents/`);
- сохранение глобальной конфигурации при установке из до того, как профили получили ее;
- синхронизация файлов облачного агента GitHub Copilot;
- с `--force` настройка инструментов, найденных только в устаревших артефактах, и очистка этих артефактов, включая устаревшие глобальные подсказки Codex.

```bash
openspec update --dry-run
```

```
2 file(s) would change:
  update  .claude/skills/openspec-propose/SKILL.md  (claude)
  add     ~/.config/openspec/config.json  (openspec)
```

`--dry-run --json` печатает тот же план, что и один документ JSON:

```json
{
  "changes": [
    { "path": ".claude/skills/openspec-propose/SKILL.md", "action": "update", "tool": "claude" },
    { "path": "~/.config/openspec/config.json", "action": "add", "tool": "openspec" }
  ],
  "notes": [],
  "failures": []
}
```

|Поле|Что он содержит|
|---|---|
|`changes[].path`|путь относительно проекта. Файл вне проекта, например глобальный навык или глобальная конфигурация, отображается в вашем домашнем каталоге как `~/...` или как абсолютный путь, если он также находится за пределами домашнего каталога.|
|`changes[].action`|`add`, `update` или `delete`. Файл, новые байты которого совпадают со старыми, не отображается.|
|`changes[].tool`|настроенный инструмент, которому принадлежит файл, например `claude`. Файлы, которые принадлежат самому OpenSpec, а не одному инструменту, глобальной конфигурации и очистке устаревших артефактов, называются `openspec`.|
|`notes[]`|`{ code, message }` для шага, о котором будет спрошен пользователь терминала. `legacy-tool-directories`: ход, о котором интерактивный запуск спрашивает в первую очередь; `changes` указывает, что это сделано. `legacy-artifacts`: были найдены файлы из более старого макета OpenSpec, такие как косая черта `openspec-proposal.md` или маркерные блоки OpenSpec в `AGENTS.md`. Без `--force` неинтерактивное обновление оставляет их в покое, как и `changes`; `--dry-run --force` перечисляет их очистку. Пустой для обычного обновления.|
|`failures[]`|`{ tool, error }` для каждого инструмента, при котором произойдет сбой реального обновления, включая запись, которую он не может выполнить: каталог, которому принадлежит файл, файл, которому принадлежит каталог, или файл или папка без разрешения на запись. Для этого инструмента `changes` останавливается там, где заканчивается настоящее обновление; другие инструменты все еще планируются. Сбои, о которых диск сообщает только во время записи, например, нехватка места, предвидеть невозможно.|

сбой перед планированием, например отсутствие каталога OpenSpec, по-прежнему печатает ровно один документ JSON: пустой план плюс массив `status` с `severity`, `code` (`update_error`) и `message`. Код выхода — 1.

**Вывод**

Когда файлы каждого инструмента соответствуют версии CLI:

```
✓ All 1 tool(s) up to date (v1.7.0)
  Tools: claude

Use --force to refresh files anyway.
```

Если файлы инструмента взяты из более старой версии CLI (или из `--force`, которая вместо этого печатает `Force updating 1 tool(s): claude`):

```
Updating 1 tool(s): claude (1.6.0 → 1.7.0)

✔ Updated Claude Code

✓ Updated: Claude Code (v1.7.0)
Tools: Claude Code

Restart your IDE for changes to take effect.
```

В каталоге без OpenSpec обновление отказывается:

```
✖ Error: No OpenSpec directory found. Run 'openspec init' first.
```

**Коды выхода**

- `0`: файлы обновлены или все уже обновлено.
- `1`: в пути нет каталога OpenSpec, или обновление не удалось.

## openspec config

Просматривает и изменяет глобальную конфигурацию.

```bash
openspec config list                  # посмотреть текущие настройки
openspec config set delivery skills   # изменить одно значение
openspec config profile               # интерактивный инструмент выбора рабочего процесса.
```

|Подкоманда|Что он делает|
|---|---|
|`path`|распечатайте расположение файла конфигурации.|
|`list`|Показать все текущие настройки.|
|`get <key>`|вывести одно значение, необработанное и доступное для сценариев.|
|`set <key> <value>`|установите значение, определяющее его тип.|
|`unset <key>`|удалите ключ, чтобы применить его по умолчанию.|
|`reset`|сброс всей конфигурации до значений по умолчанию.|
|`edit`|откройте файл конфигурации в `$EDITOR`.|
|`profile [preset]`|Настройте форма установки и рабочие процессы.|

Конфигурация является глобальной для вашего компьютера и хранится как JSON, где `config path` указывает: `$XDG_CONFIG_HOME/openspec/config.json`, если установлено, иначе `~/.config/openspec/config.json` (macOS, Linux) или `%APPDATA%\openspec\config.json` (Windows). Каждая подкоманда принимает `--scope <scope>`, но сегодня работает только `global`. Любая другая область выходит из 1 с `Error: Project-local config is not yet implemented`.

### openspec config path

```bash
openspec config path
```

```
/Users/you/.config/openspec/config.json
```

### openspec config list

```bash
openspec config list          # читаемые настройки плюс сводка профиля.
openspec config list --json   # сырая конфигурация как JSON
```

**Параметры**

|Флаг|Эффект|
|---|---|
|`--json`|Распечатайте объект конфигурации как JSON.|

**Вывод**

каждый параметр, затем сводка профиля, которая помечает значения как явные или по умолчанию:

```
featureFlags: {}
profile: core
delivery: both

Profile settings:
  profile: core (default)
  delivery: both (default)
  workflows: propose, explore, apply, update, sync, archive (from core profile)
```

### openspec config get

```bash
openspec config get delivery
```

**Аргументы**

|Аргумент|Что это такое|
|---|---|
|`key`|Ключ для чтения. Точки достигают вложенных значений (`featureFlags.workspaces`).|

**Вывод**

простое значение, готовое для сценариев. Объекты печатаются как компактный JSON:

```
both
```

**Коды выхода**

- `0`: напечатано значение.
- `1`: ключ не имеет значения, и ничего не печатается.

### openspec config set

```bash
openspec config set delivery skills
openspec config set featureFlags.workspaces true
```

**Аргументы**

|Аргумент|Что это такое|
|---|---|
|`key`|ключ для записи, разделенный точками для вложенных значений.|
|`value`|новое значение. `true`/`false` становятся логическими значениями, числовые строки становятся числами.|

**Параметры**

|Флаг|Эффект|
|---|---|
|`--string`|сохраните значение в виде строки, пропуская приведение типа.|
|`--allow-unknown`|ключи разрешения, неизвестные схеме.|

**Вывод**

```
Set featureFlags.workspaces = true
```

Неизвестные ключи и недопустимые значения завершаются с ошибкой выхода 1 до того, как что-либо будет сохранено:

```
Error: Invalid configuration key "bogus.key". Unknown top-level key "bogus".
Use "openspec config list" to see available keys.
Pass --allow-unknown to bypass this check.
```

[Русское пояснение подписей и сообщений](../../EXAMPLE_NOTES.md#example-011).


```
Error: Invalid configuration - delivery: Invalid option: expected one of "both"|"skills"|"commands"
```

Если файл конфигурации существует, но не содержит объекта JSON, либо потому, что он вообще недействителен JSON, либо потому, что его корнем является что-то другое, например `null` или массив, `config set`, `config unset` и `config profile` выходят из 1 и оставляют файл без изменений. Исправьте это с помощью `openspec config edit` или замените на `openspec config reset --all`:

```
Error: /home/you/.config/openspec/config.json could not be parsed, so it was left unchanged.
Fix it with "openspec config edit", or reset it with "openspec config reset --all".
```

[Русское пояснение подписей и сообщений](../../EXAMPLE_NOTES.md#example-012).


Пока проблема не будет исправлена, телеметрия и проверка обновлений остаются отключенными.

### openspec config unset

```bash
openspec config unset delivery
```

удаляет ключ, поэтому снова применяется значение по умолчанию. Ключи со встроенными значениями по умолчанию всегда считаются установленными, поэтому это сообщает об успехе, даже если вы никогда их не устанавливали:

```
Unset delivery (reverted to default)
```

ключ без значения печатает `Key "featureFlags.nothere" was not set`. В обоих случаях выход 0. Конфигурационный файл, который не может быть проанализирован, вместо этого выходит из 1, как и в случае с `config set`.

### openspec config reset

```bash
openspec config reset --all      # запрашивает подтверждение
openspec config reset --all -y   # без подсказки
```

**Параметры**

|Флаг|Эффект|
|---|---|
|`--all`|Обязательно. Сбросьте все.|
|`-y, --yes`|пропустить запрос подтверждения.|

**Вывод**

```
Configuration reset to defaults
```

Без `--all` происходит выход из 1 и печатается строка использования.

**Коды выхода**

- `0`: сброс выполнен, или вы ответили «нет» на запрос.
- `1`: `--all` отсутствует.
- `130`: приглашение отменено с помощью Ctrl-C.

### openspec config edit

```bash
openspec config edit
```

открывает файл конфигурации в `$EDITOR` (возврат к `$VISUAL`), сначала создавая его со значениями по умолчанию, если они отсутствуют. Когда редактор закрывается, файл проверяется. Неверный JSON или неверная конфигурация завершает работу 1.

значение редактора может содержать аргументы и пути в кавычках, например `code --wait` или `"/Applications/Sublime Text.app/Contents/SharedSupport/bin/subl" -w`. Он разбивается на слова без оболочки, поэтому `$VAR`, `~` и `;` передаются буквально. Редактор, который не может запуститься или завершает работу с ненулевым значением, печатает однострочную ошибку и завершает работу с кодом 1.

Если редактор не настроен, происходит выход 1:

```
Error: No editor configured
Set the EDITOR or VISUAL environment variable to your preferred editor
Example: export EDITOR=vim
```

### openspec config profile

```bash
openspec config profile        # интерактивный сборщик (требуется терминал)
openspec config profile core   # применить основной пресет напрямую.
```

**Аргументы**

|Аргумент|Что это такое|
|---|---|
|`preset`|необязательное имя предустановки. Существует только `core`. Он выбирает основные рабочие процессы и сохраняет настройки формы установки.|

без предварительной настройки интерактивный инструмент выбора показывает текущую форму установки и рабочие процессы, позволяет изменить один или оба (форма установки: оба, только навыки или только команды; рабочие процессы: список флажков), печатает разницу, а внутри проекта OpenSpec предлагает запустить `openspec update` для вас. За пределами терминала он выходит 1:

```
Interactive mode required. Use `openspec config profile core` or set config via environment/flags.
```

```

```

- `1`: неизвестная предустановка, терминал отсутствует или предложенный `openspec update` не работает.

## openspec list

список изменений или спецификаций `--specs`.

```bash
openspec list                    # активные изменения, сначала самые последние измененные.
openspec list --archived         # заархивированные изменения
openspec list --all              # активные и архивные изменения
openspec list --specs            # спецификации с количеством требований.
openspec list --json             # машиночитаемый, включает разрешенный корень
```

строки поступают из `openspec/changes/` и `openspec/specs/` в выбранный корень. Список изменений по умолчанию пропускает `openspec/changes/archive/`.

**Параметры**

|Флаг|Эффект|
|---|---|
|`--specs`|вместо изменений перечисляйте спецификации.|
|`--changes`|Список изменений. Это значение по умолчанию.|
|`--archived`|отображать только архивные изменения. Невозможно объединить с `--specs`.|
|`--all`|список активных и заархивированных изменений. Невозможно объединить с `--specs`. Имеет приоритет над `--archived`.|
|`--sort <order>`|`recent` (последний измененный первым) или `name`. По умолчанию: `recent`. Спецификации всегда сортируются по имени.|
|`--json`|напечатайте JSON вместо таблицы.|
|`--store <id>`|используйте зарегистрированное хранилище в качестве корня OpenSpec вместо текущего проекта.|

**Вывод**

одна строка на каждое изменение: имя, состояние задачи, последнее изменение. В столбце состояния указано `No tasks`, `2/5 tasks` или `✓ Complete`.

```
Changes:
  add-rate-limit     No tasks      just now
```

`--all` группирует активные и архивированные изменения под отдельными заголовками. Каждая группа использует выбранный порядок сортировки:

```
Changes:
  add-rate-limit     No tasks      just now

Archived Changes:
  2026-08-10-add-login     ✓ Complete    2d ago
```

```
Specs:
  api     requirements 1
```

`--json` добавляет количество задач и `status` `no-tasks`, `in-progress` или `complete`:

```json
{
  "changes": [
    {
      "name": "add-rate-limit",
      "completedTasks": 0,
      "totalTasks": 0,
      "lastModified": "2026-08-11T13:44:40.171Z",
      "status": "no-tasks"
    }
  ],
  "root": {
    "path": "/Users/you/projects/my-app",
    "source": "nearest"
  }
}
```

При использовании `--archived` или `--all` каждый объект изменения включает логическое значение `archived`. Объединенный массив использует выбранный порядок сортировки. Архивное изменение может по-прежнему иметь статус `in-progress`, если в его файле отслеживаемых задач есть непроверенные задачи. Без какого-либо флага форма JSON остается неизменной.

пустой список печатает `No active changes found.`, `No archived changes found.`, `No changes found.` или `No specs found.` и по-прежнему завершается 0.

Изменение — это каталог непосредственно под `openspec/changes/`. В отличие от спецификаций, изменения не могут быть вложены в папку пространства имен. Папка типа `changes/mobile/`, которая содержит только изменения (`changes/mobile/refresh-token/`), отображается со статусом `not a change`, за которым следует предупреждение с именами вложенных каталогов. `--json` помечает эту запись массивом `nested` и добавляет массив `warnings` верхнего уровня. `show`, `status`, `validate` и `archive` отказываются от папки с тем же сообщением. Чтобы это исправить, переместите изменение вверх и сложите пространство имен с его именем:

```bash
mv openspec/changes/mobile/refresh-token openspec/changes/mobile-refresh-token
rmdir openspec/changes/mobile
```

**Коды выхода**

- `0`: список печатается, даже если он пуст.
- `1`: корень OpenSpec не найден (вне проекта нет `--store`).

## openspec show

печатает изменение или спецификацию в виде Markdown или JSON.

```bash
openspec show add-rate-limit              # изменить: распечатывает Offer.md
openspec show add-rate-limit --diff       # изменение: добавить различия требований.
openspec show api                         # spec: печатает spec.md
openspec show api --json --no-scenarios   # спецификация JSON без текста сценария.
```

без имени, show запрашивает изменение или спецификацию, а затем перечисляет элементы на выбор. Вне интерактивного терминала он выходит из 1 и вместо этого печатает прямые формы.

**Аргументы**

|Аргумент|Что это такое|
|---|---|
|`item-name`|изменение или спецификация, отображаемая по имени папки (`add-rate-limit`, `api`).|

**Параметры**

|Флаг|Эффект|
|---|---|
|`--json`|печатать структурированный JSON вместо исходного Markdown.|
|`--type <change\|spec>`|выберите тип, когда изменение и спецификация имеют общее имя.|
|`--no-interactive`|Никогда не запрашивать: отсутствие имени становится ошибкой.|
|`--deltas-only`|JSON, изменение: ограничить вывод дельтами. Изменение JSON уже содержит только дельту, поэтому выходные данные соответствуют простому `--json`.|
|`--requirements-only`|устаревший псевдоним для `--deltas-only`. Выводит предупреждение в stderr.|
|`--diff`|Изменение: добавление дельта-дифференциалов для каждого требования. Игнорируется с предупреждением о спецификациях.|
|`--requirements`|JSON, спецификация: сохранить текст требования, очистить массивы `scenarios`.|
|`--no-scenarios`|JSON, спецификация: тот же вывод, что и у `--requirements`.|
|`-r, --requirement <id>`|JSON, спецификация: вывести одно требование по позиции, отсчитываемой от 1. Невозможно объединить с `--requirements`.|
|`--store <id>`|используйте зарегистрированное хранилище в качестве корня OpenSpec вместо текущего проекта.|

флаги, которые не относятся к разрешенному типу, игнорируются с предупреждением на stderr.

**Вывод**

текстовый режим — это необработанный переход: изменение печатает его `proposal.md`, спецификация печатает его `spec.md`.

```
# Добавить ограничение скорости.

## Why
Unauthenticated clients can exhaust the API.

## What Changes
- Add per-client rate limiting to the public API.
```

Для разнообразия `--diff` сначала печатает предложение, а затем раздел `Specifications Changed (diffs)`. Требования ADDED включают их полный текст. Требования REMOVED сохраняют авторскую причину и миграцию. В требованиях RENAMED указаны FROM и TO. Требования MODIFIED демонстрируют унифицированное отличие от соответствующего основного требования.

Если заголовок MODIFIED соответствует только после складывания регистра или пробела, выходные данные включают в себя как разницу, так и предупреждение о том, что соответствие архива является точным. Если основная спецификация или требование отсутствует, выходные данные предупреждают и печатают полный дельта-блок. Блок MODIFIED без текстовых различий печатает `(no textual changes)`.

Изменение в `--json` имеет дельта-образную форму:

```json
{
  "id": "add-rate-limit",
  "title": "Add rate limiting",
  "deltaCount": 1,
  "deltas": [
    {
      "spec": "api",
      "operation": "ADDED",
      "description": "Add requirement: The API SHALL limit each client to 100 requests per minute.",
      "requirement": {
        "name": "Rate limit",
        "text": "The API SHALL limit each client to 100 requests per minute.",
        "scenarios": [
          {
            "name": "Client exceeds the limit",
            "rawText": "- **WHEN** a client sends its 101st request within a minute\n- **THEN** the API responds 429"
          }
        ]
      },
      ...
    }
  ],
  "root": {
    "path": "/Users/you/projects/my-app",
    "source": "nearest"
  }
}
```

каждое требование содержит свой `name` — текст заголовка после `Requirement:`. Это имя архива соответствует записям MODIFIED, REMOVED и RENAMED. Каждый сценарий имеет свой `name`, текст заголовка после `Scenario:`. Закрывающий запуск `#` для любого заголовка не является частью имени.

`--json --diff` сохраняет форму верхнего уровня. Дельта MODIFIED получает строку `diff`, строку `warning` или обе. Остальные операции не изменяются. Пустая строка `diff` означает, что основной и дельта-блоки текстуально идентичны.

В спецификации `--json` перечислены требования со сценариями. Требования и сценарии содержат те же поля `name`, что и изменения JSON:

```json
{
  "id": "api",
  "title": "api",
  "overview": "Public HTTP API behavior.",
  "requirementCount": 1,
  "requirements": [
    {
      "name": "Health endpoint",
      "text": "The API SHALL expose a health endpoint.",
      "scenarios": [
        {
          "name": "Health check succeeds",
          "rawText": "- **WHEN** a client requests GET /health\n- **THEN** the API responds 200"
        }
      ]
    }
  ],
  "metadata": {
    "version": "1.0.0",
    "format": "openspec"
  },
  "root": {
    "path": "/Users/you/projects/my-app",
    "source": "nearest"
  }
}
```

неизвестное имя предполагает близкое совпадение: `Unknown item 'does-not-exist'. Did you mean: add-rate-limit, api?`. Имя, которое соответствует ошибкам изменения и спецификации и запрашивает `--type`.

**Коды выхода**

- `0`: элемент напечатан.
- `1`: неизвестное или неоднозначное имя, отсутствие имени за пределами терминала, индекс `-r` вне диапазона, `--requirements` в сочетании с `-r` или невозможно прочитать дельта- или основную спецификацию для `--diff`.

## openspec validate

проверяет изменения и спецификации на наличие структурных проблем.

```bash
openspec validate add-rate-limit   # одно изменение или спецификация по имени.
openspec validate --all            # все изменения и характеристики.
```

без имени и массового флага проверка предлагает вам выбрать элементы. Вне интерактивного терминала он выходит из 1 и вместо этого печатает флаги массовой загрузки.

**Аргументы**

|Аргумент|Что это такое|
|---|---|
|`item-name`|изменение или спецификация для проверки по имени папки (`add-rate-limit`, `api`).|

**Параметры**

|Флаг|Эффект|
|---|---|
|`--all`|Проверьте каждое изменение и спецификацию.|
|`--changes`|Подтвердите каждое изменение.|
|`--specs`|Проверьте каждую спецификацию.|
|`--archived`|проверка выполнения задачи в архивных изменениях без проверки изменений примененных спецификаций.|
|`--strict`|рассматривать предупреждения как сбои.|
|`--type <change\|spec>`|выберите тип, когда изменение и спецификация имеют общее имя.|
|`--json`|печать структурированного отчета вместо текста.|
|`--report <mode>`|Массовый вывод: `full` (по умолчанию) или `findings`. Требуется явная массовая область действия.|
|`--concurrency <n>`|Максимальное количество параллельных проверок при массовых запусках. По умолчанию: `OPENSPEC_CONCURRENCY`, иначе 6.|
|`--no-interactive`|Никогда не запрашивать: отсутствующее или неоднозначное имя становится ошибкой.|
|`--store <id>`|используйте зарегистрированное хранилище в качестве корня OpenSpec вместо текущего проекта.|

**Вывод**

Массовые прогоны печатают одну строку состояния для каждого элемента, за которой следуют все результаты и завершаются итоговыми данными:

```
✓ change/add-rate-limit
✓ spec/api
Totals: 2 passed, 0 failed (2 items)
```

**Выводы по флажку задачи**

Прогресс учитывает флажки и ничего больше, поэтому файл задач, записанный простыми маркерами, читается как нулевые задачи: `openspec list` и `openspec status` сообщают об отсутствии работы, а `openspec archive` не имеет ничего, что можно было бы пометить как незавершенное. Проверка отчетов `WARNING` для каждого файла отслеживаемой задачи, в котором перечислены работы без флажка:

```text
⚠ [ВНИМАНИЕ] Tasks.md: Это изменение считается как 0 задач: ни одна строка в файлах отслеживаемых задач не является флажком, поэтому «список openspec» и «состояние openspec» сообщают об отсутствии работы, а «архив openspec» не имеет ничего, что можно было бы пометить как незавершенное. Запишите каждую задачу как «- [ ] 1.1 Описание».
```

предупреждение срабатывает только в том случае, если во всем отслеживаемом наборе изменений вообще нет флажка. Ни один файл текстовой информации, кроме настоящего контрольного списка, не сообщается, и изменение в процессе написания сохраняет свой прогресс, как только существует единственный флажок. `--strict` превращает предупреждение в сбой. Номер строки указан в отчете `--json`.

Огражденные блоки, HTML-комментарии, вступительная часть YAML и код с отступом не сканируются, поэтому вставленный образец терминала никогда не принимается за список задач.

**Результаты слияния архива**

Для изменений проверка запускает построитель слияния архива в соответствии с текущими основными спецификациями без записи файлов. Он сообщает о конфликтах слияния, таких как отсутствие цели `MODIFIED` или конфликтующее требование `ADDED`, как `INFO`:

```text
ℹ [INFO] api/spec.md: Архив откажется от этой разницы: API MODIFIED не удалось выполнить заголовок «### Требование: ограничение скорости» — не найдено
```

эти результаты появляются даже после прохождения проверки как в текстовом виде, так и в выводе JSON. `INFO` никогда не меняет код выхода, в том числе в `--strict`: отсутствующая цель может принадлежать одноуровневому изменению, которое еще не заархивировано. Дельты, уже синхронизированные с основными спецификациями, соответствуют существующим правилам слияния архива.

Эта проверка не запускает более поздние проверки объединенной спецификации архива или проверки вывода из эксплуатации. Чистый отчет не гарантирует успеха архивирования.

Если предварительная проверка слияния не может начаться, ошибка `INFO` объясняет, почему. Существующие результаты проверки и код завершения остаются неизменными.

В элементе с ошибкой перечислены все проблемы и исправления:

```
Change 'add-rate-limit' has issues
✗ [ERROR] api/spec.md: ADDED "Rate limiting" must include at least one scenario
Next steps:
  - Ensure change has deltas in specs/: use headers ## ADDED/MODIFIED/REMOVED/RENAMED Requirements
  - Each requirement MUST include at least one #### Scenario: block
  - Debug parsed deltas: openspec show add-rate-limit --json --deltas-only
```

[Русское пояснение подписей и сообщений](../../EXAMPLE_NOTES.md#example-015).


`--json` печатает один отчет за прогон:

```json
{
  "items": [
    {
      "id": "add-rate-limit",
      "type": "change",
      "valid": true,
      "issues": [],
      "durationMs": 2
    }
  ],
  "summary": {
    "totals": {
      "items": 1,
      "passed": 1,
      "failed": 0
    },
    "byType": {
      "change": {
        "items": 1,
        "passed": 1,
        "failed": 0
      }
    }
  },
  "version": "1.0",
  "root": {
    "path": "/Users/you/projects/my-app",
    "source": "nearest"
```

записи `issues` содержат `level` `ERROR`, `WARNING` или `INFO`.

**Коды выхода**

- `0`: пройден каждый проверенный элемент, включая пустую массовую область.
- `1`: элемент не выполнен, запрос отчета недействителен или запуск не выполнен (например, неизвестное имя или отсутствие корня OpenSpec).

<a id="--report-fullfindings"></a>
### --report полный|выводы

выбирает выходные данные для явной области массовой проверки:

- **`full`**: каждый элемент. Это значение по умолчанию. Явный `--report full` сохраняет существующую форму вывода без добавления метаданных отчета.
- **`findings`**: только элементы с проблемами, включая проходящие элементы с предупреждениями или информацией. Каждый элемент по-прежнему проверяется. Итоговые значения, поведение в строгом режиме и коды выхода не изменяются.

```bash
openspec validate --all --report findings
openspec validate --archived --report findings --json
```

**Области применения**

|Флаги|Выводы `report.scope`|
|---|---|
|`--all`|`all`|
|`--changes`|`changes`|
|`--specs`|`specs`|
|`--changes --specs` или `--all` с любым флагом.|`all`|
|`--archived`|`archived`|

оба режима явного отчета отклоняют имя позиционного элемента, отсутствующую объемную область или комбинацию архивных и активных областей.

<a id="findings-text-output"></a>
#### текстовый вывод результатов

**Человеческий вывод**: стандартный вывод выводит `Scope: <scope> (<count> items)`, а затем суммирует. Без проблемных элементов:

```text
Область применения: все (2 шт.)
Ничего не найдено.
Всего: 2 пройдено, 0 не пройдено (2 элемента).
```

метки проблемных элементов, метки серьезности, пути и сообщения печатаются в поток stderr. При сбоях активной области после подсчета итогов сохраняется подсказка о повторном запуске `Details:`. Существующий корневой баннер и выходные данные о ходе выполнения могут предшествовать отчету.

<a id="findings-json-output"></a>
#### Выводы JSON

`--report findings --json` печатает один документ. В этом примере есть два чистых элемента:

```json
{
  "report": {
    "kind": "validation-findings",
    "version": "1.0",
    "scope": "all",
    "returnedItems": 0,
    "totalItems": 2
  },
  "itemFindings": [],
  "summary": {
    "totals": { "items": 2, "passed": 2, "failed": 0 },
    "byType": {
      "change": { "items": 1, "passed": 1, "failed": 0 },
      "spec": { "items": 1, "passed": 1, "failed": 0 }
    }
  },
  "root": { "path": "/Users/you/projects/my-app", "source": "nearest" }
}
```

- **`report.kind` и `report.version`**: идентифицируют форму `validation-findings`, версию `1.0`. `version` или `items` верхнего уровня не существует.
- **`report.returnedItems` и `report.totalItems`**: подсчитывают возвращенные записи и все проверенные элементы соответственно.
- **`itemFindings`**: полные записи элементов, массив `issues` которых не пуст. Включает проблемы `ERROR`, `WARNING` и `INFO`. Каждая запись сохраняет `id`, `type`, `valid`, `issues` и `durationMs`. Архивированные элементы используют `type: "change"`.
- **`summary`**: общие итоговые значения и счетчики по типам, а не счетчики возвращаемого подмножества. Пустая область имеет нулевые итоги и выход 0.
- **`root`**: те же метаданные выбранного корня, что и в полном отчете.

**Сохранение записей**: возвращаемые элементы сохраняют порядок полного отчета и все дополнительные поля по элементам или проблемам. Фильтрация не перезаписывает сообщения или местоположения, включая необязательные поля `line` и `column`.

**Ошибки команд**: ошибки выбора корня или обнаружения элементов сохраняют существующую диагностику `status` и завершают работу 1. Они не возвращают завершенный отчет о результатах или успешный пустой отчет.

<a id="invalid-report-requests"></a>
#### неверные запросы отчетов.

Оба режима явного отчета отклоняют эти запросы до выбора корня или обнаружения элемента:

- неподдерживаемое значение отчета, включая пустую строку.
- позиционное имя элемента, даже с групповым флагом.
- нет явной массовой области действия.
- `--archived` в сочетании с `--all`, `--changes` или `--specs`.

В режиме JSON отклоненный запрос выходит из 1 только с одноэлементным массивом `status`. У него нет `root` или полезной нагрузки отчета:

```bash
openspec validate --all --report bogus --json
```

```json
{
  "status": [
    {
      "severity": "error",
      "code": "invalid_validation_report_request",
      "message": "Unknown validation report 'bogus'.",
      "fix": "Use --report full|findings with --all, --changes, --specs, or --archived, without an item name. Do not combine archived and active scopes."
    }
  ]
}
```

в человеческом режиме ошибка выводится в поток stderr. Пустой `--report` без значения является синтаксической ошибкой Commander в stderr, в том числе с `--json`; он не использует этот диагностический конверт.

<a id="filter-a-full-report-externally"></a>
#### внешняя фильтрация полного отчета.

Для пользовательского представления JSON отфильтруйте полный отчет с помощью `jq` или PowerShell. Эти примеры сценариев сохраняют код выхода проверки и оставляют нетронутыми документы об ошибках команд.

В Bash с `jq`:

```bash
if validation_json=$(openspec validate --all --json); then
  validation_exit=0
else
  validation_exit=$?
fi
printf '%s\n' "$validation_json" |
  jq 'if has("items") then .items |= map(select(.issues | length > 0)) else . end'
exit "$validation_exit"
```

В PowerShell:

```powershell
$validationJson = openspec validate --all --json
$validationExit = $LASTEXITCODE
$validationReport = $validationJson | ConvertFrom-Json
if ($validationReport.PSObject.Properties.Name -contains 'items') {
  $validationReport.items = @($validationReport.items | Where-Object { $_.issues.Count -gt 0 })
}
$validationReport | ConvertTo-Json -Depth 100
exit $validationExit
```

эти пользовательские представления сохраняют ключи полного отчета, но пропускают чистые элементы. Они не являются ни полными отчетами полной версии 1, ни версией `--report findings`.

## openspec archive

перемещает завершенное изменение в архив и обновляет основные спецификации.

```bash
openspec archive add-rate-limit -y                # заархивировать одно изменение, объединить его изменения
openspec archive add-rate-limit -y --skip-specs   # архив не трогая спецификации
```

Без имени архив предложит вам выбрать изменение. За пределами интерактивного терминала он выходит из 1 и вместо этого печатает команду повторного запуска.

**Аргументы**

|Аргумент|Что это такое|
|---|---|
|`change-name`|Изменение архива по имени папки (`add-rate-limit`).|

**Параметры**

|Флаг|Эффект|
|---|---|
|`-y, --yes`|На каждое подтверждение отвечайте «да»: обновления спецификаций, незавершенные задачи, пропущенная проверка.|
|`--skip-specs`|Архивируйте, не затрагивая основные спецификации (инфраструктура, инструменты или изменения только в документации).|
|`--no-validate`|Пропустить проверку. Архив сначала попросит вас подтвердить, и `-y` ответит на него.|
|`--json`|печатайте структурированный результат вместо текста. Требуется `--yes` для подтверждения обновлений спецификаций.|
|`--store <id>`|используйте зарегистрированное хранилище в качестве корня OpenSpec вместо текущего проекта.|

**Вывод**

при успешном запуске сообщается о состоянии задачи, просматриваются обновления спецификаций, применяются их и присваивается имя папке архива:

```
Task status: ✓ Complete

Specs to update:
  api: update
Applying changes to openspec/specs/api/spec.md:
  + 1 added
Totals: + 1, ~ 0, - 0, → 0
Specs updated successfully.
Change 'add-rate-limit' archived as '2026-08-11-add-rate-limit'.
```

[Русское пояснение подписей и сообщений](../../EXAMPLE_NOTES.md#example-016).


Папка изменений целиком перемещается в `openspec/changes/archive/2026-08-11-add-rate-limit/`, к ее имени добавляется сегодняшняя дата. Каждая дельта сливается со своей основной спецификацией: требование ADDED, указанное выше, было добавлено к `openspec/specs/api/spec.md`. Без `-y` архив показывает превью и спрашивает перед обновлением. Отказ по-прежнему сохраняет изменения и оставляет спецификации в покое.

С `--json --yes`:

```json
{
  "archive": {
    "change": "add-rate-limit",
    "archivedAs": "2026-08-11-add-rate-limit",
    "path": "/Users/you/projects/my-app/openspec/changes/archive/2026-08-11-add-rate-limit",
    "specsUpdated": true,
    "totals": {
      "added": 1,
      "modified": 0,
      "removed": 0,
      "renamed": 0
    }
  },
  "root": {
    "path": "/Users/you/projects/my-app",
    "source": "nearest"
  }
}
```

Архив сначала проверяет изменение и отклоняет неудачное:

```
Validation errors in change delta specs:
  ✗ ADDED "Rate limiting" must include at least one scenario

Validation failed. Please fix the errors before archiving.
To skip validation (not recommended), use --no-validate flag.
```

[Русское пояснение подписей и сообщений](../../EXAMPLE_NOTES.md#example-017).


Невыполненные задачи предупреждают, но не блокируют. В интерактивном режиме архив спрашивает, продолжать ли, а `-y` продолжает самостоятельно:

```
Task status: 1/2 tasks
Warning: 1 incomplete task(s) found. Continuing due to --yes flag.
```

**Коды выхода**

- `0`: изменение было заархивировано, с обновлениями спецификаций или без них.
- `1`: проверка не удалась, имя изменения неизвестно, или требовалось подтверждение, и ответ не удалось прочитать.

## openspec new

Создает новый каталог изменений.

```bash
openspec new change add-caching                                # только метаданные
openspec new change add-search --goal "Users can search docs"  # записать гол
```

`new` имеет одну подкоманду `new change <name>`. Он создает `openspec/changes/<name>/`, содержащий один [файл метаданных `.openspec.yaml`](configuration/change-metadata.md):

```yaml
schema: spec-driven
created: 2026-08-11
```

Артефакты (предложение, спецификации, дизайн, задачи) здесь не представлены. Вы пишете их позже, и `openspec status` сообщает вам, какой из них следующий.

**Аргументы**

|Аргумент|Что это такое|
|---|---|
|`name`|Имя папки для изменений (`add-caching`).|

**Параметры**

|Флаг|Эффект|
|---|---|
|`--description <text>`|Также создайте `README.md` в каталоге изменений с этим текстом.|
|`--goal <text>`|сохраните строку `goal:` в `.openspec.yaml`.|
|`--schema <name>`|Схема рабочего процесса для изменения. По умолчанию: `spec-driven`, единственная поставляемая схема.|
|`--json`|распечатайте созданное изменение как JSON вместо текста.|
|`--store <id>`|используйте зарегистрированное хранилище в качестве корня OpenSpec вместо текущего проекта.|

**Вывод**

```
Created change 'add-caching' at openspec/changes/add-caching/
Schema: spec-driven
Next: openspec status --change add-caching
```

Если каталог `openspec/` не найден, `new change` создает его там, где вы находитесь, и сообщает следующее:

```
Created change 'add-caching' at openspec/changes/add-caching/
Schema: spec-driven
Next: openspec status --change add-caching

Note: no OpenSpec root was found here, so one was created at openspec/.
Run `openspec init` to finish setting this project up, or delete that directory if you meant a different project.
```

[Русское пояснение подписей и сообщений](../../EXAMPLE_NOTES.md#example-018).


уведомление отправляется на стандартный вывод вместе с остальными выводами человека и никогда не появляется с `--json`.

С `--json` в проекте, в котором уже есть `openspec/`:

```json
{
  "change": {
    "id": "add-caching",
    "path": "/Users/you/projects/my-app/openspec/changes/add-caching",
    "metadataPath": "/Users/you/projects/my-app/openspec/changes/add-caching/.openspec.yaml",
    "schema": "spec-driven"
  },
  "root": {
    "path": "/Users/you/projects/my-app",
    "source": "nearest"
  }
}
```

Если каталог `openspec/` не найден и `new change` его создал, JSON имеет ту же форму. `root.path` — это каталог, из которого вы его запустили, а `root.source` читает `implicit`:

```json
"root": {
  "path": "/Users/you/projects/my-app",
  "source": "implicit"
}
```

**Коды выхода**

- `0`: изменение создано.
- `1`: изменение уже существует или схема неизвестна.

## openspec status

сообщает о состоянии завершения артефакта для одного или каждого активного изменения.

```bash
openspec status --change add-rate-limit          # просмотр контрольного списка
openspec status --change add-rate-limit --json   # структурированный отчет
openspec status --all                            # каждое активное изменение.
openspec status --all --json                     # один пакетный отчет
```

При наличии активных изменений используйте только один из `--change` или `--all`. Без этого статус выходит из 1 и перечисляет доступные изменения, даже если существует только одно:

```text
✖ Ошибка: отсутствует обязательная опция --change (или --all для каждого активного изменения). Доступные изменения:
  добавить ограничение скорости
```

Если в проекте нет активных изменений, статус печатает `No active changes. Create one with: openspec new change <name>` и завершает работу с 0 даже без какого-либо флага. С `--all --json` такое же пустое состояние — `{ "changes": [], "message": "No active changes.", "root": ... }`.

**Параметры**

|Флаг|Эффект|
|---|---|
|`--change <id>`|изменение, о котором нужно сообщить, по имени папки.|
|`--all`|сообщать о каждом активном изменении, отсортированном по имени. Невозможно объединить с `--change`.|
|`--schema <name>`|переопределить схему, автоматически определенную из `openspec/config.yaml`. Неизвестное имя является ошибкой.|
|`--json`|печать структурированного отчета вместо текста.|
|`--store <id>`|используйте зарегистрированное хранилище в качестве корня OpenSpec вместо текущего проекта.|

**Вывод**

Контрольный список артефактов схемы: `[x]` выполнен, `[ ]` готов к записи, `[-]` заблокирован до тех пор, пока не появятся артефакты, от которых он зависит.

```
Change: add-rate-limit
Schema: spec-driven
Change root: /Users/you/projects/my-app/openspec/changes/add-rate-limit
Progress: 2/4 artifacts complete

[x] proposal
[x] specs
[ ] design
[-] tasks (blocked by: design)

Next: openspec instructions design --change "add-rate-limit" --json
```

[Русское пояснение подписей и сообщений](../../EXAMPLE_NOTES.md#example-019).


строка `Next:` называет одну команду, которая перемещает изменение вперед, поэтому `openspec status` достаточно, чтобы восстановить изменение в новом сеансе. Он называет следующий готовый артефакт, пока планирование еще не завершено, и `openspec instructions apply`, когда каждый артефакт планирования существует:

```
[x] proposal
[x] specs
[x] design
[x] tasks

All planning artifacts complete!
Next: openspec instructions apply --change "add-rate-limit" --json
```

он содержит `--store <id>` всякий раз, когда выбранный корень является хранилищем, и называет ту же команду, что и предложение JSON `nextSteps`.

`--json` добавляет зависимости для каждого артефакта, разрешенные пути к файлам и предлагаемый следующий шаг. Обрезано:

```json
{
  "changeName": "add-rate-limit",
  "schemaName": "spec-driven",
  "isComplete": false,
  "nextSteps": [
    "Run openspec instructions design --change \"add-rate-limit\" --json before writing that artifact."
  ],
  "artifacts": [
    {
      "id": "proposal",
      "outputPath": "proposal.md",
      "status": "done",
      "requires": []
    },
    {
      "id": "design",
      "outputPath": "design.md",
      "status": "ready",
      "requires": [
        "proposal"
      ]
    },
    {
      "id": "tasks",
      "outputPath": "tasks.md",
      "status": "blocked",
      "requires": [
        "specs",
        "design"
      ],
      "missingDeps": [
        "design"
      ]
    }
  ]
}
```

В случае `--all --json` `changes` содержит один и тот же объект состояния для каждого изменения, без `root` для каждого изменения. Выбранный корень один раз появляется на конверте. В этом примере обрезаются поля статуса каждого изменения, показанные выше:

```json
{
  "changes": [
    {
      "changeName": "add-rate-limit",
      "schemaName": "spec-driven",
      "artifacts": []
    }
  ],
  "root": {
    "path": "/Users/you/projects/my-app",
    "source": "nearest"
  }
}
```

Если одно изменение не может загрузиться, пакет продолжается. Его запись содержит `changeName` и диагностику `status`, тогда как остальные записи остаются доступными. Команда завершает работу 1, в том числе в режиме JSON, поэтому CI не принимает неполный отчет как успешный. Вывод JSON остается одним анализируемым документом.

**Коды выхода**

- `0`: печатается каждый запрошенный статус; пустой отчет `--all` также выходит из 0.
- `1`: не удалось загрузить запрошенное изменение, `--change` или `--all` отсутствует, два флага были объединены, изменение не существует или переопределение схемы неизвестно.

## openspec instructions

печатает инструкции по созданию артефакта, его применению или архивированию. Ваш агент запускает это во время рабочего процесса, чтобы получить текст инструкций для следующего шага.

```bash
openspec instructions proposal --change add-rate-limit   # как написать один артефакт
openspec instructions apply --change add-rate-limit      # как реализовать изменение
openspec instructions archive --change add-rate-limit    # входы для архивирования
```

**Аргументы**

|Аргумент|Что это такое|
|---|---|
|`artifact`|идентификатор артефакта из схемы (`proposal`, `specs`, `design`, `tasks` в `spec-driven`) или зарезервированные слова `apply` и `archive`.|

**Параметры**

|Флаг|Эффект|
|---|---|
|`--change <id>`|изменение для создания инструкций. Необходимый.|
|`--schema <name>`|переопределить схему. В противном случае автоматически определяется из `config.yaml`.|
|`--json`|вместо текста печатается структурированный объект.|
|`--store <id>`|используйте зарегистрированное хранилище в качестве корня OpenSpec вместо текущего проекта.|

**Вывод**

Форма артефакта печатает один блок инструкций: задачу, файл для записи, способ его записи, шаблон артефакта и то, что разблокируется при его выполнении.

```
<artifact id="proposal" change="add-rate-limit" schema="spec-driven">

<task>
Create the proposal artifact for change "add-rate-limit".
Initial proposal document outlining the change
</task>

<output>
Write to: /Users/you/projects/my-app/openspec/changes/add-rate-limit/proposal.md
</output>

<instruction>
Create the proposal document that establishes WHY this change is needed.
...
```

[Русское пояснение подписей и сообщений](../../EXAMPLE_NOTES.md#example-020).


`apply` печатает контекстные файлы, ход выполнения задачи и рабочие инструкции:

```
## Apply: add-rate-limit
Schema: spec-driven

### Context Files
- proposal: /Users/you/projects/my-app/openspec/changes/add-rate-limit/proposal.md
- specs: /Users/you/projects/my-app/openspec/changes/add-rate-limit/specs/api/spec.md
- tasks: /Users/you/projects/my-app/openspec/changes/add-rate-limit/tasks.md

### Progress
1/3 complete

### Tasks
- [x] 1.1 Add rate limit middleware
- [ ] 1.2 Return 429 with Retry-After header
- [ ] 1.3 Add tests for burst traffic

### Instruction
Read context files, work through pending tasks, mark complete as you go.
Pause if you hit blockers or need clarification.

No project context or operation guidance configured.
```

[Русское пояснение подписей и сообщений](../../EXAMPLE_NOTES.md#example-021).


Если необходимые артефакты отсутствуют, `apply` сообщает `### ⚠️ Blocked` и вместо этого называет их. `archive` печатает имя изменения, а также любой контекст проекта и руководство по эксплуатации из конфигурации. Если ничего не настроено, написано так и не более того.

в `--json` каждая форма возвращает один объект. Форма артефакта начинается:

```json
{
  "changeName": "add-rate-limit",
  "artifactId": "proposal",
  "schemaName": "spec-driven",
  "changeDir": "/Users/you/projects/my-app/openspec/changes/add-rate-limit",
  ...
```

и продолжается `outputPath`, `existingOutputPaths`, полными строками `instruction` и `template`, `dependencies`, `unlocks` и `root`. Форма `apply` содержит `contextFiles`, `progress`, `tasks`, `taskTrackingConfigured`, `state` (`blocked`, `ready`, `all_done`) и `instruction`.

каждая запись `tasks` содержит `id`, `description`, `done`, `sourcePath` и `line`. `sourcePath` — это абсолютный путь к отслеживаемому файлу, который предоставил задачу. `line` — это номер строки флажка задачи, начинающийся с единицы, в этом файле.

`taskTrackingConfigured` всегда является логическим значением: `true`, когда схема устанавливает ненулевое значение [`apply.tracks`](schemas/schema-yaml.md#tracks), даже если ни один файл не соответствует, и `false` в противном случае. Если совпадающий файл отслеживания не может быть прочитан, `unavailableTrackingFiles` содержит его абсолютный `path` и ошибку `reason`. Это поле опускается, если каждый совпавший файл доступен для чтения. Читаемые файлы по-прежнему используются в `tasks` и `progress`, но `state` не может быть `all_done`, пока не будет прочитан каждый совпадающий файл.

**Коды выхода**

- `0`: инструкция напечатана.
- `1`: неизвестный артефакт, неизвестное изменение, неизвестная схема или отсутствует `--change`. Для каждой ошибки перечислены допустимые значения.

## openspec schema

проверяет, разветвляет или создает схему (экспериментальная). Каждая подкоманда сначала печатает `Note: Schema commands are experimental and may change.` в stderr.

```bash
openspec schema which spec-driven          # где разрешается схема
openspec schema fork spec-driven my-flow   # скопировать схему в проект.
openspec schema init my-schema             # создать схему с нуля.
```

|Подкоманда|Что он делает|
|---|---|
|`which`|показать, откуда разрешается схема.|
|`validate`|проверьте структуру и шаблоны схемы.|
|`fork`|скопируйте существующую схему в проект для настройки.|
|`init`|Создайте новую локальную схему проекта.|

схемы разрешаются из трех мест. Победа в первом матче:

|Источник|Расположение|
|---|---|
|`project`|`openspec/schemas/` в текущем проекте.|
|`user`|`~/.local/share/openspec/schemas/` (соблюдаются `XDG_DATA_HOME` и Windows `%LOCALAPPDATA%`).|
|`package`|Схемы, поставляемые с CLI. Здесь живет `spec-driven`.|

### openspec schema which

показывает, какую копию схемы будет использовать CLI.

```bash
openspec schema which spec-driven
openspec schema which --all        # все схемы, сгруппированные по источнику.
```

**Аргументы**

|Аргумент|Что это такое|
|---|---|
|`name`|Схема для поиска. Требуется, если не установлен `--all`. Без любого из них, который выходит из 1.|

**Параметры**

|Флаг|Эффект|
|---|---|
|`--all`|перечислите каждую схему с указанием источника разрешения.|
|`--json`|Распечатайте разрешение как JSON.|

**Вывод**

```
Schema: spec-driven
Source: package
Path: /usr/local/lib/node_modules/@fission-ai/openspec/schemas/spec-driven
```

Когда копия с более высоким приоритетом скрывает другую, в разделе `Shadows:` перечислены скрытые копии. С `--json`:

```json
{
  "name": "my-flow",
  "source": "project",
  "path": "/Users/you/projects/my-app/openspec/schemas/my-flow",
  "shadows": []
}
```

неизвестное имя выходит из 1 и отображает список доступных схем.

### openspec schema validate

проверяет структуру и шаблоны схемы.

```bash
openspec schema validate spec-driven   # одна схема из любого источника.
openspec schema validate               # каждая локальная схема проекта.
```

он проверяет существование `schema.yaml` и анализирует, соответствует ли структура формату схемы, что файл шаблона каждого артефакта существует внутри каталога схемы `templates/` и что граф зависимостей не содержит циклов или неизвестных ссылок, в том числе в `apply.requires`. Значение `apply.tracks`, которое не совсем равно значению `generates` некоторого артефакта, печатает строку `warning:`, но не проходит проверку, поскольку тогда OpenSpec не может определить, к какому прогрессу артефакта принадлежит этот файл.

**Параметры**

|Флаг|Эффект|
|---|---|
|`--json`|печать структурированного отчета вместо текста.|
|`--verbose`|распечатайте каждый этап проверки.|

**Вывод**

```
✓ Schema 'spec-driven' is valid
```

без имени каждая схема проекта получает одну строку под заголовком `Validation Results:`. Неудачная схема перечисляет свои проблемы, и выполнение завершается 1:

```
✗ Schema 'my-schema' has errors:
  error: Template file 'tasks.md' not found for artifact 'tasks'
```

копирует существующую схему в проект, чтобы вы могли ее настроить.


**Аргументы**

|Аргумент|Что это такое|
|---|---|
|`source`|схема для копирования из любого исходного расположения.|
|`name`|имя копии. Кебаб-кейс (`my-workflow`). По умолчанию: `<source>-custom`.|

**Параметры**

|Флаг|Эффект|
|---|---|
|`--force`|перезаписать существующую целевую схему.|
|`--json`|Распечатайте результат как JSON.|

**Вывод**

```
✔ Forked 'spec-driven' to 'my-flow'

```

[Русское пояснение подписей и сообщений](../../EXAMPLE_NOTES.md#example-023).


форк попадает в `openspec/schemas/`, а поле `name:` в его `schema.yaml` перезаписывается на новое имя:

```
openspec/schemas/my-flow/
├── schema.yaml
└── templates/
    ├── design.md
    ├── proposal.md
    ├── spec.md
```

существующий пункт назначения является ошибкой, если вы не укажете `--force`. Ответвление, сохраняющее имя источника, затеняет оригинал.

### openspec schema init

Создает новую локальную схему проекта с начальными шаблонами.

```bash
openspec schema init my-schema --description "Lightweight flow" --artifacts proposal,tasks
```

если в интерактивном терминале нет `--description` и `--artifacts`, init запрашивает описание, контрольный список артефактов и вопрос о том, следует ли сделать схему проектом по умолчанию. Вне терминала используются значения по умолчанию, указанные ниже.

**Аргументы**

|Аргумент|Что это такое|
|---|---|
|`name`|имя новой схемы. Кебаб-кейс (`my-workflow`).|

**Параметры**

|Флаг|Эффект|
|---|---|
|`--description <text>`|Описание схемы. По умолчанию: `Custom workflow schema for <name>`.|
|`--artifacts <list>`|разделенные запятыми идентификаторы артефактов из `proposal`, `specs`, `design`, `tasks`. По умолчанию: все четыре.|
|`--default`|записывает `schema: <name>` в существующий `openspec/config.yaml` или `openspec/config.yml`. Создает `openspec/config.yaml`, если ни один из них не существует. Новые изменения используют эту схему.|
|`--no-default`|пропустить запрос о значении по умолчанию.|
|`--force`|перезаписать существующую схему с тем же именем.|
|`--json`|Распечатайте результат как JSON.|

Создание схемы и обновление конфигурации `--default` — это одна операция. Если OpenSpec не может проверить или записать конфигурацию, она оставляет без изменений и конфигурацию, и любую существующую схему.

**Вывод**

```
✔ Created schema 'my-schema'

Schema created at: /Users/you/projects/my-app/openspec/schemas/my-schema

Artifacts: proposal, tasks
```

Макет на диске:

```
openspec/schemas/my-schema/
├── schema.yaml
└── templates/
    ├── proposal.md
    └── tasks.md
```

`schema.yaml` связывает выбранные артефакты с их зависимостями. Когда `tasks` включен, он также получает фазу `apply`, которая отслеживает `tasks.md`. Используйте схему с `openspec new --schema my-schema`.

## openspec store

Создает хранилища и управляет ими: автономные репозитории OpenSpec, зарегистрированные на вашем компьютере.

```bash
openspec store setup team-context --path ~/openspec/team-context   # создать и зарегистрировать
openspec store register ~/stores/design-system                     # зарегистрировать существующую кассу
openspec store list                                                # посмотреть, что зарегистрировано
```

регистрации хранятся в реестре каждого компьютера: `~/.local/share/openspec/stores/registry.yaml` или `$XDG_DATA_HOME/openspec/stores/registry.yaml`, если установлен `XDG_DATA_HOME`. Каждая подкоманда использует `--json` для печати структурированного отчета вместо текста. Запуск `openspec store` с отсутствующей или неизвестной подкомандой завершает работу 1 и выводит список подкоманд.

|Подкоманда|Что он делает|
|---|---|
|`setup [id]`|Создайте папку хранилища и зарегистрируйте ее.|
|`register [path]`|Зарегистрируйте существующую папку хранилища.|
|`unregister <id>`|Забудьте о регистрации. Папка остается на диске.|
|`remove <id>`|Забудьте регистрацию и удалите папку.|
|`list` (псевдоним `ls`)|список зарегистрированных хранилищ.|
|`doctor [id]`|проверьте регистрацию, метаданные и состояние Git для зарегистрированных хранилищ.|

### openspec store setup

Создает папку хранилища и регистрирует ее.

```bash
openspec store setup team-context --path ~/openspec/team-context
```

В интерактивном терминале программа установки запрашивает отсутствующее имя и местоположение и подтверждает, прежде чем что-либо создавать. За пределами одного, отсутствующее имя или `--path` выходит из 1 с флагом для передачи. Повторная настройка для зарегистрированного хранилища сообщает `Registry: already registered`.

Программа установки завершает работу с номером 1 с помощью `store_setup_inside_git_repo`, когда `--path` находится внутри другого репозитория Git, поскольку инициализация хранилища там будет вкладывать один репозиторий в другой. `--no-init-git` не создает репозиторий, поэтому пропускает эту проверку. Используйте его, чтобы сохранить хранилище по адресу `~/openspec/<id>`, когда ваш домашний каталог сам по себе является репозиторием Git, например репозиторием точечных файлов.

**Аргументы**

|Аргумент|Что это такое|
|---|---|
|`id`|название хранилища. Он становится идентификатором, который вы передаете `--store`.|

**Параметры**

|Флаг|Эффект|
|---|---|
|`--path <path>`|Папка, в которой должен находиться хранилище (расширяется `~`).|
|`--init-git`|инициализируйте репозиторий Git с помощью первоначальной фиксации. По умолчанию.|
|`--no-init-git`|пропускать все действия Git: ни инициализации, ни первоначальной фиксации.|
|`--remote <url>`|источник канонического клона, записанный в `store.yaml`.|

**Вывод**

```
Store ready: team-context
Location: /Users/you/stores/team-context
OpenSpec root: ready
Registry: registered

Next: run normal OpenSpec commands against this store, for example:
  openspec new change <change-id> --store team-context
Share this store by committing and pushing it like any Git repo.
```

[Русское пояснение подписей и сообщений](../../EXAMPLE_NOTES.md#example-024).


`--json` сообщает, что было создано и где зарегистрировано:

```json
{
  "store": {
    "id": "design-system",
    "root": "/Users/you/stores/design-system",
    "metadata_path": "/Users/you/stores/design-system/.openspec-store/store.yaml"
  },
  "registry": {
    "path": "/Users/you/.local/share/openspec/stores/registry.yaml",
    "registered": true,
    "already_registered": false
  },
  "git": {
    "is_repository": true,
    "initialized": true,
    "committed": true
  },
  "created_files": [
    "openspec/",
    "openspec/specs/",
    "openspec/changes/",
    "openspec/changes/archive/",
    "openspec/config.yaml",
    "openspec/specs/.gitkeep",
    "openspec/changes/archive/.gitkeep",
    ".openspec-store/store.yaml"
  ],
  "status": []
}
```

### openspec store register

регистрирует существующую папку хранилища, например хранилище товарища по команде, который вы клонировали.

```bash
openspec store register ~/stores/design-system
```

папка должна содержать исправный корень `openspec/`. При наличии `.openspec-store/store.yaml` регистр повторно использует записанный идентификатор. Без этого регистрация запрашивает перед созданием этих метаданных. За пределами интерактивного терминала вместо этого передайте `--yes`. Машина может зарегистрировать одну кассу для каждого идентификатора хранилища. Второй путь под тем же идентификатором или тот же путь под вторым идентификатором выходит из 1.

**Аргументы**

|Аргумент|Что это такое|
|---|---|
|`path`|папка хранилища для регистрации (`~` расширяется). Необходимый.|

**Параметры**

|Флаг|Эффект|
|---|---|
|`--id <id>`|Идентификатор хранилища. По умолчанию используются метаданные или имя папки.|
|`--yes`|подтвердите создание метаданных идентификации хранилища для работоспособного корня OpenSpec.|

**Вывод**

```
Store registered: design-system
Location: /Users/you/stores/design-system
OpenSpec root: ready
Registry: registered
```

`--json` печатает документ той же формы, что и `store setup --json`.

В этом случае ошибка будет `store_remove_contains_registered_store`: сначала запустите `openspec store unregister <nested-id>` или `openspec store unregister <id>`, чтобы забыть хранилище без удаления файлов.

**Параметры**

|Флаг|Эффект|
|---|---|
|`--yes`|подтвердите удаление папки локального хранилища.|

## openspec workset

создает, сохраняет и открывает личные рабочие представления. Рабочий набор — это сохраненный именованный список папок, с которыми вы работаете вместе.

```bash
openspec workset create checkout --member ~/projects/checkout-api --member web=~/projects/checkout-web
openspec workset list
openspec workset remove checkout --yes
```

|Подкоманда|Что он делает|
|---|---|
|`create [name]`|создайте и сохраните именованный рабочий вид выбранных вами папок.|
|`list`, `ls`|показывать сохраненные рабочие наборы вместе с их участниками.|
|`open <name>`|откройте сохраненный рабочий набор в своем инструменте (окно редактора или сеанс агента).|
|`remove <name>`|удалить сохраненный рабочий набор (папки участников не затрагиваются).|

Рабочий набор является чисто локальным:

- его состояние находится в одной папке: `~/.local/share/openspec/worksets/` (`$XDG_DATA_HOME/openspec/worksets/`, если установлено; `%LOCALAPPDATA%\openspec\worksets\` в Windows).
- Ничего не записывается в папки участников, ничего не фиксируется и не передается.
- Удаление этой папки удаляет все следы.

### openspec workset create

сохраняет именованный рабочий вид папок.

```bash
openspec workset create checkout \
  --member ~/projects/checkout-api \
  --member web=~/projects/checkout-web
```

В интерактивном терминале создайте подсказки для всего, что не указано в флагах: имя, папки по одной, инструмент, а затем предложение открыть рабочий набор сейчас. За пределами одного отсутствующее имя или член является ошибкой. Имя, которое уже сохранено, всегда является ошибкой. Сначала удалите его.

**Аргументы**

|Аргумент|Что это такое|
|---|---|
|`name`|имя рабочего набора. Кебаб-регистр: строчные буквы, цифры, одинарные дефисы. Требуется вне интерактивного терминала.|

**Параметры**

|Флаг|Эффект|
|---|---|
|`--member <member>`|папка участника как `<path>` или `<name>=<path>`, повторяемая. Первый является основным. Путь должен указывать на существующую папку, а метка по умолчанию должна соответствовать собственному имени папки.|
|`--tool <id>`|предпочтительный инструмент для открытия этого рабочего набора. Встроенные идентификаторы: `code` (VS Code), `cursor` (Cursor). `claude` и `codex` временно отключены.|
|`--json`|Распечатайте сохраненный рабочий набор как JSON.|

**Вывод**

```
Saved workset 'checkout' (2 members) to your machine.
Open it any time with: openspec workset open checkout
```

[Русское пояснение подписей и сообщений](../../EXAMPLE_NOTES.md#example-031).

### openspec workset open

открывает сохраненный рабочий набор в вашем инструменте. Инструменты редактора (`code`, `cursor`) получают сгенерированный файл `.code-workspace`. Откроется окно и команда вернется. Инструменты агента CLI (`claude`, `codex`) возьмут на себя управление этим терминалом со всеми подключенными участниками. Они временно отключены, пока этот процесс перерабатывается, поэтому рабочие наборы пока открываются в IDE.

```bash
openspec workset open checkout                # сохраненный инструмент или подсказка.
openspec workset open checkout --tool cursor  # этот инструмент только один раз
```

**Аргументы**

|Аргумент|Что это такое|
|---|---|
|`name`|рабочий набор, который нужно открыть.|

**Параметры**

|Флаг|Эффект|
|---|---|
|`--tool <id>`|Откройте с помощью этого инструмента только один раз.|

При отсутствии `--tool` и сохраненного инструмента при открытии предлагается выбрать установленный инструмент. За пределами интерактивного терминала вместо этого происходит выход 1.

- Папка участника, которая больше не существует, пропускается с предупреждением. Если основной член отсутствует, следующий выживший участник становится основным для этого открытия. Если папка-член не существует, открытие не удается.
- `--json` отклонен: поднесите терминал к инструменту и не имеет режима JSON.
- При сбое запуска ошибка заканчивается маршрутом вручную: путем к файлу рабочей области и списком участников.

**Коды выхода**

- Зеркально отражает инструмент: команда завершается с собственным кодом выхода инструмента, а сигнал становится `128+n` (`130` после Ctrl-C).
- `1`: неизвестный рабочий набор, нет доступной папки-участника или нет пригодного для использования инструмента.

### openspec workset remove

удаляет сохраненный рабочий набор и созданный им файл `.code-workspace`. Папки участников никогда не трогаются.

```bash
openspec workset remove checkout --yes
```

В интерактивном терминале команда «Удалить» отображает рабочий набор и запрашивает подтверждение. При использовании `--json` или вне терминала требуется `--yes` и выход 1 без него.

**Параметры**

|Флаг|Эффект|
|---|---|
|`--yes`|подтвердите удаление в неинтерактивном режиме.|
|`--json`|Распечатайте удаление как JSON.|

**Вывод**

```
Removed workset 'checkout'. Member folders were not touched.
```

## openspec version

сообщает о работающей версии OpenSpec и о том, как была установлена эта копия.

```bash
openspec version                 # локальная версия и подробности установки.
openspec version --json          # структурированный локальный отчет.
openspec version --check         # также проверьте реестр на наличие обновлений.
openspec version --check --json  # структурированный локальный отчет и отчет об обновлениях.
```

без `--check` эта команда является локальной и не обращается к реестру. Он работает вне проекта OpenSpec. Существующий флаг `openspec --version` остается самой короткой формой и печатает только номер версии.

**Параметры**

|Флаг|Эффект|
|---|---|
|`--json`|распечатайте один документ JSON с версией вместо текста.|
|`--check`|проверьте настроенный реестр на наличие более новой версии.|

**Вывод**

Для глобальной установки npm:

```text
OpenSpec 1.13.2 (npm, глобальный)
```

область установки — `global`, `project`, `temporary` для временного средства запуска, такого как npx, `source` для оформления заказа или `standalone` для [автономной установки](../start/installation.md#install). OpenSpec вместо того, чтобы гадать, опускает детали, которые не может идентифицировать.

`--json` сохраняет неизвестные детали в виде явных значений `null`:

```json
{
  "schemaVersion": 1,
  "version": "1.13.2",
  "install": {
    "location": "/opt/homebrew/lib/node_modules/@fission-ai/openspec",
    "packageManager": "npm",
    "scope": "global"
  }
}
```

Для `--check` доступное обновление добавляет последнюю версию и команду, когда OpenSpec может определить безопасную команду для этой установки:

```text
OpenSpec 1.13.2 (npm, глобальный)
Доступно обновление: 1.14.0.
  npm install -g @fission-ai/openspec@latest
```

```json
{
  "schemaVersion": 1,
  "version": "1.13.2",
  "install": {
    "location": "/opt/homebrew/lib/node_modules/@fission-ai/openspec",
    "packageManager": "npm",
    "scope": "global"
  },
  "update": {
    "status": "available",
    "latest": "1.14.0",
    "command": "npm install -g @fission-ai/openspec@latest",
    "canSelfUpgrade": true
  }
}
```

Значения состояния обновления:

|Состояние|Значение|
|---|---|
|`available`|Реестр вернул безопасную версию, более новую, чем работающая версия.|
|`current`|Проверка завершена, но более новой версии не обнаружено.|
|`disabled`|существующие настройки конфиденциальности или проверки обновлений блокировали доступ к реестру. `latest` — это `null`.|
|`offline`|Реестр был недоступен или вернул непригодный для использования ответ. `latest` — это `null`.|

для автономной установки команда обновления — `openspec install`.

`DO_NOT_TRACK`, отказ от телеметрии, `OPENSPEC_NO_UPDATE_CHECK`, обнаружение CI и отклоненные переопределения реестра, отличные от HTTPS, отключают проверку. Отключенные и автономные проверки по-прежнему завершаются 0, поскольку доступность обновлений носит рекомендательный характер. Эта команда никогда не обновляет OpenSpec; `canSelfUpgrade` сообщает только, может ли существующий путь `openspec update` безопасно обновить эту копию.

**Коды выхода**

- `0`: печатается локальный отчет, включая отключенные или автономные проверки обновлений.
- `1`: синтаксис команды неверен, например, неподдерживаемая опция `--upgrade`.

## openspec install

устанавливает автономный `openspec`, отдельный файл, который работает без Node.js. Запустите его из установки npm или Homebrew для переключения или из автономной установки, чтобы обновить ее на месте.

```bash
openspec install          # новейший выпуск
openspec install 1.15.0   # конкретный выпуск
```

он запускает [сценарий установки](../start/installation.md#install), который выбирает новейшую версию, все файлы которой прикреплены, и файл для вашего компьютера, и сравнивает ее с `SHA256SUMS` этой версии:

- **Из диспетчера пакетов**: устанавливается в `~/.local/bin` (Windows: `%LOCALAPPDATA%\Programs\openspec`) и печатается команда, удаляющая старую копию, например `npm uninstall -g @fission-ai/openspec`. Он никогда не удаляет эту копию сам.
- **При автономной установке**: заменяет работающий файл там, где он есть, под своим собственным именем.

После этого указывается, какая копия `openspec` сейчас запущена, поскольку копия менеджера пакетов, расположенная ранее в вашем PATH, продолжает работать, пока вы ее не удалите.

**Аргументы**

|Аргумент|Что это такое|
|---|---|
|`version`|выпуск для установки, как `1.15.0`. Необязательный; по умолчанию используется самая последняя.|

`OPENSPEC_INSTALL_DIR` и `OPENSPEC_INSTALL_NAME` выбирают другую папку или имя файла.

**Коды выхода**

- `0`: установлено.
- `1`: версия не является релизной, либо загрузка или установка не удалась. Ваша текущая копия остается такой, какой она была.

## openspec feedback

отправляет отзыв о OpenSpec.

```bash
openspec feedback "Validate output is hard to scan"
openspec feedback "Archive fails on Windows" --body "Steps: init, propose, archive. Error: EPERM."
```

CLI сохраняет ваше сообщение как проблему GitHub в репозитории `Fission-AI/OpenSpec` через ваш `gh` CLI. Название становится `Feedback: <message>`. В теле используются заголовки формы ошибки: ваше сообщение под `What happened`, текст `--body` под `Details` и раздел `Minimal steps to reproduce` с просьбой добавить шаги, поскольку CLI не может их заполнить. В нижнем колонтитуле добавляется версия CLI, платформа и временная метка. Выпуск получил маркировку `feedback`. Если репозиторий не определяет эту метку, CLI повторяет попытку без нее и сообщает об этом.

**Аргументы**

|Аргумент|Что это такое|
|---|---|
|`message`|Краткое описание в одну строку. Становится названием выпуска. Необходимый.|

**Параметры**

|Флаг|Эффект|
|---|---|
|`--body <text>`|в тело задачи добавлено более подробное описание.|

**Вывод**

В случае успеха:

```
✓ Feedback submitted successfully!
Issue URL: https://github.com/Fission-AI/OpenSpec/issues/1234
```

Без установленного `gh` или без входа в систему `gh` ничего не отправляется. CLI печатает ваш форматированный отзыв между маркерами `--- FORMATTED FEEDBACK ---`, а затем ссылку, которая открывает форму отчета об ошибке с заполненным заголовком, тем, что произошло (ваше сообщение и текст `--body`), версией CLI и средой (версией платформы и узла). Оставшуюся часть формы вы заполняете в браузере. Путь без входа в систему добавляет `To auto-submit in the future: gh auth login`.

**Коды выхода**

- `0`: возникла проблема или был выполнен резервный вариант ручной отправки (нет `gh` или `gh` не вошел в систему).
- `1`: сообщение не выдано.
- Собственный код `gh`: `gh` не удалось выполнить аутентификацию (сеть, ограничение скорости, проблемы отключены). CLI сначала перепечатывает ваш отзыв и URL-адрес для отправки вручную.

## openspec completion

устанавливает или генерирует дополнения оболочки.

```bash
openspec completion install        # определить вашу оболочку, установить, подключить конфигурацию
openspec completion generate zsh   # вывести скрипт на стандартный вывод.
```

Поддерживаемые оболочки: `zsh`, `bash`, `fish`, `powershell`. Каждая подкоманда принимает необязательный аргумент оболочки. Опустите его, и CLI обнаружит вашу оболочку из окружающей среды.

|Подкоманда|Что он делает|
|---|---|
|`generate [shell]`|Распечатайте сценарий завершения на стандартный вывод.|
|`install [shell]`|Напишите сценарий и настройте файл запуска оболочки.|
|`uninstall [shell]`|Удалите скрипт и блок конфигурации.|

Устанавливается вместе с Nix, доработки уже имеются: пакет flake поставляет сценарии Bash, Fish и Zsh в стандартные места, поэтому `install` не требуется ([Установка](../start/installation.md#nix)).

### openspec completion generate

печатает сценарий и ничего не пишет.

```
#compdef openspec

# сценарий завершения Zsh для OpenSpec CLI.
# генерируется автоматически, не редактируйте вручную.

_openspec() {
  local context state line
  typeset -A opt_args
...
```

### openspec completion install

записывает сценарий и редактирует конфигурацию оболочки. Редактирование конфигурации находится между маркерами `# OPENSPEC:START` и `# OPENSPEC:END`. Сначала создается резервная копия существующего сценария (копия `.backup-<timestamp>`).

|Оболочка|Расположение сценария.|Конфигурация изменена.|
|---|---|---|
|зш|`~/.zsh/completions/_openspec`|`~/.zshrc`|
|баш|`~/.local/share/bash-completion/completions/openspec`|`~/.bashrc`|
|рыба|`~/.config/fish/completions/openspec.fish`|Нет: рыба загружает его автоматически.|
|powershell|`OpenSpecCompletion.ps1` рядом с вашим профилем.|`$PROFILE`|

если установлен Oh My Zsh, сценарий вместо этого попадает в `$ZSH_CUSTOM/completions/_openspec` (по умолчанию `~/.oh-my-zsh/custom/completions/_openspec`).

**Параметры**

|Флаг|Эффект|
|---|---|
|`--verbose`|Также выведите путь установки, путь к резервной копии и файл конфигурации, который был отредактирован.|

**Вывод**

```
✓ Completion script installed and .zshrc configured successfully

Restart your shell or run: exec zsh
```

### openspec completion uninstall

удаляет сценарий и отмеченный блок конфигурации. Он спрашивает, прежде чем прикасаться к вашей конфигурации (по умолчанию: Нет).

**Параметры**

|Флаг|Эффект|
|---|---|
|`-y, --yes`|пропустить запросы на подтверждение.|

**Вывод**

```
✓ Completion script removed from /Users/you/.zsh/completions/_openspec. Removed OpenSpec configuration from ~/.zshrc
```

**Коды выхода**

- `0`: сценарий создан, установлен или удален. При отмене удаления также происходит выход из 0.
- `1`: оболочка не поддерживается или не обнаружена, либо произошел сбой на этапе установки или удаления.

## openspec change

устаревшая форма существительного `show`, `list` и `validate`. Каждый запуск предупреждает и указывает на команды, выполняемые сначала глаголом, а затем все равно запускается:

```
Warning: The "openspec change ..." commands are deprecated. Prefer verb-first commands (e.g., "openspec list", "openspec validate --changes").
Warning: "openspec change list" is deprecated. Use "openspec list".
add-rate-limit
```

[Русское пояснение подписей и сообщений](../../EXAMPLE_NOTES.md#example-033).


|Устарело.|использовать вместо этого|
|---|---|
|`openspec change show <name>`|`openspec show <name>`|
|`openspec change list`|`openspec list`|
|`openspec change validate <name>`|`openspec validate <name>` (все изменения: `openspec validate --changes`)|

В разделах «сначала глагола» описаны флаги.

## openspec spec

устаревшая форма существительного `show`, `list` и `validate`. Каждый запуск предупреждает и указывает на команды, выполняемые сначала глаголом, а затем все равно запускается:

```
Warning: The "openspec spec ..." commands are deprecated. Prefer verb-first commands (e.g., "openspec show", "openspec validate --specs").
api
```

|Устарело.|использовать вместо этого|
|---|---|
|`openspec spec show <id>`|`openspec show <id>`|
|`openspec spec list`|`openspec list --specs`|
|`openspec spec validate <id>`|`openspec validate <id>` (все спецификации: `openspec validate --specs`)|

В разделах «сначала глагола» описаны флаги.
