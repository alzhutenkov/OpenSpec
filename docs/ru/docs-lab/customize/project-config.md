<a id="project-configuration"></a>
# Конфигурация проекта

> внесите изменения в план рабочих процессов так, как вы хотите, с помощью нескольких строк в config.yaml.

`openspec/config.yaml` сообщает рабочим процессам, как вы хотите запланировать изменения.

Например, следующая конфигурация обновляет правила создания артефакта [tasks.md](../reference/schemas/spec-driven/index.md):

```yaml
rules:
  tasks:
    - завершать каждую задачу фиксацией.
```

Когда агент запускается, он использует эти правила и гарантирует, что каждая задача завершается шагом фиксации.

Правила должны быть краткими. Здесь все попадает в контекст агента, а подробные правила могут ухудшить результат.

<a id="how-it-works"></a>
## Как это работает

config.yaml содержит инструкции, которые агент получает при создании артефактов или работе в рабочем процессе.

Вот что происходит при каждом запуске:

1. вы запускаете рабочий процесс (например, `/openspec-propose`).
2. Агент вызывает команду [`openspec instructions`](../reference/cli.md).
3. команда считывает ваш контекст и правила из config.yaml.
4. встроенные инструкции OpenSpec и ваши настройки объединены в одно приглашение для агента.
5. Агент следует этому приглашению, чтобы записать артефакт.

Например, с помощью поля `context` и правила из верхней части этой страницы, вот что возвращает [`openspec instructions`](../reference/cli.md) для Tasks.md (обрезанный и аннотированный):

```xml
<artifact id="tasks" change="add-dark-mode" schema="spec-driven">

  <!-- From your config.yaml: context -->
  <project_context>
    Designs and tasks must cover Windows, macOS, and Linux
    Write all artifacts in Spanish
  </project_context>

  <!-- From your config.yaml: rules for tasks -->
  <rules>
    - End every task with a commit
  </rules>

  <!-- From OpenSpec: the built-in guidance -->
  <instruction>
    ...how to write a good tasks.md...
  </instruction>

  <template>
    ...the tasks.md structure to fill in...
  </template>

</artifact>
```

Сначала приходит ваша конфигурация, затем встроенные инструкции и шаблон OpenSpec. Правила добавляются к встроенным модулям и никогда не заменяют их. Изменения в config.yaml доходят до агента при следующем запуске.

<a id="the-fields"></a>
## Поля

три поля определяют то, что получает агент. Точный контракт каждого поля (типы, ограничения, проверка) находится в [Конфигурация проекта (config.yaml)](../reference/configuration/config-yaml.md).

|Поле|Что он делает|Введен в|
|---|---|---|
|`context`|инструкции, которые всегда получает агент.|Всё: каждый артефакт, `apply`, `archive`.|
|`rules`|Дополнительные инструкции для одного артефакта.|Только создание этого артефакта.|
|`operations`|Руководство по выполнению этапа рабочего процесса.|только `apply` и `archive`.|

другие поля config.yaml (`schema`, `store`, `references`) выбирают, какую схему и какой корень OpenSpec использует проект. Страница контракта охватывает их.

Последний столбец является точным, поэтому поле охватывает только перечисленные там шаги. В частности, `verify` никогда не получает `rules`. Он проверяет реализацию на соответствие написанным артефактам.

<a id="context"></a>
### контекст

`context` — это фон, который агент получает, когда создает артефакт, применяет задачи или архивирует изменения.

```yaml
context: |
  Мы поставляем кроссплатформенные продукты. Проекты и задачи должны охватывать Windows, macOS и Linux.
  писать все артефакты на испанском языке.
```

используйте `context` для фактов и ограничений, которые должны формировать выходные данные рабочего процесса. Храните долговременную проектную документацию в файлах документации проекта и оставляйте все, что агент может узнать, прочитав код.

**Другой язык**: поскольку контекст достигает каждого артефакта, вы можете добавить `Write all artifacts in Spanish.`, чтобы дать указание агенту писать артефакты предложений, спецификаций, дизайна и задач на испанском языке.

<a id="rules"></a>
### правила

`rules` прикрепляется к одному артефакту с ключом по идентификатору артефакта. Каждая строка добавляется во встроенное руководство этого артефакта:

```yaml
rules:
  proposal:
    - предложения должны содержать не более 500 слов.
  tasks:
    - каждая задача пользовательского интерфейса включает тест Playwright.
```

Предложения теперь остаются короткими, и Tasks.md всегда планирует тесты браузера. Все остальные артефакты нетронуты.

<a id="operations"></a>
### операции

`operations` указывает, как агент выполняет `apply` и `archive`, а не то, что говорят артефакты:

```yaml
operations:
  apply:
    guidance:
      - запускайте линтер перед пометкой задачи как выполненной.
  archive:
    guidance:
      - подведите итоги отправки перед архивированием.
```

во время применения агент проверяет выполнение задач. Во время архивирования оно закрывается сводкой.

<a id="when-configyaml-isnt-enough"></a>
## Когда config.yaml недостаточно

Config добавляет инструкции поверх стандартного рабочего процесса, но не может изменить существующие артефакты или их структуру. Если вам нужен такой уровень контроля или правила не регулируют поведение последовательно, [разветвите схему](schemas.md).
