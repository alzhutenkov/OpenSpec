<a id="schemas"></a>
# Схемы

> Измените то, что производит OpenSpec: артефакты, их порядок и их шаблоны.

Схема определяет, что производит предложение об изменении: какие артефакты, в каком порядке, на основе каких шаблонов. Например, [spec-driven](../reference/schemas/spec-driven/index.md), встроенная схема по умолчанию, создает эти четыре примерно в следующем порядке, каждая из которых основана на предыдущей:

```
proposal → specs → design → tasks
```

создайте форк схемы, если вы хотите, чтобы это были разные документы, независимо от того, означает ли это меньшее их количество, разные имена или другую структуру.

<a id="where-schemas-live"></a>
## Где живут схемы

OpenSpec ищет схему в трех местах по порядку и использует первую найденную:

1. **Ваш проект**: `openspec/schemas/`, зафиксированный в репозитории, чтобы его получила вся ваша команда.
2. **Ваша машина**: `~/.local/share/openspec/schemas` в macOS и Linux (или под `$XDG_DATA_HOME`, если вы его установили) или `%LOCALAPPDATA%\openspec\schemas` в Windows. Схемы здесь доступны в каждом проекте, над которым вы работаете.
3. **Пакет**: встроенные модули, такие как `spec-driven`, поставляются внутри самой openspec.

одно и то же имя может существовать более чем в одном месте, и побеждает более конкретное местоположение. `openspec schema which` показывает, какая копия используется:

```
$ openspec schema which spec-driven
Schema: spec-driven
Source: project
Path: /your-project/openspec/schemas/spec-driven

Shadows:
  package: .../openspec/schemas/spec-driven
```

<a id="whats-in-a-schema"></a>
## Что находится в схеме

Схема определяется папкой простых файлов: один файл schema.yaml, в котором объявляются артефакты, и шаблон для каждого из них. Вот встроенный `spec-driven`:

```
spec-driven/
├── schema.yaml
└── templates/
    ├── proposal.md
    ├── spec.md
    ├── design.md
    └── tasks.md
```

- **schema.yaml**: объявляет каждый артефакт, файл, который он генерирует, шаблон, с которого он начинается, что ему требуется в первую очередь, а также инструкции, которые агент получает при его создании. Контракт каждого поля находится в [schema.yaml](../reference/schemas/schema-yaml.md).
- **templates/**: один скелет Markdown для каждого артефакта, который заполняет агент.

Вот обрезанная запись артефакта задач в файле schema.yaml:

```yaml
artifacts:
  - id: tasks
    generates: tasks.md
    description: Контрольный список внедрения с отслеживаемыми задачами.
    template: tasks.md
    instruction: |
      ...what the agent is told when creating tasks.md...
    requires:
      - specs
      - design
```

встроенные схемы поставляются внутри пакета openspec, поэтому вы никогда не редактируете их на месте. Вы получаете свою собственную копию путем форка.

<a id="creating-your-own-custom-schema"></a>
## Создание собственной схемы.

Получить собственную схему можно двумя способами:

1. **Разветвите существующую схему** и отредактируйте свою копию. Начните здесь, когда существующая схема близка к тому, что вы хотите, потому что все в ней уже работает.
2. **Начать с нуля**, когда ни один из них не подходит, создавая пустую схему с помощью `openspec schema init`.

<a id="fork-an-existing-schema"></a>
### Форк существующей схемы.

1. создайте форк схемы, с которой вы хотите начать, работая из корня вашего проекта:

   ```console
   $ openspec schema fork spec-driven

   Note: Schema commands are experimental and may change.
   ✔ Forked 'spec-driven' to 'spec-driven-custom'

   Source: .../openspec/schemas/spec-driven (package)
   Destination: /your-project/openspec/schemas/spec-driven-custom
   ```

[Русское пояснение подписей и сообщений](../../EXAMPLE_NOTES.md#example-003).


   передайте второй аргумент, чтобы выбрать имя (`openspec schema fork spec-driven team-flow`). Имена шашлычные.

2. отредактируйте копию: schema.yaml и шаблоны. [Редактирование вашей форка](#editing-your-fork) описывает, что нужно изменить.

3. Подтвердите это:

   ```bash
   openspec schema validate spec-driven-custom
   ```

   Это единственная команда, которая обнаруживает неработающую схему (отсутствующие шаблоны, плохой YAML, циклы зависимостей) до того, как вы приступите к изменению.

4. укажите это в своем проекте в openspec/config.yaml. Этот шаг ваш, потому что fork оставляет config.yaml нетронутым:

   ```yaml
   schema: spec-driven-custom
   ```

5. Новые предложения по изменениям теперь соответствуют вашей схеме. Изменения, созданные ранее, сохраняют исходную схему.

Чтобы заменить значение по умолчанию везде, не трогая config.yaml, создайте форк с тем же именем: `openspec schema fork spec-driven spec-driven`. Копия вашего проекта затем затеняет встроенную, как объясняет [Где живут схемы](#where-schemas-live).

<a id="start-from-scratch"></a>
### Начать с нуля.

`openspec schema init` создает новую схему вместо копирования:

```console
$ openspec schema init lite --description "Lite flow" --artifacts proposal,tasks

✔ Created schema 'lite'
Schema created at: /your-project/openspec/schemas/lite
Artifacts: proposal, tasks
```

Леса пусты. Артефакты поступают только из четырех встроенных идентификаторов, а сгенерированные шаблоны не содержат инструкций, поэтому агент получает меньше указаний, пока вы не напишете свои собственные. После этого шаги форка применяются без изменений: проверьте его, затем укажите на него config.yaml.

<a id="editing-your-fork"></a>
## Редактирование вашей форка

В форке есть два типа файлов для редактирования:

- **шаблоны/** изменяют скелет каждого документа. Добавьте раздел в шаблон задач и каждый новый tasks.md будет начинаться с него. Сохраняйте заголовок `#` в первой строке: артефакт наследует его, поэтому каждый созданный файл открывается как документ с названием.
- **schema.yaml** меняет сам рабочий процесс: какие артефакты существуют, что каждый из них требует в первую очередь, а также инструкции, которые агент получает при его создании.

Например, чтобы удалить проектный документ для более компактного потока:

1. удалите запись `design` из файла schema.yaml.
2. Удалить `design` из списка `requires` `tasks`.
3. Подтвердите:

   ```console
   $ openspec schema validate spec-driven-custom

   ✓ Schema 'spec-driven-custom' is valid
   ```

пропустите шаг 2 и проверьте его:

```console
✗ Schema 'spec-driven-custom' has errors:
  error: Invalid dependency reference in artifact 'tasks': 'design' does not exist
```

Проверяйте после каждого редактирования вручную. В противном случае нарушенная схема проявляется в середине изменения, когда рабочий процесс запрашивает несуществующий файл. Как и в случае с config.yaml, изменения схемы достигают агента при следующем запуске.

<a id="a-fork-is-a-snapshot"></a>
## Форк — это снимок

`openspec update` обновляет установленные навыки и команды и никогда не затрагивает `openspec/schemas/`. Ваш форк продолжает работать точно так же, как вы его оставили, что также означает, что он перестает получать улучшения по мере развития встроенной схемы. Чтобы использовать их позже, снова разветвите встроенный модуль под новым именем и перенесите различия.

<a id="sharing-schemas"></a>
## Совместное использование схем

Публикация схемы означает копирование ее папки.

- **С вашей командой**: зафиксируйте `openspec/schemas/`, и все в репозитории будут его использовать.
- **В ваших проектах**: поместите папку в каталог пользовательского уровня из [Где находятся схемы](#where-schemas-live).
- **От сообщества**: в [каталоге сообщества](../../docs/customization.md#community-schemas) перечислены общие схемы. Скопируйте его в `openspec/schemas/<name>`, и он будет работать как ваш собственный.

Мы работаем над реестром схем, общедоступным и частным, поэтому схемы можно устанавливать по имени, а не копировать вручную.

<a id="use-openspec-with-superpowers"></a>
### Используйте OpenSpec со сверхспособностями

Поддерживаемая сообществом схема [`superpowers-bridge`](https://github.com/JiangWay/openspec-schemas/tree/main/superpowers-bridge) соединяет артефакты OpenSpec с навыками выполнения [Суперсил (английский)](https://github.com/obra/superpowers). Следуйте примечаниям по установке и совместимости моста, прежде чем копировать его в свой проект.

мост выпущен за пределами OpenSpec. OpenSpec не тестирует и не проверяет версию интеграции Superpowers.
