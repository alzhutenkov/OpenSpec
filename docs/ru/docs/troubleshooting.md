# Устранение неполадок

Конкретные исправления конкретных проблем. В каждой записи указывается симптом, в предложении объясняется вероятная причина и предлагается решение. Если вы не видите здесь свою проблему, вам может помочь [FAQ](faq.md), а [Discord (английский)](https://discord.gg/YctCnvvshC) определенно поможет.

<a id="installation-and-setup"></a>
## Установка и настройка

### `openspec: command not found`

CLI не установлен или ваша оболочка не может его найти. Установите его глобально и проверьте:

```bash
npm install -g @fission-ai/openspec@latest
openspec --version
```

Если он установлен, но все еще не найден, возможно, вашего глобального каталога npm bin нет на вашем `PATH`. Запустите `npm prefix -g`, чтобы увидеть, где находятся глобальные пакеты: в macOS и Linux двоичные файлы находятся в `bin/` этого каталога, а в Windows они находятся непосредственно в нем. Убедитесь, что этот путь находится на вашем `PATH`. (`npm bin -g` был удален в npm 9.)

Если вы использовали [установку с помощью AI](installation.md#install-with-your-ai-assistant), это ожидаемая точка передачи: это приглашение говорит вашему помощнику показать вам изменение `PATH`, а не редактировать файлы запуска оболочки самостоятельно.

<a id="requires-nodejs-20190-or-higher"></a>
### «Требуется Node.js 20.19.0 или выше»

OpenSpec работает на узле 20.19.0+. Проверьте свою версию и при необходимости обновите ее:

```bash
node --version
```

Если вы используете Bun для установки OpenSpec, обратите внимание, что OpenSpec все еще *работает* на Node, поэтому вам в любом случае понадобится Node 20.19.0+, доступный на вашем `PATH`. См. [Установка](installation.md).

<a id="openspec-init-didnt-configure-my-ai-tool"></a>
### `openspec init` не настроил мой инструмент искусственного интеллекта.

Init спрашивает, какие инструменты настроить. Если вы пропустили свой инструмент или хотите добавить другой, просто запустите его еще раз или воспользуйтесь неинтерактивной формой:

```bash
openspec init --tools claude,cursor
```

Полный список идентификаторов инструментов находится в разделе [Поддерживаемые инструменты](supported-tools.md). Используйте `--tools all` для всего и `--tools none`, чтобы пропустить настройку инструмента.

<a id="commands-dont-show-up"></a>
## команды не отображаются.

Если `/opsx:propose` (или эквивалент вашего инструмента) не появляется или ничего не делает, прочитайте этот список. Им приказано первыми провериться.

1. **Возможно, вы находитесь не в том месте.** Слэш-команды отправляются в чат вашего ИИ-помощника, а не в ваш терминал. Если вы ввели `/opsx:propose` в свою оболочку, вот в чем проблема. См. [Как работают команды](how-commands-work.md).

2. **Перегенерируйте файлы.** Из корня проекта:

   ```bash
   openspec update
   ```

   перезаписывает файлы навыков и команд для каждого настроенного вами инструмента.

   Файлы инструкций берутся из *установленного* CLI, поэтому устаревший CLI сообщает обо всем актуальном, даже не записывая новые рабочие процессы. `openspec update` теперь проверяет это и предлагает обновиться — воспользуйтесь предложением, если увидите его.

3. **Перезапустите помощника.** Большинство инструментов сканируют навыки и команды при запуске. Свежее окно часто делает это.

4. **Подтвердите существование файлов.** Для Claude Code убедитесь, что `.claude/skills/` содержит папки `openspec-*`. Другие инструменты используют свои собственные каталоги, все они перечислены в разделе [Поддерживаемые инструменты](supported-tools.md).

5. **Убедитесь, что вы инициализировали этот проект.** Навыки записываются для каждого проекта. Если вы клонировали репозиторий или переключили папки, запустите там `openspec init` (или `openspec update`).

6. **Подтвердите, что ваш инструмент поддерживает командные файлы.** Codex, CodeArts, ForgeCode, Hermes, Kimi Code, Mistral Vibe, Zed Agent и общая цель `.agents` не получают сгенерированные командные файлы `opsx-*`; вместо этого они используют вызовы на основе навыков, поэтому `/opsx` никогда не будет выполнять для них автозаполнение. Введите `$openspec-propose` в Codex, `/skill:openspec-propose` в Kimi Code и `/openspec-propose` в остальных. Общая цель `.agents` не зависит от поставщика, поэтому `/openspec-propose` является распространенной формой, а не гарантированной — если ваш помощник не отвечает на нее, проверьте его собственную документацию, чтобы узнать, как она вызывает навык. Amazon Q получает командные файлы, но загружает их в свою библиотеку подсказок, а не в косую черту — введите там `@opsx-propose`, а не `/opsx`. Форма каждого инструмента указана в [Как вызвать](supported-tools.md#how-to-invoke).

<a id="working-with-changes"></a>
## Работа с изменениями

<a id="change-not-found"></a>
### «Изменение не найдено»

Команда не смогла определить, какое изменение вы имели в виду. Назовите его явно или проверьте то, что существует:

```bash
openspec list                    # посмотреть активные изменения
/opsx:apply add-dark-mode        # назовите изменение в чате
```

Также убедитесь, что вы находитесь в правильном каталоге проекта.

<a id="no-artifacts-ready"></a>
### «Артефакты не готовы»

каждый артефакт либо уже создан, либо заблокирован в ожидании зависимости. Посмотрите, что блокирует:

```bash
openspec status --change <name>
```

Затем сначала создайте недостающую зависимость. Помните о порядке: предложение включает спецификации и дизайн; Технические спецификации и дизайн вместе позволяют решать поставленные задачи.

<a id="openspec-validate-reports-warnings-or-errors"></a>
### `openspec validate` сообщает о предупреждениях или ошибках.

Валидация проверяет ваши спецификации и изменения на наличие структурных проблем. Прочтите сообщение: в нем указаны файл и проблема.

```bash
openspec validate <name>           # проверить один элемент
openspec validate --all            # проверить все
openspec validate --all --strict   # более строгие проверки, подходят для CI.
openspec validate --archived       # ошибка, если в архивных изменениях есть непроверенные задачи.
```

Распространенными причинами являются отсутствие обязательного раздела (например, в спецификации без сценариев) или неправильный дельта-заголовок. Исправьте файл и запустите заново. [Справочник CLI](cli.md#openspec-validate) документирует формат вывода.

Одно сообщение заслуживает отдельного внимания:

```text
MODIFIED "<requirement>" опускает сценарии, которые все еще есть в текущей спецификации: "<scenario>"
```

Требование `MODIFIED` заменяет весь блок требований, поэтому оно должно содержать все сценарии, пережившие изменение, а не только те, которые вы редактировали. Скопируйте названные сценарии из `openspec/specs/<capability-path>/spec.md` обратно в дельту, сохранив все каталоги домена на пути. Это часто появляется в более старых изменениях после того, как чье-то другое изменение добавило сценарий к тому же требованию — архив в любом случае отклоняет это изменение, и проверка теперь говорит об этом, прежде чем вы его реализуете.

<a id="the-ai-created-incomplete-or-wrong-artifacts"></a>
### ИИ создал неполные или неправильные артефакты.

У ИИ не было достаточного контекста. Несколько рычагов помогут:

- добавьте контекст проекта в `openspec/config.yaml`, чтобы ваш стек и соглашения внедрялись в каждый запрос. См. [Настройка](customization.md#project-configuration).
- добавьте `rules:` для каждого артефакта, чтобы получить рекомендации, применимые, скажем, только к спецификациям.
- При предложении дайте более подробное описание.
- используйте расширенный `/opsx:continue` для создания одного артефакта за раз и просмотра каждого, вместо того, чтобы `/opsx:ff` делал их все сразу.

<a id="archive-wont-finish-or-warns-about-incomplete-tasks"></a>
### Архивирование не завершается или предупреждает о незавершенных задачах.

Архив не *блокируется* при незавершенных задачах, но предупреждает вас, поскольку архивирование обычно означает, что работа завершена. Если задачи остаются намеренно (вы вносите частичное изменение), продолжайте. В противном случае сначала завершите задания. Архив также предложит синхронизировать ваши дельта-спецификации с основными, если вы еще этого не сделали; скажите «да», если у вас нет причин не делать этого.

<a id="user-force-closed-the-prompt-with-0-null"></a>
### «Пользователь принудительно закрыл приглашение с нулевым значением 0»

Что-то запустило `openspec archive`, где ничто не может ответить на вопрос — агент ИИ, вызывающий его из инструмента, задания CI или любой оболочки с закрытым стандартным вводом. Архив запрашивает до трех подтверждений, и одно из них, на которое невозможно ответить, давало сбой с этим необработанным сообщением.

Передайте `--yes`, чтобы ответить им заранее:

```bash
openspec archive <change-name> --yes
```

Сохраните все флаги, которые вы уже передавали: `--skip-specs` и `--no-validate` меняют действие архива, поэтому простой повторный запуск `--yes` — это не одна и та же команда. Текущие версии задают имя флага и печатают строку `Fix:`, которую вы можете вставить. Если вы хотели выбрать из списка, передайте имя изменения явно: сборщику тоже нужен ответ.

Если вместо этого вы запустили архив с его выводом, перенаправленным в файл или захваченным инструментом, и *сделали* ответ по конвейеру (`printf 'y\n' | openspec archive …`), более старые версии записывали escape-коды терминала в этот захват при рисовании приглашения — в некоторых средах этого достаточно, чтобы сильно раздуть файл. Текущие версии считывают запросы подтверждения как обычный текст, если стандартный вывод не является терминалом, а `openspec archive` без аргументов (который в противном случае рисовал бы интерактивный инструмент выбора изменений) просит вас заранее передать имя изменения вместо отображения меню в захвате. В любом случае, перенаправление и запуск агента остаются чистыми; передача `--yes` (с измененным именем) полностью пропускает подсказки.

<a id="configuration"></a>
## Конфигурация

<a id="my-configyaml-isnt-being-applied"></a>
### Мой `config.yaml` не применяется.

Трое обычных подозреваемых:

1. **Неверное имя файла.** Это должен быть `openspec/config.yaml`, а не `.yml`.
2. **Неверный YAML.** Запустите его через любой валидатор YAML; CLI также сообщает о синтаксических ошибках с номерами строк.
3. **Вы ожидали перезагрузки.** Она вам не нужна. Изменения конфигурации вступают в силу немедленно.

<a id="unknown-artifact-id-in-rules-x"></a>
### «Неизвестный идентификатор артефакта в правилах: X»

ключ в `rules:` не соответствует ни одному артефакту в вашей схеме. Для схемы `spec-driven` по умолчанию действительными идентификаторами являются `proposal`, `specs`, `design`, `tasks`. Чтобы просмотреть идентификаторы для любой схемы:

```bash
openspec schemas --json
```

<a id="context-too-large"></a>
### «Слишком большой контекст»

Поле `context:` намеренно ограничено размером 50 КБ, поскольку оно вводится в каждый запрос. Подведите итог или дайте ссылку на более длинные документы, а не вставляйте их. Контекст бережливости также дает лучшие и быстрые результаты.

<a id="schema-not-found"></a>
### «Схема не найдена»

Имя схемы, на которую вы ссылаетесь, не существует. Перечислите то, что доступно, и проверьте правописание:

```bash
openspec schemas                    # список доступных схем.
openspec schema which <name>        # посмотрите, откуда разрешается схема.
openspec schema init <name>         # создать собственный
```

см. [Кастомизация](customization.md#custom-schemas).

<a id="migration-from-the-legacy-workflow"></a>
## переход с устаревшего рабочего процесса

<a id="legacy-files-detected-in-non-interactive-mode"></a>
### «Устаревшие файлы обнаружены в неинтерактивном режиме»

Вы находитесь в CI или неинтерактивной оболочке, и OpenSpec нашел старые файлы, которые нужно очистить, но не может вам подсказать. Одобрить автоматически:

```bash
openspec init --force
```

Для Codex OpenSpec может обнаруживать старые управляемые файлы подсказок в `$CODEX_HOME/prompts` или `~/.codex/prompts`. Эта очистка ограничивается устаревшими именами файлов подсказок Codex, включенными в разрешенный список OpenSpec, а неинтерактивный `openspec init` удаляет только те файлы, для которых существуют навыки замены `.agents/skills/openspec-*`. Неинтерактивный `openspec update` оставляет все устаревшие очистки нетронутыми, если вы не передадите `--force`.

<a id="commands-didnt-appear-after-migrating"></a>
### команды не появлялись после миграции

Перезапустите интегрированную среду разработки. Навыки обнаруживаются при запуске. Если они по-прежнему не появляются, запустите `openspec update` и проверьте расположение файлов в [Поддерживаемые инструменты](supported-tools.md).

<a id="my-old-projectmd-wasnt-migrated"></a>
### Мой старый `project.md` не был перенесен.

Это намеренно. OpenSpec никогда не удаляет `project.md` автоматически, поскольку он может содержать написанный вами контекст. Переместите полезные части в раздел `context:` `config.yaml`, а затем удалите их самостоятельно. В [Руководстве по миграции](migration-guide.md#migrating-projectmd-to-configyaml) все это описано, включая подсказку, которую вы можете передать своему ИИ для выполнения дистилляции.
