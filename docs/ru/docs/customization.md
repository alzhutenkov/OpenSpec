<a id="customization"></a>
# Настройка

OpenSpec предоставляет три уровня настройки:

|Уровень|Что он делает|Лучше всего подходит для|
|-------|--------------|----------|
|**Конфигурация проекта**|установить значения по умолчанию, внедрить контекст/правила.|Большинство команд|
|**Пользовательские схемы**|определение собственных артефактов рабочего процесса.|Команды с уникальными процессами|
|**Глобальные переопределения**|совместное использование схем во всех проектах.|Опытные пользователи|

---

<a id="project-configuration"></a>
## Конфигурация проекта

Файл `openspec/config.yaml` — это самый простой способ настроить OpenSpec для вашей команды. Это позволяет вам:

- **Установить схему по умолчанию** — пропустить `--schema` в каждой команде.
- **Внедрение контекста проекта** – ИИ видит ваш технологический стек, соглашения и т. д.
- **Добавлять правила для каждого артефакта** – пользовательские правила для конкретных артефактов.
- **Добавить руководство для каждой операции** — консультативные настройки для применения и архивирования.
- **Запомните варианты интеграции** – например. подписка на [агент облачного кодирования GitHub Copilot](supported-tools.md#github-copilot-cloud-coding-agent)

<a id="quick-setup"></a>
### Быстрая настройка

```bash
openspec init
```

Это поможет вам создать конфигурацию в интерактивном режиме. Или создайте его вручную:

```yaml
# openspec/config.yaml
schema: spec-driven

context: |
  Tech stack: TypeScript, React, Node.js, PostgreSQL
  API style: RESTful, documented in docs/api.md
  Testing: Jest + React Testing Library
  Мы ценим обратную совместимость для всех общедоступных API.

rules:
  proposal:
    - включить план отката.
    - Определите затронутые команды.
  specs:
    - использовать формат «Дано/Когда/Тогда».
    - Ссылайтесь на существующие шаблоны, прежде чем изобретать новые.

operations:
  apply:
    guidance:
      - запускайте целевые тесты перед полным пакетом.
  archive:
    guidance:
      - краткий обзор завершения

# устанавливается `openspec init`, когда вы выбираете (или отклоняете) GitHub Copilot.
# агент облачного кодирования; контролирует, будут ли `init`/`update` создавать свои файлы.
githubCopilot:
  cloudAgent: false
```

<a id="how-it-works"></a>
### Как это работает

**Схема по умолчанию:**

```bash
# Без конфигурации
openspec new change my-feature --schema spec-driven

# С конфигом — схема автоматическая
openspec new change my-feature
```

**Внедрение контекста и правил:**

При создании любого артефакта ваш контекст и правила вводятся в подсказку ИИ:

```xml
<context>
Tech stack: TypeScript, React, Node.js, PostgreSQL
...
</context>

<rules>
- Include rollback plan
- Identify affected teams
</rules>

<template>
[Schema's built-in template]
</template>
```

- **Контекст** отображается во ВСЕХ артефактах.
- **Правила** отображаются ТОЛЬКО для соответствующего артефакта.

**Руководство по эксплуатации:**

`operations.apply.guidance` и `operations.archive.guidance` — это дополнительные массивы рекомендательных инструкций
о том, как агент должен выполнять эти операции. Они отличаются
от `rules` : руководство по эксплуатации не ограничивает содержимое артефакта,
а правила артефактов никогда не переименовываются как руководство по эксплуатации.

Примените и заархивируйте эти входные данные во время выполнения:

```bash
openspec instructions apply --change my-feature --json
openspec instructions archive --change my-feature --json
```

обе поверхности возвращают текущий проект `context` и соответствующий `operationGuidance` в виде
отдельных необязательных полей. Каждый вызов считывает новый снимок из выбранного корня.
Если выбран `--store <id>` , изменения, контекст и рекомендации поступают из этого
хранилища, а не из текущего репозитория. Команда инструкции архивирования доступна только
для чтения: она не проверяет и не объединяет дельта-спецификации, не записывает
основные спецификации, не перемещает изменения и не запускает рабочий процесс статического архивирования.

Контекст проекта является обязательным вводом на уровне подсказки. Сгенерированные рабочие процессы
читают его и применяют соответствующие факты, соглашения и ограничения проекта. Руководство
по эксплуатации является дополнительным дополнительным советом: рабочие процессы учитывают каждую запись
и следуют за записями, которые применимы и совместимы со встроенным рабочим процессом.

оба поля остаются отдельными от состояния, контролируемого CLI, разрешенных путей, встроенных
шагов, явного выбора пользователя и правил артефактов. Рабочий процесс сообщает о конфликтах
контекста, сохраняя при этом управляющее значение. Он не следует неприменимым или противоречивым
рекомендациям и объясняет, почему. Ни одно из полей не является обязательной
проверкой, и рабочие процессы не копируют свой текст в файлы реализации, спецификации,
артефакты изменений или сводки, если только пользователь отдельно не запрашивает это содержимое.

**Безопасность ввода при архивировании и синхронизации спецификаций:**

Архивирование, массовое архивирование и автономная синхронизация используют
`artifactPaths.specs.existingOutputPaths` из `openspec status --json` в качестве единственного источника
дельта-спецификаций. Схема без артефакта `specs` или изменение,
конкретный список вывода которого пуст, нечего синхронизировать;
другие артефакты не используются для определения дельта-спецификаций.

Прежде чем семантическое слияние запишет основную спецификацию, рабочий процесс использует
текущие выходные данные `openspec instructions specs --change <name> --json` . Возвращенные правила `specs` ограничивают только основные
спецификации, полученные в результате этого слияния. Одиночный архив передает этот снимок
во встроенную синхронизацию, автономная синхронизация извлекает его напрямую, а массовый архив
получает каждый необходимый снимок перед его первой записью спецификации. Ненулевой или
недопустимый ответ на инструкцию архива/спецификаций JSON — это ошибка поиска, а
не пустой ввод: рабочий процесс останавливается перед записью или изменением затронутой
спецификации (для массового архивирования — перед любой пакетной записью или перемещением).

эта конфигурация не меняет фазы выполнения архива, пользовательские запросы,
операции с файловой системой, владение семантическим слиянием, прямую команду `openspec archive`
, а также структуру и выходные данные артефакта `rules` .

<a id="schema-resolution-order"></a>
### Порядок разрешения схемы

Когда OpenSpec нужна схема, он проверяет в следующем порядке:

1. Флаг CLI: `--schema <name>`
2. Изменить метаданные (`.openspec.yaml` в папке изменений)
3. Конфигурация проекта (`openspec/config.yaml`)
4. по умолчанию (`spec-driven`)

<a id="custom-schemas"></a>
## Пользовательские схемы

Если конфигурации проекта недостаточно, создайте собственную схему с полностью настраиваемым рабочим процессом. Пользовательские схемы находятся в каталоге `openspec/schemas/` вашего проекта и контролируются вашим кодом.

```text
ваш-проект/
├── openspec/
│   ├── config.yaml        # Конфигурация проекта
│   ├── schemas/           # Здесь находятся пользовательские схемы
│   │   └── my-workflow/
│   │       ├── schema.yaml
│   │       └── templates/
│   └── changes/           # Ваши изменения
└── src/
```

<a id="fork-an-existing-schema"></a>
### Форк существующей схемы

Самый быстрый способ настройки — это создать форк встроенной схемы:

```bash
openspec schema fork spec-driven my-workflow
```

копирует всю схему `spec-driven` в `openspec/schemas/my-workflow/`, где вы можете ее свободно редактировать.

**Что вы получаете:**

```text
openspec/schemas/my-workflow/
├── schema.yaml           # Определение рабочего процесса
└── templates/
    ├── proposal.md       # Шаблон для артефакта предложения
    ├── spec.md           # Шаблон для спецификаций
    ├── design.md         #Шаблон для дизайна
    └── tasks.md          #Шаблон для задач
```

Теперь отредактируйте `schema.yaml`, чтобы изменить рабочий процесс, или отредактируйте шаблоны, чтобы изменить то, что генерирует ИИ.

<a id="create-a-schema-from-scratch"></a>
### Создание схемы с нуля

Для совершенно нового рабочего процесса:

```bash
# Интерактивный
openspec schema init research-first

# Неинтерактивный
openspec schema init rapid \
  --description "Rapid iteration workflow" \
  --artifacts "proposal,tasks" \
  --default
```

<a id="schema-structure"></a>
### Структура схемы

Схема определяет артефакты в вашем рабочем процессе и то, как они зависят друг от друга:

```yaml
# openspec/schemas/my-workflow/schema.yaml
name: my-workflow
version: 1
description: индивидуальный рабочий процесс моей команды.

artifacts:
  - id: proposal
    generates: proposal.md
    description: Документ с первоначальным предложением.
    template: proposal.md
    instruction: |
      Создайте предложение, объясняющее, ПОЧЕМУ необходимо это изменение.
      Сосредоточьтесь на проблеме, а не на решении.
    requires: []

  - id: design
    generates: design.md
    description: Технический проект
    template: design.md
    instruction: |
      Создайте проектный документ, объясняющий КАК реализовать.
    requires:
      - proposal    # Can't create design until proposal exists

  - id: tasks
    generates: tasks.md
    description: Контрольный список реализации
    template: tasks.md
    requires:
      - design

apply:
  requires: [tasks]
  tracks: tasks.md
```

**Ключевые поля:**

|Поле|Назначение|
|-------|---------|
|`id`|уникальный идентификатор, используемый в командах и правилах.|
|`generates`|имя выходного файла (поддерживает такие шаблоны, как `specs/**/*.md`)|
|`template`|файл шаблона в каталоге `templates/`.|
|`instruction`|инструкции ИИ по созданию этого артефакта.|
|`requires`|Зависимости — какие артефакты должны существовать в первую очередь.|

перечислите артефакты в том порядке, в котором вы хотите
их записать. `requires` решает, что возможно; порядок списка `artifacts:`
определяет, что будет первым, когда несколько артефактов будут готовы одновременно.

<a id="templates"></a>
### Шаблоны

Шаблоны — это файлы Markdown, которыми руководствуется ИИ. Они вводятся в командную строку при создании этого артефакта.

```markdown
<!-- templates/proposal.md -->
## Why

<!-- Объясните причину этого изменения. Какую проблему это решает? -->

## What Changes

<!-- Опишите, что изменится. Будьте конкретны в отношении новых возможностей или модификаций. -->

## Impact

<!-- Затронутый код, API, зависимости, системы. -->
```

Шаблоны могут включать в себя:
- заголовки разделов, которые должен заполнить ИИ.
- HTML-комментарии с указаниями для ИИ.
- примеры форматов, показывающие ожидаемую структуру.

<a id="validate-your-schema"></a>
### Проверьте свою схему

Прежде чем использовать пользовательскую схему, проверьте ее:

```bash
openspec schema validate my-workflow
```

проверяется:
- синтаксис `schema.yaml` правильный.
- существуют все указанные шаблоны.
- нет циклических зависимостей.
- идентификаторы артефактов действительны.

<a id="use-your-custom-schema"></a>
### Используйте свою собственную схему

После создания используйте свою схему с:

```bash
# Указать по команде
openspec new change feature --schema my-workflow

# Или установить по умолчанию в config.yaml.
schema: my-workflow
```

<a id="debug-schema-resolution"></a>
### Разрешение схемы отладки

Не знаете, какая схема используется? Проверьте с:

```bash
# посмотрите, откуда разрешается конкретная схема.
openspec schema which my-workflow

# список всех доступных схем.
openspec schema which --all
```

выходные данные показывают, откуда они: ваш проект, каталог пользователя или пакет:

```text
Схема: мой рабочий процесс
Источник: проект
Путь: /path/to/project/openspec/schemas/my-workflow
```

---

> **Примечание:** OpenSpec также поддерживает схемы уровня пользователя в `~/.local/share/openspec/schemas/` для совместного использования в проектах, но схемы уровня проекта в `openspec/schemas/` рекомендуются, поскольку они контролируются вашим кодом.

<a id="examples"></a>
## Примеры

<a id="rapid-iteration-workflow"></a>
### Рабочий процесс быстрой итерации

Минимальный рабочий процесс для быстрых итераций:

```yaml
# openspec/schemas/rapid/schema.yaml
name: rapid
version: 1
description: быстрая итерация с минимальными накладными расходами.

artifacts:
  - id: proposal
    generates: proposal.md
    description: Быстрое предложение
    template: proposal.md
    instruction: |
      Создайте краткое предложение по этому изменению.
      Сосредоточьтесь на том, что и почему, пропуская подробные характеристики.
    requires: []

  - id: tasks
    generates: tasks.md
    description: Контрольный список реализации
    template: tasks.md
    requires: [proposal]

apply:
  requires: [tasks]
  tracks: tasks.md
```

<a id="adding-a-review-artifact"></a>
### Добавление артефакта обзора

Создайте форк по умолчанию и добавьте этап проверки:

```bash
openspec schema fork spec-driven with-review
```

Затем отредактируйте `schema.yaml`, добавив:

```yaml
  - id: review
    generates: review.md
    description: Контрольный список проверки перед внедрением
    template: review.md
    instruction: |
      Создайте контрольный список проверки на основе дизайна.
      включите соображения безопасности, производительности и тестирования.
    requires:
      - design

  - id: tasks
    # ... existing tasks config ...
    requires:
      - specs
      - design
      - review    # Now tasks require review too
```

<a id="community-schemas"></a>
## Схемы сообщества

OpenSpec также поддерживает схемы, поддерживаемые сообществом, распространяемые через автономные репозитории. Они обеспечивают продуманные рабочие процессы, которые интегрируют OpenSpec с другими инструментами или системами, аналогично тому, как [каталог расширений сообщества github/spec-kit](https://github.com/github/spec-kit/tree/main/extensions) работает для spec-kit.

Схемы сообщества не включены в ядро ​​OpenSpec — они находятся в собственных репозиториях с собственной периодичностью выпуска. Чтобы использовать его, скопируйте пакет схемы в каталог `openspec/schemas/<schema-name>/` вашего проекта (в README каждого репозитория есть инструкции по установке).

|--------|-----------|-----------|-------------|

Добавляет манифест проверки локальных изменений ADR и записывает квалифицирующие долгосрочные решения как неизменяемые, заменяемые ADR.|
|`superpowers-bridge`|@JiangWay|[JiangWay/openspec-schemas (английский)](https://github.com/JiangWay/openspec-schemas/tree/main/superpowers-bridge)|объединяет управление артефактами OpenSpec с навыками выполнения [obra/superpowers (английский)](https://github.com/obra/superpowers) (мозговой штурм, написание планов, TDD через субагентов, проверка кода, завершение). Добавляет артефакт `retrospective`, основанный на доказательствах, заполняющий пробел, который Superpowers изначально не покрывает.|

Утверждения — это только наблюдаемое поведение (состояние HTTP, тело ответа, постоянное состояние — никогда не регистрировать подстроки); при каждом запуске фиксируются начальное/конечное время в формате UTC, продолжительность и оптимальная оценка потребления токенов LLM.|
|`anvil`|@jikkujoyce|[jikkujoyce/openspec-schemas (английский)](https://github.com/jikkujoyce/openspec-schemas/tree/main/schemas/anvil)|Рабочий процесс, основанный на спецификациях, с дисциплиной TDD и этапом состязательной проверки. Поток: `proposal` → `specs` → `design` → `review` → `test-plan` → `tasks` → `apply` → `verify`. `review` написан рецензентом с новым контекстом, доступным только для чтения (вторая модель, если таковая доступна) и выдает строку `VERDICT:`, сообщающую агенту шлюзовать `test-plan`, `tasks` и `apply`; OpenSpec проверяет только наличие артефактов, поэтому используйте шлюз с помощью собственного CI или перехватчика. `test-plan` сопоставляет каждый сценарий спецификации с именованным тестом и выполняет функцию красного/зеленого реестра, который проверяет `verify`.|
|`ml-research`|@tsenst|[идеало/openspec-schemas (английский)](https://github.com/idealo/openspec-schemas/tree/main/openspec/schemas/ml-research)|Рабочий процесс эксперимента машинного обучения. Поток: `proposal` → `design` → `evaluation` → `tasks` → `apply` → `specs`. `evaluation` исправляет метрики, критерии успеха и условия фальсификации перед запуском; `apply` записывает `results.md`; `specs` записывает только подтвержденные данные (включая опровергнутые гипотезы) как требования `Finding:` со связанными блоками `Evidence:`.|
