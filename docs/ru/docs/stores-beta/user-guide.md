# Хранилища: план в собственном репозитории

> **Бета-версия.** Хранилища, ссылки, рабочий контекст и рабочие наборы
> новый. Имена команд, флаги, форматы файлов и вывод JSON могут измениться.
> форма между выпусками. Каждое прохождение ниже было проведено с учетом
> текущая сборка, но после обновления перечитайте это руководство.

<a id="the-problem-this-solves"></a>
## Проблема, которую это решает

OpenSpec обычно находится внутри одного репозитория кода: папки `openspec/` рядом с
вашим кодом, в которой хранятся спецификации и изменения для этого репозитория.

Это перестает соответствовать моменту, когда ваше планирование превышает один репозиторий:

- Ваша работа охватывает несколько репозиториев — одна функция касается сервера API,
  веб-приложение и общая библиотека. Чья папка `openspec/` выполняет план
  живешь?
- Ваша команда планирует еще до появления кода или планирует то, что никогда не станет реальностью.
  код в *этом* репозитории.
- Требования принадлежат одной команде и используются другими. Вики
  версия меняется, и ваш агент кодирования все равно не может ее прочитать.

**хранилище** — это ответ: автономное репозиторий, вся работа которого заключается в планировании. Он
имеет ту же самую знакомую вам форму `openspec/` — спецификации и изменения —
плюс небольшой идентификационный файл. Вы регистрируете его на своей машине один раз по
имени, и тогда каждая обычная команда OpenSpec может работать в нем откуда угодно.

<a id="the-shape"></a>
## Форма

```
            team-plans  (a store: planning in its own repo)
            ├── .openspec-store/store.yaml     личность: «Я — командные планы»
            └── openspec/
                ├── specs/      что правда
                └── changes/    что в движении
                      ▲
                      │ registered on each machine by name;
                      │ shared by pushing/cloning like any repo
        ┌─────────────┼─────────────┐
        │             │             │
    web-app       api-server     mobile-app
   (code repo)   (code repo)    (code repo)
```

Два правила делают это простым:

1. **Хранилище — это всего лишь репозиторий git.** Вы фиксируете, отправляете, извлекаете и просматриваете его.
   себя. OpenSpec никогда не клонирует, не синхронизирует и не отправляет что-либо самостоятельно.
2. **Декларации, а не механизмы.** Репозитории могут *декларировать*, как они относятся к
   хранилища (показаны ниже). Объявления меняют то, что OpenSpec может вам сказать —
   никогда там, где действуют ваши команды.

<a id="story-one-team-one-planning-repo"></a>
## История: одна команда, одно планирование репозитория.

команда сохраняет свои спецификации и изменения в `team-plans`
, а не разбрасывает их по репозиториям кода.

**День первый (кто бы это ни настраивал):**

```bash
openspec store setup team-plans --path ~/openspec/team-plans \
  --remote git@github.com:acme/team-plans.git
git -C ~/openspec/team-plans push -u origin main
```

передача `--remote` записывает URL-адрес клона в собственный идентификационный файл
хранилища (`.openspec-store/store.yaml`) при первоначальной фиксации. Каждый будущий клон рождается,
зная, откуда он взялся, поэтому проверки работоспособности и сообщения
об ошибках могут распечатать полное исправление, которое можно вставить,
для товарищей по команде, у которых его еще нет.

**Каждый товарищ по команде (один раз на машину):**

```bash
git clone git@github.com:acme/team-plans.git ~/openspec/team-plans
openspec store register ~/openspec/team-plans
```

С этого момента все работают в одном и том же репозитории планирования по имени:

```bash
openspec status --store team-plans --change add-login
openspec show add-login --store team-plans
```

**Совместное использование работы — это git, намеренно.** Создаваемое вами изменение существует
только в вашей проверке до тех пор, пока вы не зафиксируете и
не отправите его — то же самое, что и код. Планы получают
ветки, пул-реквесты и ревью бесплатно, потому что хранилище — это обычный репозиторий.

**Соединение репозиториев кода команды.** Репозиторию кода, планирование которого
полностью реализовано, требуется ровно одна строка в `openspec/config.yaml` :

```yaml
# веб-приложение/openspec/config.yaml
store: team-plans
```

Теперь каждая команда OpenSpec, запущенная внутри `web-app`
, действует на `team-plans` вообще без флагов:

```bash
cd ~/src/web-app
openspec status --change add-login
```

```
Using OpenSpec root: team-plans (/Users/you/openspec/team-plans)
...
```

указатель является запасным вариантом, а не переопределением: явный `--store`
всегда побеждает, и если репозиторий создает собственные собственные папки
планирования, они выигрывают (с предупреждением об удалении устаревшего указателя).

**Одно значение по умолчанию для каждого репозитория на вашем компьютере.** Если вы
работаете со многими репозиториями кода, которые все планируют разместить в одном хранилище,
задайте его один раз глобально, вместо добавления строки `store:` в каждое репозиторий:

```bash
openspec config set defaultStore team-plans
```

теперь любая команда, выполняемая вне корня планирования — без `--store`
и без указателя проекта — разрешается в `team-plans` . Он
находится внизу списка приоритетов, поэтому `--store` , локальный корень и указатель
проекта `store:` все равно выигрывают. Корневой баннер и блок JSON
`root` сообщают `source: "global_default"` с идентификатором хранилища, поэтому вы всегда можете
определить общемашинное значение по умолчанию по собственному указателю репозитория. Очистите это
с помощью `openspec config unset defaultStore` . Если идентификатор не зарегистрирован, выдается ошибка
команды и предлагается зарегистрировать его или очистить устаревшее значение по умолчанию.

<a id="example-one-feature-two-component-repos"></a>
## Пример: одна функция, два репозитория компонентов.

Предположим, что `add-checkout-promo` изменяет `checkout-api` и `checkout-web` . Команда хочет иметь
один общий контракт на продукт, в то время как для каждого
репозитория кода по-прежнему требуются свои собственные задачи реализации, ветка и проверка.

используйте два слоя:

1. сохранить общее поведение в `team-plans`.
2. храните планы реализации в репозитории каждого компонента и ссылайтесь на хранилище.
   как восходящий контекст только для чтения.

Сначала спланируйте общий контракт в хранилище:

```bash
openspec new change add-checkout-promo --store team-plans
openspec status --change add-checkout-promo --store team-plans
```

Предложение и спецификации должны описывать поведение на границе между
компонентами — например, поля продвижения, возвращаемые службой, и то, как
интерфейс обрабатывает неподходящее оформление заказа. Просмотрите это изменение в репозитории
хранилища, как и любую другую ветку и запрос на включение.

<a id="what-context-does-planning-see"></a>
### В каком контексте рассматривается планирование?

выбор хранилища меняет корень OpenSpec; он не обнаруживает и не читает
все репозитории кода, использующие это хранилище. Инструкции хранилища видят артефакты и настроенный
контекст в хранилище. Они видят код компонента только в том случае,
если эти папки также доступны агенту или редактору и агент их читает.

Рабочий набор — это удобный способ открыть
хранилище планирования и оба репозитория кода вместе:

```bash
openspec workset create checkout-promo \
  --member ~/openspec/team-plans \
  --member ~/src/checkout-api \
  --member ~/src/checkout-web \
  --tool code
openspec workset open checkout-promo
```

это делает папки видимыми в одном рабочем пространстве IDE. Он не копирует
исходный контекст в хранилище, не выбирает затронутые репозитории и не предоставляет агенту
разрешение на их редактирование. Поместите надежные данные о перекрестных компонентах в общие
спецификации; не полагайтесь на то, что планировщик помнит источник, который ему довелось проверить.

<a id="how-does-implementation-start-in-each-repo"></a>
### Как начинается реализация в каждом репозитории?

Если явный корень `--store` или более близкий к `openspec/` не
применяется, указатель `store: team-plans` направляет команды в это хранилище. Он не разделяет
один список задач хранилища по каталогу, из которого был вызван
`apply` . OpenSpec в настоящее время не направляет задачи в репозитории.

Когда каждому компоненту требуется цикл применения/проверки с независимой
областью действия, дайте ему локальный корень OpenSpec и
ссылайтесь на центральное хранилище, а не указывайте на него:

```yaml
# checkout-api/openspec/config.yaml (и аналогично в checkout-web)
schema: spec-driven
references:
  - team-plans
```

После того как общий контракт будет одобрен и доступен в
основных спецификациях хранилища, внесите небольшое локальное изменение для части компонента:

```bash
cd ~/src/checkout-api
openspec new change implement-checkout-promo-api

cd ~/src/checkout-web
openspec new change implement-checkout-promo-ui
```

Справочный индекс в инструкциях каждого репозитория содержит сводную информацию
о спецификации хранилища и точную команду выборки `openspec show ... --store team-plans` . Каждое
локальное предложение ссылается на этот общий контракт, а его задачи
описывают только работу в этом компоненте. Затем запустите `/opsx:apply` в
каждом репозитории отдельно; Разрешение root сохраняет артефакты и изменения реализации
в пределах этого репозитория. Изменения сервиса и внешнего интерфейса теперь
можно тестировать, просматривать, объединять и архивировать независимо друг от друга.

Если реализация должна начаться, пока изменение общего хранилища
еще активно, извлеките его явно с помощью `openspec show add-checkout-promo --store team-plans` ;
справочные индексы перечисляют канонические спецификации хранилища, а не
активные изменения хранилища. Сохраняйте ссылки на ветки хранилища и
ветки компонентов в описаниях запросов на включение, чтобы
рецензенты могли видеть, какой версии контракта соответствует каждая реализация.

<a id="story-requirements-that-cross-team-lines"></a>
## История: требования, пересекающие границы команды

Требования принадлежат команде платформы. Продуктовые команды создают на
основе них свои собственные репозитории и собственные разработки.
Ссылка описывает эти отношения, не перемещая чью-либо работу.

```
   platform-reqs (store)                 api-server (code repo)
   owned by the platform team            owned by a product team
   ┌──────────────────────────┐          ┌──────────────────────────┐
   │ openspec/specs/          │ ◀────────│ openspec/config.yaml │
   │   payments/spec.md       │ reads    │   references:            │
   │   auth/spec.md           │          │     - platform-reqs      │
   │                          │          │ openspec/specs/          │
   │ openspec/changes/        │          │   (their own designs)    │
   │   platform work          │          │ openspec/changes/        │
   │                          │          │   (their own work)       │
   │                          │          └──────────────────────────┘
   └──────────────────────────┘
```

[Русское пояснение подписей и сообщений](../../EXAMPLE_NOTES.md#example-057).


**Команда продукта заявляет, на чем она
основана** в своем репозитории `openspec/config.yaml` :

```yaml
references:
  - platform-reqs
```

ссылки доступны только для чтения. В репозитории хранится собственный корень
`openspec/` ; работа остается там. Что изменилось: `openspec instructions` в этом
репозитории теперь включает индекс спецификаций указанного хранилища — каждая из
которых содержит однострочное описание и точную команду выборки (`openspec show <spec-id>
--type spec --store platform-reqs`). Агент, работающий в `api-server` , может
найти требования к восходящим платежам, ссылаться на них и написать
свой низкоуровневый проект в корне репозитория — без необходимости вставки контекста.

ссылка может содержать исходный код клона, поэтому товарищи по команде,
у которых еще нет хранилища, получают полное исправление, а не тупик:

```yaml
references:
  - { id: platform-reqs, remote: "git@github.com:acme/platform-reqs.git" }
```

**Если вы хотите, чтобы план и код открывались вместе, создайте
рабочий набор.** Это личное и явное решение: каждый человек выбирает папки,
с которыми он фактически работает на своем компьютере. Ничего из
этих локальных путей оформления заказа не передается в общий репозиторий планирования.

```bash
openspec workset create platform \
  --member ~/openspec/platform-reqs \
  --member ~/src/api-server \
  --member ~/src/web-app
```

<a id="worksets-reopen-the-folders-you-work-on-together"></a>
## Рабочие наборы: повторно откройте папки, над которыми вы работаете вместе.

Отдельно от всего вышеперечисленного: большинство людей открывают одни и те же
несколько папок вместе в каждом сеансе — репозиторий планирования плюс два
или три репозитория кода. **Рабочий набор** — это личное именованное представление,
которое можно повторно открыть с помощью одной команды в выбранном вами инструменте.

```
  workset "platform"                 openspec workset open platform
  ├── team-plans   ~/openspec/team-plans │
  ├── api-server   ~/src/api-server ▼
  └── web-app      ~/src/web-app все три открываются в вашем инструменте.
```

```bash
openspec workset create platform \
  --member ~/openspec/team-plans --member ~/src/api-server \
  --tool code
openspec workset list
```

```
platform  (opens in VS Code)
  team-plans  /Users/you/openspec/team-plans
  api-server  /Users/you/src/api-server
```

`openspec workset open platform` затем запускает сохраненный инструмент: редакторы (VS Code, Cursor) открывают
одно окно с каждым участником и возвращаются. Первый член является
основным. Переопределите инструмент в любое время с помощью `--tool <id>` .

Рабочие наборы намеренно *не* имеют общее состояние. Они живут на вашей машине,
никогда не берут на себя обязательств и не предъявляют претензий к работе —
они записывают только то, что вам нравится, открыто вместе. Удаление одного из
них никогда не затрагивает папки участников. Новые инструменты — это конфигурация, а не
код: все, что запускается через файл рабочей области или флаги подключения для
каждой папки, можно добавить под ключом `openers` в глобальной конфигурации (`openspec config edit`).

<a id="how-commands-decide-where-to-act"></a>
## Как команды решают, что делать.

Каждая обычная команда определяет свой корень одинаково, в следующем порядке:

```
1. --store <id>          you said so explicitly        → that store
2. nearest openspec/     a real planning root here     → this repo
   (walking up from cwd)
3. store: pointer        config.yaml declares a store  → that store
4. defaultStore          global config sets a machine  → that store
                         default
5. none of the above     stores registered on this     → error with a
                         machine?                        selection hint
                         no stores registered?         → the current
                                                          directory
                                                          (classic behavior)
```

<a id="known-limitations"></a>
## известные ограничения.

- **Форма бета-версии.** Все на этой странице может меняться в зависимости от выпуска —
  имена, флаги, форматы файлов, ключи JSON.
- **Одна касса для каждого идентификатора хранилища для каждой машины.** Регистрация второй кассы.
  под тем же идентификатором происходит сбой с подсказкой сначала к `store unregister`.
- **Никакой синхронизации никогда — так задумано.** OpenSpec никогда не клонирует, не извлекает и не отправляет.
  Устаревшая проверка показывает устаревшие спецификации, пока *вы* не вытащите; ссылки
  индексируется в реальном времени из всего, что есть на диске.
- **Пустые папки планирования могут отсутствовать.** В новом хранилище может не быть
  `openspec/changes/`, `openspec/specs/` или `openspec/changes/archive/` в Git.
  пока. Это допускается во время бета-тестирования; эти папки появляются когда-то нормально
  команды создают для них файлы.
- **Репозитории указателей остаются указателями.** Репозиторий только для конфигурации,
  `openspec/config.yaml` объявляет, что `store: <id>` рассматривается как внешний
  планирование, а не как касса хранилища для регистрации. Сначала удалите строку `store:`.
  если вы намеренно хотите преобразовать этот репозиторий в корень локального хранилища.
- **Некоторые команды остаются на своих местах.** `templates` и
  устаревшие формы существительных (`openspec change show`, ...) действуют на текущий
  только каталог — без `--store`. `schemas` следует каноническому выбору корня
  приоритет и принимает `--store <id>`, сохраняя при этом успешный массив JSON.
  форма не изменилась.
- **Состояние каждой машины соответствует каждой машине.** Реестр хранилища и рабочие наборы.
  локальные настройки. Ничто в компоновке вашей машины не является
  всегда стремился к совместному планированию.
- **Два стиля запуска рабочих наборов.** Инструмент, который нельзя запустить с помощью
  флаги прикрепления файлов рабочей области или отдельных папок не могут быть добавлены в качестве открывающего элемента.
- **Агент JSON имеет известное разделение регистра** (ключи семейства хранилищ
  Snake_case, семейство рабочих процессов CamelCase). Документировано в
  [агентский контракт](../agent-contract.md); его объединение откладывается до
  версия версии.

<a id="where-things-live"></a>
## Где живут вещи

|Что?|Где|Поделились?|
|---|---|---|
|Планирование хранилища.|`<store>/openspec/` (спецификации, изменения)|Да — зафиксируйте и отправьте его.|
|фирменный стиль хранилища.|`<store>/.openspec-store/store.yaml`|Да — зафиксировано с хранилищем|
|Реестр хранилища.|`<data dir>/openspec/stores/registry.yaml`|Нет — только эта машина|
|Рабочие наборы|`<data dir>/openspec/worksets/`|Нет — только эта машина|

`<data dir>` — это `~/.local/share/openspec` в
macOS и Linux (или `$XDG_DATA_HOME/openspec` ,
если установлено), и `%LOCALAPPDATA%\openspec` в Windows.
