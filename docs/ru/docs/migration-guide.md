<a id="migrating-to-opsx"></a>
# Переход на OPSX

Это руководство поможет вам перейти от устаревшего рабочего процесса OpenSpec к OPSX. Миграция должна быть плавной: ваша существующая работа сохраняется, а новая система обеспечивает большую гибкость.

<a id="whats-changing"></a>
## Что меняется?

OPSX заменяет старый рабочий процесс с фазовой синхронизацией на гибкий подход, основанный на действиях. Вот ключевое изменение:

|Аспект|Наследие|OPSX|
|--------|--------|------|
|**Команды**|`/openspec:proposal`, `/openspec:apply`, `/openspec:archive`|по умолчанию: `/opsx:propose`, `/opsx:explore`, `/opsx:apply`, `/opsx:update`, `/opsx:sync`, `/opsx:archive` (расширенные команды рабочего процесса необязательны)|
|**Рабочий процесс**|создать все артефакты одновременно.|Создавайте постепенно или все сразу — на ваш выбор.|
|**Возвращаюсь**|Неудобные фазовые вентили.|Natural — обновляйте любой артефакт в любое время.|
|**Кастомизация**|фиксированная структура.|управляемый схемой, полностью взломанный.|
|**Конфигурация**|`CLAUDE.md` с маркерами + `project.md`|Очистить конфигурацию в `openspec/config.yaml`.|

**Изменение философии:** Работа не является линейной. OPSX перестает притворяться.

<a id="before-you-begin"></a>
## Прежде чем начать

<a id="your-existing-work-is-safe"></a>
### Ваша существующая работа безопасна

Процесс миграции разработан с учетом сохранения:

- **Активные изменения в `openspec/changes/`** — Полностью сохранены. Вы можете продолжить их с помощью команд OPSX.
- **Архивные изменения** — Нетронутые. Ваша история останется нетронутой.
- **Основные спецификации `openspec/specs/`** — без изменений. Это ваш источник истины.
- **Ваш контент в CLAUDE.md, AGENTS.md и т. д.** — Сохраняется. Удалены только блоки маркеров OpenSpec; все, что вы написали, остается.

<a id="what-gets-removed"></a>
### Что будет удалено

Заменяются только файлы, управляемые OpenSpec:

|Что?|Зачем|
|------|-----|
|устаревшие каталоги/файлы команд косой черты.|заменена новой системой навыков.|
|`openspec/AGENTS.md`|устаревший триггер рабочего процесса.|
|маркеры OpenSpec в `CLAUDE.md`, `AGENTS.md` и т. д.|Больше не требуется.|

**Расположение устаревших команд в зависимости от инструмента** (примеры: ваш инструмент может отличаться):

- Claude Code: `.claude/commands/openspec/`
- Cursor: `.cursor/commands/openspec-*.md`
- Devin Desktop, ранее Windsurf: `.windsurf/workflows/openspec-*.md`
- Клайн: `.clinerules/workflows/openspec-*.md`
- Ру: `.roo/commands/openspec-*.md`
- GitHub Copilot: `.github/prompts/openspec-*.prompt.md` (только расширения IDE; не поддерживается в Copilot CLI)
- Codex: OpenSpec теперь использует канонический путь `.agents/skills/openspec-*`. Файлы `SKILL.md`, управляемые OpenSpec, по прежнему пути `.codex/skills` согласовываются только после наличия замен; пользовательские файлы и отличающиеся копии остаются на месте. Если немаркированное дерево `.agents` уже содержит навыки OpenSpec, OpenSpec сохраняет существующий рендеринг Codex (`$openspec-*`) или общий (`/openspec-*`) вместо угадывания из устаревшего каталога. Выберите `codex` явно с помощью `openspec init`, чтобы сменить владельца. Устаревшая очистка подсказки по-прежнему предназначена только для имен файлов OpenSpec, включенных в разрешенный список, в `$CODEX_HOME/prompts` или `~/.codex/prompts`.
- И другие (Дополнить, Продолжить, Amazon Q и т. д.)

При миграции обнаруживаются настроенные вами инструменты и очищаются их устаревшие файлы.

Список удаления может показаться длинным, но это все файлы, изначально созданные OpenSpec. Ваш собственный контент никогда не удаляется.

<a id="what-needs-your-attention"></a>
### Что требует вашего внимания

Один файл требует переноса вручную:

**`openspec/project.md`** — Этот файл не удаляется автоматически, поскольку он может содержать написанный вами контекст проекта. Вам нужно будет:

1. просмотрите его содержимое.
2. переместите полезный контекст в `openspec/config.yaml` (см. руководство ниже).
3. удалите файл, когда будете готовы.

**Почему мы внесли это изменение:**

Старый `project.md` был пассивным — агенты могли его прочитать, а могли и нет, могли забыть, что они прочитали. Мы обнаружили, что надежность была непостоянной.

Новый контекст `config.yaml` **активно внедряется в каждый запрос на планирование OpenSpec**. Это означает, что соглашения вашего проекта, стек технологий и правила всегда присутствуют, когда ИИ создает артефакты. Более высокая надежность.

**Компромисс:**

Поскольку контекст добавляется в каждый запрос, вам следует быть кратким. Сосредоточьтесь на том, что действительно важно:
- Технический стек и ключевые соглашения.
- Неочевидные ограничения, которые должен знать ИИ.
- правила, которые раньше часто игнорировались.

Не беспокойтесь о том, чтобы все было идеально. Мы все еще изучаем, что здесь работает лучше всего, и будем улучшать работу внедрения контекста по мере экспериментов.

<a id="running-the-migration"></a>
## Запуск миграции

`openspec init` и `openspec update` обнаруживают устаревшие файлы и проводят один и тот же процесс очистки. Используйте то, что соответствует вашей ситуации:

- Новое устанавливает по умолчанию профиль `core` (`propose`, `explore`, `apply`, `update`, `sync`, `archive`).
- при перенесенной установке сохраняются ранее установленные рабочие процессы путем записи профиля `custom` при необходимости.

<a id="using-openspec-init"></a>
### Использование `openspec init`

запустите это, если вы хотите добавить новые инструменты или перенастроить настроенные инструменты:

```bash
openspec init
```

команда init обнаруживает устаревшие файлы и помогает выполнить очистку:

```
Upgrading to the new OpenSpec

OpenSpec now uses agent skills, the emerging standard across coding
agents. This simplifies your setup while keeping everything working
as before.

Files to remove
No user content to preserve:
  • .claude/commands/openspec/
  • openspec/AGENTS.md

Files to update
OpenSpec markers will be removed, your content preserved:
  • CLAUDE.md
  • AGENTS.md

Needs your attention
  • openspec/project.md
    We won't delete this file. It may contain useful project context.

    The new openspec/config.yaml has a "context:" section for planning
    context. This is included in every OpenSpec request and works more
    reliably than the old project.md approach.

    Review project.md, move any useful content to config.yaml's context
    section, then delete the file when ready.

? Upgrade and clean up legacy files? (Y/n)
```

[Русское пояснение подписей и сообщений](../EXAMPLE_NOTES.md#example-050).


**Что происходит, когда вы говорите «да»:**

1. устаревшие каталоги команд косой черты удалены.
2. маркеры OpenSpec удалены из `CLAUDE.md`, `AGENTS.md` и т. д. (ваш контент останется)
3. `openspec/AGENTS.md` удален.
4. В `.claude/skills/` установлены новые навыки.
5. `openspec/config.yaml` создан со схемой по умолчанию.

<a id="using-openspec-update"></a>
### Использование `openspec update`

Запустите это, если вы просто хотите перенести и обновить существующие инструменты до последней версии:

```bash
openspec update
```

команда обновления также обнаруживает и очищает устаревшие артефакты, а затем обновляет сгенерированные навыки/команды в соответствии с вашим текущим профилем и настройками формы установки.

<a id="non-interactive--ci-environments"></a>
### Неинтерактивные среды/среды CI

Для миграции по сценарию:

```bash
openspec init --force --tools claude
```

флаг `--force` пропускает запросы и автоматически принимает очистку.

сюда входит очистка файлов подсказок Codex, управляемых OpenSpec, в глобальном каталоге подсказок Codex. Очистка нацелена только на устаревшие имена файлов подсказок Codex, включенные в разрешенный список OpenSpec, удаляет их только после существования навыков замены `.agents/skills/openspec-*` и сохраняет все остальные файлы.

<a id="migrating-projectmd-to-configyaml"></a>
## Перенос project.md в config.yaml

старый `openspec/project.md` представлял собой файл Markdown произвольной формы для контекста проекта. Новый `openspec/config.yaml` структурирован и, что особенно важно, **включен в каждый запрос на планирование**, поэтому ваши соглашения всегда присутствуют, когда работает ИИ.

<a id="before-projectmd"></a>
### До (project.md)

```markdown
# Контекст проекта

это монорепозиторий TypeScript с использованием React и Node.js.
Мы используем Jest для тестирования и следуем строгим правилам ESLint.
Наш API является RESTful и документирован в docs/api.md.

## Соглашения

- все общедоступные API должны поддерживать обратную совместимость.
- Новые функции должны включать тесты.
- используйте формат «Дано/Когда/Тогда» для спецификаций.
```

<a id="after-configyaml"></a>
### После (config.yaml)

```yaml
schema: spec-driven

context: |
  Tech stack: TypeScript, React, Node.js
  Testing: Jest with React Testing Library
  API: RESTful, documented in docs/api.md
  мы поддерживаем обратную совместимость для всех общедоступных API.

rules:
  proposal:
    - включить план отката для рискованных изменений.
  specs:
    - использовать формат «Дано/Когда/То» для сценариев.
    - Ссылайтесь на существующие шаблоны, прежде чем изобретать новые.
  design:
    - включить диаграммы последовательности для сложных потоков.
```

<a id="key-differences"></a>
### Ключевые отличия

|project.md|config.yaml|
|------------|-------------|
|Markdown произвольной формы.|Структурированный YAML|
|один фрагмент текста.|отдельный контекст и правила для каждого артефакта.|
|Неясно, когда оно используется.|контекст отображается во ВСЕХ артефактах; правила появляются только в соответствующих артефактах|
|Не выбрана схема.|явное поле `schema:` устанавливает рабочий процесс по умолчанию.|

<a id="what-to-keep-what-to-drop"></a>
### Что оставить, что отказаться

При миграции будьте избирательны. Спросите себя: «Нужно ли это ИИ для *каждого* запроса на планирование?»

**Хорошие кандидаты на `context:`**
- Технический стек (языки, платформы, базы данных).
- Ключевые архитектурные шаблоны (монорепозиторий, микросервисы и т. д.).
- неочевидные ограничения («мы не можем использовать библиотеку X, потому что...»)
- важные соглашения, которые часто игнорируются.

**Вместо этого перейдите на `rules:`**
- форматирование, специфичное для артефакта («используйте в спецификациях задано/когда/тогда»)
- критерии проверки («предложения должны включать планы отката»).
- они отображаются только для соответствующего артефакта, что упрощает выполнение других запросов.

**Полностью исключить**
- общие рекомендации, которые ИИ уже знает.
- Подробные объяснения, которые можно резюмировать.
- исторический контекст, не влияющий на текущую работу.

<a id="migration-steps"></a>
### Этапы миграции

1. **Создайте config.yaml** (если он еще не создан init):
   ```yaml
   schema: spec-driven
   ```

2. **Добавьте контекст** (будьте кратки — это входит в каждый запрос):
   ```yaml
   context: |
     Здесь находится история вашего проекта.
     Сосредоточьтесь на том, что действительно нужно знать ИИ.
   ```

3. **Добавить правила для каждого артефакта** (необязательно):
   ```yaml
   rules:
     proposal:
       - Рекомендации для вашего предложения
     specs:
       - Ваши правила написания спецификаций
   ```

4. **Удалите project.md**, как только переместите все полезное.

**Не зацикливайтесь на этом.** Начните с самого необходимого и продолжайте повторять. Если вы заметили, что ИИ упускает что-то важное, добавьте это. Если контекст кажется раздутым, обрежьте его. Это живой документ.

<a id="need-help-use-this-prompt"></a>
### Нужна помощь? Используйте эту подсказку

Если вы не знаете, как выделить свой project.md, спросите своего помощника по искусственному интеллекту:

```
Я переношу данные из прежнего project.md OpenSpec в новый формат config.yaml.

Вот мой текущий project.md:
[вставьте содержимое project.md]

Помогите создать config.yaml со следующими разделами:
1. Краткий `context:` (он добавляется к каждому запросу планирования, поэтому оставьте только стек, основные ограничения и часто игнорируемые соглашения).
2. `rules:` для отдельных артефактов, если указания относятся к ним. Например, «используйте Given/When/Then» относится к правилам спецификаций, а не к общему контексту.

Исключите общие сведения, которые ИИ-модели уже знают. Сократите текст до необходимого минимума.
```

ИИ поможет вам определить, что важно, а что можно отрезать.

<a id="the-new-commands"></a>
## Новые команды

Доступность команды зависит от профиля:

**По умолчанию (профиль `core`):**

|Команда|Назначение|
|---------|---------|
|`/opsx:propose`|внесите изменения и сгенерируйте артефакты планирования за один шаг.|
|`/opsx:explore`|Продумывайте идеи без структуры.|
|`/opsx:apply`|Реализация задач из tasks.md.|
|`/opsx:update`|пересмотреть артефакты планирования изменений и обеспечить их согласованность.|
|`/opsx:sync`|объединить дельта-спецификации с основными спецификациями.|
|`/opsx:archive`|Завершить и заархивировать изменение.|

**Расширенный рабочий процесс (пользовательский выбор):**

|Команда|Назначение|
|---------|---------|
|`/opsx:new`|Запуск нового каркаса изменений.|
|`/opsx:continue`|создать следующий артефакт (по одному)|
|`/opsx:ff`|Перемотка вперед: создавайте артефакты планирования сразу.|
|`/opsx:verify`|проверьте соответствие реализации спецификациям.|
|`/opsx:bulk-archive`|одновременно архивировать несколько изменений.|
|`/opsx:onboard`|управляемый сквозной рабочий процесс адаптации|

включите расширенные команды с помощью `openspec config profile`, затем запустите `openspec update`.

<a id="command-mapping-from-legacy"></a>
### Сопоставление команд из Legacy

|Наследие|эквивалент OPSX|
|--------|-----------------|
|`/openspec:proposal`|`/opsx:propose` (по умолчанию) или `/opsx:new`, затем `/opsx:ff` (расширенный)|
|`/openspec:apply`|`/opsx:apply`|
|`/openspec:archive`|`/opsx:archive`|

<a id="new-capabilities"></a>
### Новые возможности

Эти возможности являются частью расширенного набора команд рабочего процесса.

**Детальное создание артефактов:**
```
/opsx:continue
```
создает по одному артефакту за раз на основе зависимостей. Используйте это, если хотите просмотреть каждый шаг.

**Режим исследования:**
```
/opsx:explore
```
Обсудите идеи с партнером, прежде чем приступать к изменениям.

<a id="understanding-the-new-architecture"></a>
## Понимание новой архитектуры

<a id="from-phase-locked-to-fluid"></a>
### От фазовой синхронизации к жидкостному

Устаревший рабочий процесс требовал линейного прогресса:

```
┌──────────────┐      ┌──────────────┐      ┌──────────────┐
│   ПЛАНИРОВАНИЕ │ ───► │ ВНЕДРЕНИЕ │ ───► │ АРХИВИРОВАНИЕ │
│    PHASE     │      │    PHASE     │      │    PHASE     │
└──────────────┘      └──────────────┘      └──────────────┘

If you're in implementation and realize the design is wrong?
Too bad. Phase gates don't let you go back easily.
```

OPSX использует действия, а не фазы:

```
         ┌───────────────────────────────────────────────┐
         │           ACTIONS (not phases)                │
         │                                               │
         │     новый ◄──► продолжить ◄──► применить ◄──► архив │
         │      │          │           │             │   │
         │      └──────────┴───────────┴─────────────┘   │
         │                    any order                  │
         └───────────────────────────────────────────────┘
```

<a id="dependency-graph"></a>
### Граф зависимостей

Артефакты образуют ориентированный граф. Зависимости — это средства реализации, а не ворота:

```
                        proposal
                       (root node)
                            │
              ┌─────────────┴─────────────┐
              │                           │
              ▼                           ▼
           specs                       design
        (requires:                  (requires:
         proposal)                   proposal)
              │                           │
              └─────────────┬─────────────┘
                            │
                            ▼
                         tasks
                     (requires:
                     specs, design)
```

Когда вы запускаете `/opsx:continue`, он проверяет, что готово, и предлагает следующий артефакт. Вы также можете создать несколько готовых артефактов в любом порядке.

<a id="skills-vs-commands"></a>
### Навыки против команд

устаревшая система использовала командные файлы для конкретных инструментов:

```
.claude/commands/openspec/
├── proposal.md
├── apply.md
└── archive.md
```

OPSX использует новый стандарт **навыков**:

```
.claude/skills/
├── openspec-explore/SKILL.md
├── openspec-new-change/SKILL.md
├── openspec-continue-change/SKILL.md
├── openspec-apply-change/SKILL.md
└── ...
```

Навыки распознаются несколькими инструментами кодирования ИИ и предоставляют более обширные метаданные.

Codex доступен только для навыков в OPSX. OpenSpec больше не генерирует файлы пользовательских подсказок Codex; вместо этого используйте сгенерированные каталоги `.agents/skills/openspec-*`.

<a id="continuing-existing-changes"></a>
## Продолжение существующих изменений

Ваши текущие изменения легко работают с командами OPSX.

**Есть ли активное изменение по сравнению с устаревшим рабочим процессом?**

```
/opsx:apply add-my-feature
```

OPSX считывает существующие артефакты и продолжает с того места, где вы остановились.

**Хотите добавить дополнительные артефакты к существующему изменению?**

```
/opsx:continue add-my-feature
```

показывает, что можно создать на основе того, что уже существует.

**Нужно посмотреть статус?**

```bash
openspec status --change add-my-feature
```

<a id="the-new-config-system"></a>
## Новая система конфигурации

<a id="configyaml-structure"></a>
### Структура config.yaml

```yaml
# Обязательно: схема по умолчанию для новых изменений.
schema: spec-driven

# Необязательно: контекст проекта (максимум 50 КБ).
# внедрено во ВСЕ инструкции по артефактам.
context: |
  история вашего проекта, технический стек,
  conventions, and constraints.

# Необязательно: правила для каждого артефакта.
# внедряется только в соответствующие артефакты.
rules:
  proposal:
    - включить план отката.
  specs:
    - использовать формат «Дано/Когда/Тогда».
  design:
    - Стратегии возврата к документу
  tasks:
    - разбить на куски продолжительностью максимум 2 часа.
```

<a id="schema-resolution"></a>
### Разрешение схемы

При определении того, какую схему использовать, OPSX проверяет по порядку:

1. **Флаг CLI**: `--schema <name>` (высший приоритет)
2. **Изменить метаданные**: `.openspec.yaml` в каталоге изменений.
3. **Конфигурация проекта**: `openspec/config.yaml`
4. **По умолчанию**: `spec-driven`

<a id="available-schemas"></a>
### Доступные схемы

|Схема|Артефакты|Лучше всего подходит для|
|--------|-----------|----------|
|`spec-driven`|предложение → спецификации → дизайн → задачи|Большинство проектов|

Список всех доступных схем:

```bash
openspec schemas
```

<a id="custom-schemas"></a>
### Пользовательские схемы

Создайте свой собственный рабочий процесс:

```bash
openspec schema init my-workflow
```

Или создайте форк существующего:

```bash
openspec schema fork spec-driven my-workflow
```

подробности см. в разделе [Настройка](customization.md).

<a id="troubleshooting"></a>
## Устранение неполадок

<a id="legacy-files-detected-in-non-interactive-mode"></a>
### «Устаревшие файлы обнаружены в неинтерактивном режиме»

вы работаете в CI или неинтерактивной среде. Использование:

```bash
openspec init --force
```

<a id="commands-not-appearing-after-migration"></a>
### Команды не отображаются после миграции

Перезапустите интегрированную среду разработки. Навыки обнаруживаются при запуске.

<a id="unknown-artifact-id-in-rules"></a>
### «Неизвестный идентификатор артефакта в правилах»

Убедитесь, что ваши ключи `rules:` соответствуют идентификаторам артефактов вашей схемы:

- **на основе спецификации**: `proposal`, `specs`, `design`, `tasks`

запустите это, чтобы увидеть действительные идентификаторы артефактов:

```bash
openspec schemas --json
```

<a id="config-not-being-applied"></a>
### Конфигурация не применяется.

1. убедитесь, что файл находится по адресу `openspec/config.yaml` (а не `.yml`).
2. проверка синтаксиса YAML.
3. изменения конфигурации вступают в силу немедленно — перезагрузка не требуется.

<a id="projectmd-not-migrated"></a>
### project.md не перенесен

Система намеренно сохраняет `project.md`, поскольку он может содержать ваш пользовательский контент. Просмотрите его вручную, переместите полезные части в `config.yaml`, затем удалите.

<a id="want-to-see-what-would-be-cleaned-up"></a>
### Хотите посмотреть, что будет очищено?

Запустите init и отклоните запрос на очистку — вы увидите полную сводку обнаружения без каких-либо изменений.

<a id="quick-reference"></a>
## Краткий справочник

<a id="files-after-migration"></a>
### Файлы после миграции

```
project/
├── openspec/
│   ├── характеристики/ # Без изменений
│   ├── изменения/ # Без изменений
│   │ └── архив/ # Без изменений
│   └── config.yaml # НОВИНКА: Конфигурация проекта
├── .claude/
│   └── навыки/ # НОВИНКА: навыки OPSX
│       ├── openspec-propose/ # основной профиль по умолчанию
│       ├── openspec-explore/
│       ├── openspec-apply-change/
│       ├── openspec-update-change/
│       ├── openspec-sync-specs/
│       ├── openspec-archive-change/
│       └── ... # расширенный профиль добавляет новые/продолжить/ff/и т. д.
├── CLAUDE.md                     # маркеры OpenSpec удалены, ваш контент сохранен.
└── AGENTS.md                     # маркеры OpenSpec удалены, ваш контент сохранен.
```

<a id="whats-gone"></a>
### Что пропало

- `.claude/commands/openspec/` — заменен на `.claude/skills/`
- `openspec/AGENTS.md` — устаревший
- `openspec/project.md` — перейти на `config.yaml`, затем удалить
- блоки маркеров OpenSpec в `CLAUDE.md`, `AGENTS.md` и т. д.

<a id="command-cheatsheet"></a>
### Шпаргалка по командам

```text
/opsx:propose      Start quickly (default core profile)
/opsx:apply        Implement tasks
/opsx:archive      Finish and archive

# Расширенный рабочий процесс (если включен):
/opsx:new          Scaffold a change
/opsx:continue     Create next artifact
/opsx:ff           Create planning artifacts
```
