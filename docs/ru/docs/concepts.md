<a id="concepts"></a>
# Концепции

В этом руководстве объясняются основные идеи OpenSpec и то, как они сочетаются друг с другом. Для практического использования см. [Начало работы](getting-started.md) и [Рабочие процессы](workflows.md).

<a id="philosophy"></a>
## Философия

OpenSpec построен на четырех принципах:

```
fluid not rigid         — no phase gates, work on what makes sense
iterative not waterfall — learn as you build, refine as you go
easy not complex        — lightweight setup, minimal ceremony
brownfield-first        — works with existing codebases, not just greenfield
```

[Русское пояснение подписей и сообщений](../../../openspec/specs/russian-documentation/support/EXAMPLE_NOTES.md#example-045).


<a id="why-these-principles-matter"></a>
### Почему эти принципы важны

**Жидкий, а не жесткий.** Традиционные системы спецификаций разбивают вас на этапы: сначала вы планируете, затем реализуете, а затем все готово. OpenSpec более гибок — вы можете создавать артефакты в любом порядке, который имеет смысл для вашей работы.

**Итеративный, а не каскадный.** Требования меняются. Понимание углубляется. То, что вначале казалось хорошим подходом, может оказаться неэффективным после того, как вы увидите кодовую базу. OpenSpec принимает эту реальность.

**Просто и не сложно.** Некоторые платформы спецификации требуют обширной настройки, жестких форматов или сложных процессов. OpenSpec не мешает вам. Инициализируйте за считанные секунды, начинайте работать немедленно, настраивайте только при необходимости.

**Браунфилд в первую очередь.** Большинство программных работ не создаются с нуля, а модифицируются существующие системы. Дельта-подход OpenSpec позволяет легко указать изменения в существующем поведении, а не просто описывать новые системы.

<a id="the-big-picture"></a>
## Общая картина

OpenSpec распределяет вашу работу по двум основным направлениям:

```
┌────────────────────────────────────────────────────────────────────┐
│                        openspec/                                   │
│                                                                    │
│   ┌─────────────────────┐      ┌───────────────────────────────┐   │
│   │       specs/        │      │         changes/              │   │
│   │                     │      │                               │   │
│   │ Источник истины │◄─────│ Предлагаемые изменения │ │
│   │  How your system    │ merge│  Each change = one folder     │   │
│   │  currently works    │      │  Contains artifacts + deltas  │   │
│   │                     │      │                               │   │
│   └─────────────────────┘      └───────────────────────────────┘   │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

**Спецификации** являются источником истины: они описывают, как ваша система ведет себя в данный момент.

**Изменения** — это предлагаемые модификации — они хранятся в отдельных папках, пока вы не будете готовы их объединить.

Это разделение является ключевым. Вы можете работать над несколькими изменениями параллельно без конфликтов. Вы можете просмотреть изменение до того, как оно повлияет на основные спецификации. А когда вы архивируете изменение, его дельты полностью сливаются с источником истины.

<a id="specs"></a>
## Спецификации

спецификации описывают поведение вашей системы с использованием структурированных требований и сценариев.

<a id="structure"></a>
### Структура

```
openspec/specs/
├── auth/
│   └── spec.md           # Поведение аутентификации
├── payments/
│   └── spec.md           # Обработка платежей
├── notifications/
│   └── spec.md           # Система уведомлений
└── ui/
    └── spec.md           # Поведение и темы пользовательского интерфейса.
```

Организуйте спецификации по доменам — логические группы, которые имеют смысл для вашей системы. Общие шаблоны:

- **По функциональной области**: `auth/`, `payments/`, `search/`
- **По компонентам**: `api/`, `frontend/`, `workers/`
- **По ограниченному контексту**: `ordering/`, `fulfillment/`, `inventory/`

<a id="spec-format"></a>
### Формат спецификации

Спецификация содержит требования, и каждое требование имеет сценарии:

```markdown
# Спецификация аутентификации

## Purpose
Аутентификация и управление сеансами приложения.

## Requirements

### Requirement: Аутентификация пользователя.
Система SHALL выдает токен JWT при успешном входе в систему.

#### Scenario: действительные учетные данные.
- GIVEN — пользователь с действительными учетными данными.
- WHEN пользователь отправляет форму входа.
- THEN возвращается токен JWT.
- AND пользователь перенаправляется на панель управления.

#### Scenario: неверные учетные данные.
- GIVEN неверные учетные данные.
- WHEN пользователь отправляет форму входа.
- THEN отображается сообщение об ошибке.
- AND токен не выдается.

### Requirement: истечение срока действия сеанса.
Сеансы системы MUST прекращаются после 30 минут бездействия.

#### Scenario: тайм-аут простоя
- GIVEN сеанс с аутентификацией.
- WHEN Прошло 30 минут без активности.
- THEN сеанс признан недействительным.
- AND пользователь должен пройти повторную аутентификацию.
```

**Ключевые элементы:**

|Элемент|Назначение|
|---------|---------|
|`## Purpose`|Высокоуровневое описание домена этой спецификации.|
|`### Requirement:`|определенное поведение, которое должна иметь система.|
|`#### Scenario:`|Конкретный пример требования в действии.|
|SHALL/MUST/СЛЕДУЕТ|ключевые слова RFC 2119, указывающие силу требований.|

<a id="why-structure-specs-this-way"></a>
### Зачем структурировать спецификации таким образом

**Требования — это «что»** — они указывают, что должна делать система, без указания реализации.

**Сценарии — это «когда»** — они предоставляют конкретные примеры, которые можно проверить. Хорошие сценарии:
- доступны для тестирования (для них можно написать автоматический тест).
- охватывает как счастливый путь, так и крайние случаи.
- используйте «Дано/Когда/Тогда» или аналогичный структурированный формат.

**ключевые слова RFC 2119** (SHALL, MUST, SHOULD, MAY) сообщают о намерении:
- **MUST/SHALL** — абсолютное требование
- **СЛЕДУЕТ** — рекомендуется, но существуют исключения.
- **МОЖЕТ** — необязательно.

<a id="what-a-spec-is-and-is-not"></a>
### Что такое спецификация (и чем она не является)

Спецификация — это **контракт о поведении**, а не план реализации.

Хорошее содержание спецификаций:
- наблюдаемое поведение, на которое полагаются пользователи или последующие системы.
- входы, выходы и состояния ошибок.
- Внешние ограничения (безопасность, конфиденциальность, надежность, совместимость).
- сценарии, которые можно протестировать или явно проверить.

Избегайте использования в спецификациях:
- внутренние имена классов/функций.
- выбор библиотеки или платформы.
- Пошаговые подробности реализации.
- подробные планы выполнения (они принадлежат `design.md` или `tasks.md`).

Быстрый тест:
- Если реализацию можно изменить без изменения видимого извне поведения, то, скорее всего, она не принадлежит спецификации.

<a id="keep-it-lightweight-progressive-rigor"></a>
### Сохраняйте легкость: прогрессивная строгость

OpenSpec стремится избежать бюрократии. Используйте самый легкий уровень, при котором изменение все еще можно проверить.

**Облегченная спецификация (по умолчанию):**
- краткие требования, ориентированные на поведение.
- четкие рамки и отсутствие целей.
- Несколько конкретных приемочных проверок.

**Полная спецификация (для более высокого риска):**
- изменения между командами или между репо
- API/изменения контракта, миграции, проблемы безопасности/конфиденциальности.
- изменения, двусмысленность которых может привести к дорогостоящей доработке.

Большинство изменений должно оставаться в упрощенном режиме.

<a id="human--agent-collaboration"></a>
### Сотрудничество человека и агента

Во многих командах люди исследуют, а агенты создают артефакты. Предполагаемый цикл:

1. Человек обеспечивает намерение, контекст и ограничения.
2. Агент преобразует это в требования и сценарии, ориентированные на поведение.
3. Агент хранит детали реализации в `design.md` и `tasks.md`, а не в `spec.md`.
4. Валидация подтверждает структуру и ясность перед реализацией.

Благодаря этому спецификации становятся понятными для людей и согласованными для агентов.

<a id="changes"></a>
## Изменения

Изменение — это предлагаемая модификация вашей системы, упакованная в виде папки со всем необходимым для ее понимания и реализации.

<a id="change-structure"></a>
### Изменение структуры

```
openspec/changes/add-dark-mode/
├── proposal.md           # Почему и что
├── design.md             # Как (технический подход)
├── tasks.md              # Контрольный список реализации
├── .openspec.yaml        # Изменить метаданные (необязательно): схема, создано,skip_specs, retire_capabilities, а также ваши собственные ключи x-*.
└── specs/                # Характеристики Delta
    └── ui/
        └── spec.md       # Что меняется в ui/spec.md
```

Каждое изменение является самостоятельным. Он имеет:
- **Артефакты** — документы, отражающие намерения, дизайн и задачи.
- **Дельта-спецификации** — спецификации того, что добавляется, изменяется или удаляется.
- **Метаданные** — дополнительная конфигурация для этого конкретного изменения.

<a id="why-changes-are-folders"></a>
### Почему изменения — это папки

Упаковка изменений в виде папки имеет несколько преимуществ:

1. **Все вместе.** Предложения, дизайн, задачи и спецификации собраны в одном месте. Никакой охоты по разным локациям.

2. **Параллельная работа.** Несколько изменений могут существовать одновременно, не вызывая конфликтов. Работа над `add-dark-mode` также ведется, одновременно с `fix-auth-bug`.

3. **Очистить историю.** При архивировании изменения переносятся в `changes/archive/` с сохранением полного контекста. Вы можете оглянуться назад и понять не только то, что изменилось, но и почему.

4. **Удобство для просмотра.** Папку изменений легко просмотреть — откройте ее, прочитайте предложение, проверьте дизайн, посмотрите изменения в спецификациях.

<a id="artifacts"></a>
## Артефакты

Артефакты — это документы внутри изменения, которые направляют работу.

<a id="the-artifact-flow"></a>
### Поток артефактов

```
proposal ──────► specs ──────► design ──────► tasks ──────► implement
    │               │             │              │
   why            what           how          steps
 + scope        changes       approach      to take
```

Артефакты дополняют друг друга. Каждый артефакт обеспечивает контекст для следующего.

<a id="artifact-types"></a>
### Типы артефактов

<a id="proposal-proposalmd"></a>
#### Предложение (`proposal.md`)

В предложении отражены **намерение**, **объем** и **подход** на высоком уровне.

```markdown
# Предложение: добавить темный режим.

## намерение
пользователи запросили опцию темного режима, чтобы уменьшить нагрузку на глаза.
при использовании в ночное время и в соответствии с системными настройками.

## Область
В объёме:
- Переключение темы в настройках.
- определение системных предпочтений.
- сохранение предпочтений в localStorage.

Вне области применения:
- Пользовательские цветовые темы (будущая работа)
- переопределения тем для каждой страницы.

## Подход
используйте пользовательские свойства CSS для оформления тем в контексте React.
для управления состоянием. Определить системные предпочтения при первой загрузке,
разрешить ручное управление.
```

**Когда обновлять предложение:**
- изменения объема (сужение или расширение)
- Намерение проясняет (лучшее понимание проблемы)
- Принципиально меняется подход

<a id="specs-delta-specs-in-specs"></a>
#### Спецификации (разностные спецификации в `specs/`)

Дельта-спецификации описывают **что меняется** по сравнению с текущими спецификациями. См. [Дельта-спецификации](#delta-specs) ниже.

<a id="design-designmd"></a>
#### Дизайн (`design.md`)

Дизайн отражает **технический подход** и **архитектурные решения**.

````markdown
# Дизайн: добавлен темный режим.

## Технический подход
состояние темы управляется через контекст React, чтобы избежать детализации реквизита.
пользовательские свойства CSS позволяют переключаться во время выполнения без переключения классов.

## Архитектурные решения

### Решение: контекст поверх Redux
Использование контекста React для состояния темы, потому что:
- Простое двоичное состояние (светлый/темный)
- нет сложных переходов состояний.
- позволяет избежать добавления зависимости Redux.

### Решение: пользовательские свойства CSS
Использование переменных CSS вместо CSS-in-JS, потому что:
- работает с существующей таблицей стилей.
- нет накладных расходов во время выполнения.
- решение, ориентированное на браузер.

## поток данных
```
ThemeProvider (контекст)
       │
       ▼
ThemeToggle ◄──► localStorage
       │
       ▼
переменные CSS (применяются к :root)
```

## File Changes
- `src/contexts/ThemeContext.tsx` (new)
- `src/components/ThemeToggle.tsx` (new)
- `src/styles/globals.css` (modified)
````

**Когда обновлять дизайн:**
- реализация показывает, что этот подход не будет работать.
- найдено лучшее решение
- Изменяются зависимости или ограничения.

<a id="tasks-tasksmd"></a>
#### Задачи (`tasks.md`)

Задачи – это **контрольный список реализации** — конкретные шаги с флажками.

```markdown
# Задачи

## 1. Инфраструктура темы.
- [ ] 1.1 Создание ThemeContext со светлым/темным состоянием.
- [ ] 1.2 Добавление пользовательских свойств CSS для цветов.
- [ ] 1.3 Реализовать сохранение localStorage.
- [ ] 1.4 Добавлено обнаружение системных предпочтений.

## 2. Компоненты пользовательского интерфейса.
- [ ] 2.1 Создание компонента ThemeToggle
- [ ] 2.2 Добавить переключатель на страницу настроек.
- [ ] 2.3 Обновить заголовок, включив в него быстрое переключение.

## 3. Стиль
- [ ] 3.1 Определить цветовую палитру темной темы
- [ ] 3.2 Обновление компонентов для использования переменных CSS.
- [ ] 3.3 Проверка контрастности на предмет доступности
```

**Рекомендации по выполнению задач:**
- Группируйте связанные задачи под заголовками.
- использовать иерархическую нумерацию (1.1, 1.2 и т. д.).
- делайте задачи достаточно маленькими, чтобы их можно было выполнить за один сеанс.
- укажите, как проверяется каждая задача (тест, команда или наблюдаемый результат).
- Разместите тесты и документацию, необходимые для работы каждой группы, внутри этой группы, а не в последней догоняющей группе.
- отмечайте задачи по мере их выполнения.

<a id="delta-specs"></a>
## Дельта-спецификации

Дельта-спецификации являются ключевой концепцией, которая позволяет OpenSpec работать при разработке существующих месторождений. Они описывают **что меняется**, а не повторяют всю спецификацию.

<a id="the-format"></a>
### Формат

```markdown
# Дельта для аутентификации

## ADDED Requirements

### Requirement: двухфакторная аутентификация.
Система MUST поддерживает двухфакторную аутентификацию на основе TOTP.

#### Scenario: регистрация 2FA
- GIVEN пользователь без включенной двухфакторной аутентификации.
- WHEN пользователь включает 2FA в настройках.
- THEN отображается QR-код для настройки приложения аутентификации.
- AND пользователь должен подтвердить код перед активацией.

#### Scenario: вход в систему с использованием двухфакторной аутентификации.
- GIVEN пользователь с включенной двухфакторной аутентификацией.
- WHEN пользователь отправляет действительные учетные данные.
- THEN представлен вызов OTP.
- вход в систему AND завершается только после получения действительного OTP.

## MODIFIED Requirements

### Requirement: истечение срока действия сеанса.
сеансы системы MUST прекращаются после 15 минут бездействия.
(Раньше: 30 минут)

#### Scenario: тайм-аут простоя
- GIVEN сеанс с аутентификацией.
- WHEN Прошло 15 минут без активности
- THEN сеанс признан недействительным.

## REMOVED Requirements

### Requirement: запомнить меня.
(Устарело в пользу 2FA. Пользователи должны повторно аутентифицироваться при каждом сеансе.)
```

<a id="delta-sections"></a>
### Дельта-разделы

|Раздел|Значение|Что происходит в архиве|
|---------|---------|------------------------|
|`## ADDED Requirements`|Новое поведение.|добавлено в основную спецификацию.|
|`## MODIFIED Requirements`|Изменено поведение.|заменяет существующее требование.|
|`## REMOVED Requirements`|устаревшее поведение.|удалено из основной спецификации; удаление последнего требования отменяет возможность и удаляет ее файл спецификации, когда изменение объявляет `retire_capabilities: true`|
|`## Purpose`|Для чего нужны совершенно новые возможности|определяет цель создаваемой основной спецификации; игнорируется, если спецификация уже существует|

<a id="why-deltas-instead-of-full-specs"></a>
### Почему дельты вместо полных спецификаций

**Ясность.** Дельта точно показывает, что меняется. Прочитав полную спецификацию, вам придется мысленно сравнить ее с текущей версией.

**Предотвращение конфликтов.** Два изменения могут касаться одного и того же файла спецификации без конфликта, если они изменяют разные требования.

**Эффективность проверки.** Рецензенты видят изменения, а не неизменный контекст. Сосредоточьтесь на том, что важно.

**Подходит для Браунфилда.** Большая часть работ изменяет существующее поведение. Дельты делают модификации первоклассными, а не второстепенными.

<a id="schemas"></a>
## Схемы

схемы определяют типы артефактов и их зависимости для рабочего процесса.

<a id="how-schemas-work"></a>
### Как работают схемы

```yaml
# openspec/schemas/spec-driven/schema.yaml
name: spec-driven
artifacts:
  - id: proposal
    generates: proposal.md
    requires: []              # No dependencies, can create first

  - id: specs
    generates: specs/**/*.md
    requires: [proposal]      # Needs proposal before creating

  - id: design
    generates: design.md
    requires: [proposal]      # Can create in parallel with specs

  - id: tasks
    generates: tasks.md
    requires: [specs, design] # Needs both specs and design first
```

[Русское пояснение подписей и сообщений](../../../openspec/specs/russian-documentation/support/EXAMPLE_NOTES.md#example-046).


**Артефакты образуют граф зависимостей:**

```
                    proposal
                   (root node)
                       │
         ┌─────────────┴─────────────┐
         │                           │
         ▼                           ▼
      specs                       design
   (requires:                  (requires:
    proposal)                   proposal)
         │                           │
         └─────────────┬─────────────┘
                       │
                       ▼
                    tasks
                (requires:
                specs, design)
```

**Зависимости — это средства реализации, а не ворота.** Они показывают, что можно создать, а не то, что вы должны создать дальше. Вы можете пропустить дизайн, если он вам не нужен. Вы можете создавать спецификации до или после проектирования — и то, и другое зависит только от предложения.

<a id="built-in-schemas"></a>
### Встроенные схемы.

**на основе спецификации** (по умолчанию)

Стандартный рабочий процесс для разработки на основе спецификаций:

```
proposal → specs → design → tasks → implement
```

Подходит для: большинства функций, требующих согласования спецификаций перед реализацией.

<a id="custom-schemas"></a>
### Пользовательские схемы

Создавайте собственные схемы для рабочего процесса вашей команды:

```bash
# Создать с нуля.
openspec schema init research-first

# Или создайте форк существующего.
openspec schema fork spec-driven research-first
```

**Пример пользовательской схемы:**

```yaml
# openspec/schemas/research-first/schema.yaml
name: research-first
artifacts:
  - id: research
    generates: research.md
    requires: []           # Do research first

  - id: proposal
    generates: proposal.md
    requires: [research]   # Proposal informed by research

  - id: tasks
    generates: tasks.md
    requires: [proposal]   # Skip specs/design, go straight to tasks
```

[Русское пояснение подписей и сообщений](../../../openspec/specs/russian-documentation/support/EXAMPLE_NOTES.md#example-047).


Подробную информацию о создании и использовании пользовательских схем см. в разделе [Настройка](customization.md).

<a id="archive"></a>
## Архив

Архивирование завершает изменение путем объединения его дельта-спецификаций с основными спецификациями и сохранения изменений для истории.

<a id="what-happens-when-you-archive"></a>
### Что происходит при архивировании

```
Before archive:

openspec/
├── specs/
│   └── auth/
│       └── spec.md ◄────────────────┐
└── changes/                         │
    └── add-2fa/                     │
        ├── proposal.md              │
        ├── design.md                │ merge
        ├── tasks.md                 │
        └── specs/                   │
            └── auth/                │
                └── spec.md ─────────┘


After archive:

openspec/
├── specs/
│   └── auth/
│       └── spec.md        # Теперь включает требования 2FA.
└── changes/
    └── archive/
        └── 2025-01-24-add-2fa/    # Сохранено для истории
            ├── proposal.md
            ├── design.md
            ├── tasks.md
            └── specs/
                └── auth/
                    └── spec.md
```

<a id="the-archive-process"></a>
### Процесс архивирования

1. **Объединить изменения.** Каждый раздел дельта-спецификации (ADDED/MODIFIED/REMOVED) применяется к соответствующей основной спецификации.

2. **Переместить в архив.** Папка изменений перемещается в `changes/archive/` с префиксом даты для хронологического порядка.

3. **Сохранить контекст.** Все артефакты в архиве остаются нетронутыми. Вы всегда можете оглянуться назад, чтобы понять, почему были внесены изменения.

<a id="why-archive-matters"></a>
### Почему архивирование имеет значение

**Состояние очистки.** Активные изменения (`changes/`) показывают только текущую работу. Завершенная работа уходит в сторону.

**Аудитный журнал.** В архиве сохраняется полный контекст каждого изменения — не только то, что изменилось, но и предложение, объясняющее почему, дизайн, объясняющий, как, и задачи, показывающие выполненную работу.

**Эволюция спецификаций.** Спецификации растут естественным образом по мере архивирования изменений. Каждый архив объединяет свои изменения, со временем создавая комплексную спецификацию.

<a id="how-it-all-fits-together"></a>
## Как все это сочетается друг с другом

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                              OPENSPEC FLOW                                   │
│                                                                              │
│   ┌────────────────┐                                                         │
│   │  1. START      │  /opsx:propose (core) or /opsx:new (expanded)           │
│   │     CHANGE     │                                                         │
│   └───────┬────────┘                                                         │
│           │                                                                  │
│           ▼                                                                  │
│   ┌────────────────┐                                                         │
│   │  2. CREATE     │  /opsx:ff or /opsx:continue (expanded workflow)         │
│   │     ARTIFACTS  │  Creates proposal → specs → design → tasks              │
│   │                │  (based on schema dependencies)                         │
│   └───────┬────────┘                                                         │
│           │                                                                  │
│           ▼                                                                  │
│   ┌────────────────┐                                                         │
│   │  3. IMPLEMENT  │  /opsx:apply                                            │
│   │     TASKS      │  Work through tasks, checking them off                  │
│   │ │◄──── Обновляйте артефакты по мере обучения │
│   └───────┬────────┘                                                         │
│           │                                                                  │
│           ▼                                                                  │
│   ┌────────────────┐                                                         │
│   │  4. VERIFY     │  /opsx:verify (optional)                                │
│   │     WORK       │  Check implementation matches specs                     │
│   └───────┬────────┘                                                         │
│           │                                                                  │
│           ▼                                                                  │
│   ┌────────────────┐     ┌──────────────────────────────────────────────┐    │
│   │ 5. АРХИВ │────►│ Дельта-спецификации объединяются в основные │ │
│   │     CHANGE     │     │  Change folder moves to archive/             │    │
│   └───────────────┘ │ Спецификации теперь являются обновленным источником истины │ │
│                          └──────────────────────────────────────────────┘    │
│                                                                              │
└──────────────────────────────────────────────────────────────────────────────┘
```

**Благотворный цикл:**

1. спецификации описывают текущее поведение
2. Изменения предполагают модификации (в виде дельт).
3. Внедрение делает изменения реальными
4. Архив объединяет изменения в спецификации.
5. спецификации теперь описывают новое поведение.
6. Следующее изменение основано на обновленных спецификациях.

<a id="glossary"></a>
## Глоссарий

|Термин|Определение|
|------|------------|
|**Артефакт**|документ с изменением (предложение, дизайн, задачи или дельта-спецификации).|
|**Архив**|процесс завершения изменения и объединения его изменений с основными спецификациями.|
|**Изменить**|Предлагаемая модификация системы, упакованная в виде папки с артефактами.|
|**Дельта-спецификация**|спецификация, описывающая изменения (ADDED/MODIFIED/REMOVED) относительно текущих спецификаций.|
|**Домен**|логическая группа спецификаций (например, `auth/`, `payments/`).|
|**Требование**|определенное поведение, которое должна иметь система.|
|**Сценарий**|конкретный пример требования, обычно в формате «Дано/Когда/Тогда».|
|**Схема**|определение типов артефактов и их зависимостей.|
|**Спецификация**|спецификация, описывающая поведение системы, содержащая требования и сценарии.|
|**Источник истины**|каталог `openspec/specs/`, содержащий текущее согласованное поведение.|
