# Справочник CLI

OpenSpec CLI (`openspec`) предоставляет команды терминала для настройки, проверки, проверки состояния и управления проектом. Эти команды дополняют команды AI (например, `/opsx:propose`), описанные в разделе [Команды](commands.md).

<a id="summary"></a>
## Резюме

|Категория|Команды|Назначение|
|----------|----------|---------|
|**Настройка**|`init`, `update`|инициализируйте и обновите OpenSpec в своем проекте.|
|**Хранилища (отдельные репозитории OpenSpec)**|`store setup`, `store register`, `store unregister`, `store remove`, `store list`, `store doctor`|Управление хранилищами — зарегистрированные вами автономные репозитории OpenSpec.|
|**Здоровье**|`doctor`|сообщить о работоспособности отношений для выбранного корня.|
|**Рабочий контекст**|`context`|Соберите рабочий набор (корневой + ссылочные хранилища).|
|**Личные рабочие наборы**|`workset create`, `workset list`, `workset open`, `workset remove`|сохраняйте и открывайте личные локальные рабочие представления в своем инструменте.|
|**Просмотр**|`list`, `view`, `show`|Изучите изменения и спецификации.|
|**Проверка**|`validate`|проверьте изменения и спецификации на наличие проблем.|
|**Жизненный цикл**|`archive`|Завершить выполненные изменения.|
|**Рабочий процесс**|`new change`, `status`, `instructions`, `templates`, `schemas`|поддержка рабочего процесса на основе артефактов.|
|**Схемы**|`schema init`, `schema fork`, `schema validate`, `schema which`|создание пользовательских рабочих процессов и управление ими.|
|**Конфигурация**|`config`|просмотр и изменение настроек.|
|**Утилита**|`feedback`, `completion`|Обратная связь и интеграция оболочки.|

## Команды человека и агента

Большинство команд CLI предназначены для **использования человеком** в терминале. Некоторые команды также поддерживают **использование агента/скрипта** через вывод JSON.

<a id="human-only-commands"></a>
### Команды, доступные только человеку

Эти команды являются интерактивными и предназначены для использования в терминале:

|Команда|Назначение|
|---------|---------|
|`openspec init`|Инициализировать проект (интерактивные подсказки)|
|`openspec view`|Интерактивная панель управления.|
|`openspec workset open <name>`|открыть сохраненный рабочий набор (окно редактора или сеанс агента терминала).|
|`openspec config edit`|Открыть конфигурацию в редакторе.|
|`openspec feedback`|Отправьте отзыв через GitHub.|
|`openspec completion install`|Установите автодополнение оболочки.|

<a id="agent-compatible-commands"></a>
### Команды, совместимые с агентом

эти команды поддерживают вывод `--json` для программного использования агентами и сценариями ИИ:

|Команда|Использование человеком|Использование агента|
|---------|-----------|-----------|
|`openspec list`|просмотреть изменения/спецификации.|`--json` для структурированных данных.|
|`openspec show <item>`|прочитать содержимое|`--json` для разбора|
|`openspec validate`|Проверьте наличие проблем.|`--all --json` для массовой проверки.|
|`openspec status`|просмотр прогресса артефакта.|`--json` для структурированного статуса|
|`openspec instructions`|Узнайте дальнейшие действия|`--json` для инструкций агента.|
|`openspec templates`|найти пути к шаблонам.|`--json` для разрешения пути.|
|`openspec schemas`|список доступных схем.|`--json` для обнаружения схемы; `--store <id>` для выбора зарегистрированного корня|
|`openspec store setup <id>`|Создайте и зарегистрируйте локальное хранилище.|`--json` с явными входными данными для вывода структурированной настройки.|
|`openspec store register <path>`|Зарегистрируйте существующий хранилище.|`--json` для вывода структурированной регистрации.|
|`openspec store unregister <id>`|забыть регистрацию в местном хранилище.|`--json` для вывода структурированной очистки.|
|`openspec store remove <id>`|удалить зарегистрированную папку локального хранилища.|`--yes --json` для неинтерактивного удаления.|
|`openspec store list`|просмотр зарегистрированных хранилищ.|`--json` для структурированных регистраций.|
|`openspec store doctor`|проверьте настройки локального хранилища.|`--json` для структурированной диагностики|
|`openspec new change <id>`|создание структуры репо-локальных изменений.|`--json` плюс `--store <id>` для использования зарегистрированного хранилища в качестве корня OpenSpec.|
|`openspec workset create [name]`|создание личного рабочего представления.|`--member <path> --json` для неинтерактивной композиции.|
|`openspec workset list`|просмотр сохраненных рабочих наборов.|`--json` для структурированных представлений.|
|`openspec workset remove <name>`|удалить сохраненное представление.|`--yes --json` для неинтерактивного удаления.|

<a id="setup-commands"></a>
## Команды настройки

### `openspec init`

инициализируйте OpenSpec в своем проекте. Создает структуру папок и настраивает интеграцию инструментов AI.

поведение по умолчанию использует глобальные настройки конфигурации по умолчанию: профиль `core`, форма установки `both`, рабочие процессы `propose, explore, apply, update, sync, archive`.

```
openspec init [path] [options]
```

используйте `--language <language>` , чтобы добавить языковую инструкцию в `openspec/config.yaml`
нового проекта. Для существующего проекта отредактируйте поле `context` конфигурации,
чтобы OpenSpec никогда не перезаписывал рекомендации для конкретного проекта.

**Аргументы:**

|Аргумент|Обязательность|Описание|
|----------|----------|-------------|
|`path`|Нет|целевой каталог (по умолчанию: текущий каталог).|

**Параметры:**

|Опция|Описание|
|--------|-------------|
|`--tools <list>`|настройка инструментов ИИ в неинтерактивном режиме. Используйте `all`, `none` или список, разделенный запятыми.|
|`--language <language>`|запись артефактов на этом языке при создании новой конфигурации.|
|`--force`|автоматическая очистка устаревших файлов без запроса.|
|`--profile <profile>`|переопределить глобальный профиль для этого запуска (`core` или `custom`).|
|`--no-animation`|показывать статический экран приветствия вместо анимированного.|
|`--copilot-cloud`|Настройте GitHub Copilot [файлы облачного агента кодирования](supported-tools.md#github-copilot-cloud-coding-agent) без запроса.|
|`--no-copilot-cloud`|пропускать файлы облачного агента кодирования GitHub Copilot без запроса.|

`--profile custom` использует все рабочие процессы, выбранные в данный момент в глобальной конфигурации (`openspec config profile`).

Анимация приветствия также пропускается, если установлена ​​переменная среды `OPENSPEC_NO_ANIMATION` (любое значение, включая пустое), когда для `NO_COLOR` установлено непустое значение или когда включена настройка ОС по ограничению движения (macOS уменьшает движение, анимация GNOME отключена).

**Поддерживаемые идентификаторы инструментов (`--tools`)** — `windsurf` также принимается в качестве псевдонима для `devin`: `amazon-q`, `antigravity`, `auggie`, `bob`, `claude`, `cline`, `command-code`, `codeartsagent`, `codex`, `devin`, `forgecode`, `codebuddy`, `continue`, `costrict`, `crush`, `cursor`, `factory`, `gemini`, `github-copilot`, `hermes`, `iflow`, `junie`, `kilocode`, `kimi`, `kiro`, `lingma`, `minimax-code`, `vibe`, `oh-my-pi`, `opencode`, `pi`, `codeassistant`, `qoder`, `qwen`, `rovodev`, `roocode`, `trae`, `zed`, `zcode`, `agents`

> Этот список отражает `AI_TOOLS` в `src/core/config.ts`. См. [Поддерживаемые инструменты](supported-tools.md) для получения информации о навыках и путях команд каждого инструмента.

**Примеры:**

```bash
# Интерактивная инициализация
openspec init

# инициализировать в определенном каталоге.
openspec init ./my-project

# Неинтерактивный режим: настройка для Claude и Cursor.
openspec init --tools claude,cursor

# Неинтерактивный режим: настройка глобальных навыков кода MiniMax.
openspec init --tools minimax-code

# настройка для всех поддерживаемых инструментов.
openspec init --tools all

# переопределить профиль для этого запуска.
openspec init --profile core

# пропуск запросов и автоматическая очистка устаревших файлов.
openspec init --force
```

**Что он создаёт:**

```
openspec/
├── specs/              #Ваши характеристики (источник истины)
├── changes/            # Предлагаемые изменения
└── config.yaml         # Конфигурация проекта

.claude/skills/         # Claude Code skills (if claude selected)
.cursor/skills/         # Cursor skills (if cursor selected)
.cursor/commands/       # Cursor OPSX commands (if delivery includes commands)
.agents/skills/         # Shared skills for AGENTS.md-compatible tools (if agents selected)
... (other tool configs)
```

### `openspec update`

Обновите файлы инструкций OpenSpec после обновления CLI. Повторно генерирует файлы конфигурации инструмента AI, используя ваш текущий глобальный профиль, выбранные рабочие процессы и форма установки.

```
openspec update [path] [options]
```

**Аргументы:**

|Аргумент|Обязательность|Описание|
|----------|----------|-------------|
|`path`|Нет|целевой каталог (по умолчанию: текущий каталог).|

**Параметры:**

|Опция|Описание|
|--------|-------------|
|`--force`|принудительное обновление, даже если файлы обновлены.|
|`--dry-run`|Сообщите, что изменится в обновлении, и ничего не пишите.|
|`--json`|с помощью `--dry-run` выведите запланированные изменения как JSON.|

**Пример:**

```bash
# обновление файлов инструкций после обновления npm.
npm install -g @fission-ai/openspec@latest
openspec update
```

**Предварительный просмотр обновления:**

`--dry-run` сообщает о файлах, которые обновление добавит, изменит или удалит,
и ничего не пишет. Пути указаны относительно проекта; файлы за его
пределами (навыки в вашем домашнем каталоге) отображаются с префиксом `~/` .

```bash
openspec update --dry-run --json
```

```json
{
  "changes": [
    { "path": ".claude/skills/openspec-explore/SKILL.md", "action": "update", "tool": "claude" },
    { "path": "~/.minimax/skills/openspec-propose/SKILL.md", "action": "add", "tool": "minimax-code" }
  ],
  "notes": [],
  "failures": []
}
```

План — это то, что делает неинтерактивный запуск, и в
нем перечислены все файлы, которые он затронет: перемещение из прежнего каталога
инструмента, сохранение глобальной конфигурации для установки из предыдущих профилей, файлы облачного
агента Copilot и, с помощью `--force` , очистка устаревших артефактов.
Файлы, принадлежащие самому OpenSpec, а не одному инструменту, имеют `tool: "openspec"` .
`notes` помечает шаги, о которых будет спрашиваться пользователь терминала, каждый из
которых имеет стабильный `code` : `legacy-tool-directories` (перемещение указано как выполненное)
и `legacy-artifacts` (файлы старого макета, которые обновление оставляет без `--force` ).
`failures` перечисляет инструменты, с которыми реальное обновление не сработает, включая записи,
которые он не может выполнить (каталог вместо файла, нет разрешения
на запись); для этого инструмента план останавливается там, где было бы
обновление, и один сломанный инструмент не будет стоить вам остальной части
плана. Оба пусты для обычного обновления. Полная ссылка — [openspec.dev/docs/cli](../docs-lab/reference/cli.md) .

сбой `--dry-run --json` по-прежнему печатает ровно один документ JSON, пустой план
плюс массив `status` , и завершает работу с ненулевым значением.

сначала обновите пакет. Файлы инструкций генерируются установленным CLI, поэтому запуск `openspec update` на устаревшей установке сообщает обо всем актуальном виде без добавления рабочих процессов, поставляемых в новых выпусках.

Чтобы сделать это видимым, `openspec update` запрашивает реестр npm, была ли опубликована более новая версия CLI. Когда ваш отстает, он предлагает обновиться:

```text
доступна более новая версия OpenSpec CLI (v1.6.0 → v1.7.0).
  Запуск из: /usr/local/lib/node_modules/@fission-ai/openspec
? Обновиться до версии 1.7.0 сейчас? (Да/нет)
```

ответьте «да», и он запустит `npm install -g @fission-ai/openspec@latest`, затем повторно запустит обновление с новым CLI, чтобы новые рабочие процессы попадали в одну и ту же команду. Он подтверждает обновление, запрашивая у установленного двоичного файла его версию, а не доверяя коду выхода npm, поэтому, если другая установка, установленная ранее на вашем `PATH`, все еще отвечает, она сообщает вам, а не заявляет об успехе. Ответьте «нет», и он напечатает команду и обновит ваш CLI. Ctrl-C останавливает команду.

Предложение появляется только в интерактивном терминале и только тогда, когда установка принадлежит npm — единственный случай, который `npm install -g` фактически исправляет. Все остальное получает команду, соответствующую тому, как оно было установлено:

|Как устанавливается OpenSpec|Что вы получаете|
|---------------------------|--------------|
|глобальная установка npm.|приглашение и обновление запускаются автоматически — в интерактивном терминале; конвейерный вывод вместо этого получает напечатанную команду|
|глобальная установка pnpm, Bun, Yarn или Volta.|собственная команда этого менеджера: `pnpm add -g …@latest`, `bun add -g …@latest`, `yarn global add …@latest` или `volta install …@latest`.|
|зависимость проекта.|примечание для обновления зависимости, поскольку его менеджер пакетов владеет файлом блокировки.|
|Кэш `npx`/`dlx`.|`npx @fission-ai/openspec@latest update` — эта команда является обновлением, поэтому второго шага нет.|
|клон git.|Ничего — ваша версия такая, как написано в ветке.|

Всякий раз, когда что-либо печатается, оно называет каталог, из которого был загружен работающий CLI — это нужно проверить, когда вы выполнили обновление, но ваш `PATH` все еще принадлежит устаревшей прошивке.

он запрашивает реестр в `npm_config_registry`, когда npm экспортирует его, и в `https://registry.npmjs.org` в противном случае. Ни один `.npmrc` не читается: позволить содержимому файла выбирать, куда направляется исходящий запрос, — это поток, которого стоит избегать, а `.npmrc` проекта перемещается вместе с репозиторием. На частном зеркале экспортируйте `npm_config_registry` или настройте `OPENSPEC_NO_UPDATE_CHECK` на полный пропуск проверки. Проверка пропускается, если для `CI` установлено любое значение, кроме явного значения отключения (`false`, `0`, `no`, `off` или пустое), в `NODE_ENV=test` и всякий раз, когда установлено `OPENSPEC_NO_UPDATE_CHECK` (любое значение), `DO_NOT_TRACK=1` или `OPENSPEC_TELEMETRY=0`. Он запускается до обновления и может задержать его максимум на 1,5 секунды — после этого он прекращает работу, даже если сеть автоматически отбрасывает пакеты, и продолжает молчать, когда реестр недоступен.

**Как определяется актуальность:** файлы навыков записывают версию, которая их сгенерировала, поэтому
OpenSpec сравнивает ее с установленной версией CLI. Командные файлы не имеют
отметки версии, поэтому для инструмента, у которого есть команды, но нет
навыков (форма установки `commands` ), OpenSpec сравнивает содержимое файла с тем, что
он будет генерировать сейчас — изменения в этих файлах считаются отклонением
и перезаписываются. При поставке `skills` или `both` проверяется только записанная версия,
поэтому отредактированный вручную файл, версия которого все еще совпадает, остается в
покое; используйте `--force` , чтобы переписать его. В любом случае сгенерированные
файлы принадлежат OpenSpec — храните свои собственные инструкции в другом месте.

<a id="stores-standalone-openspec-repos"></a>
## Хранилища (автономные репозитории OpenSpec)

> **Бета.** Хранилища и созданные на их основе функции (ссылки, рабочий контекст, рабочие наборы) являются новыми; имена команд, флаги, форматы файлов и выходные данные JSON могут менять форму между выпусками. Подробное руководство по устранению неполадок см. в [руководстве для хранилищ](stores-beta/user-guide.md).

Хранилище — это автономное хранилище OpenSpec, которое вы зарегистрировали на этом компьютере, например хранилище планирования или хранилище контрактов. Регистрация хранилища позволяет обычным командам (`list`, `show`, `status`, `validate`, `new change`, `archive`, ...) действовать в нем из любого места, передав `--store <id>`.

### `openspec store setup`

Создайте и зарегистрируйте локальное хранилище. Без аргументов в
терминале OpenSpec помогает пользователю выполнить настройку. Агенты и сценарии
должны передавать явные входные данные и использовать `--json` .

```bash
openspec store setup [id] [options]
```

**Параметры:**

|Опция|Описание|
|--------|-------------|
|`--path <path>`|Папка, в которой должен находиться хранилище (например, `~/openspec/<id>`).|
|`--remote <url>`|Запишите канонический пульт в `store.yaml` нового хранилища.|
|`--init-git`|инициализировать репозиторий Git с помощью первоначальной фиксации (по умолчанию).|
|`--no-init-git`|пропускать все действия Git: без инициализации, без первоначальной фиксации.|
|`--json`|Выход JSON|

неинтерактивные запуски (`--json`, сценарии, агенты) должны передавать как идентификатор хранилища, так и `--path`. В интерактивном терминале программа установки запрашивает местоположение с редактируемым предложением в видимом, принадлежащем пользователю месте (например, `~/openspec/<id>`); по умолчанию он никогда не использует каталог управляемых данных OpenSpec.

Примеры:

```bash
openspec store setup
openspec store setup team-context
openspec store setup team-context --path ~/openspec/team-context --no-init-git
openspec store setup team-context --path ~/openspec/team-context --no-init-git --json
```

### `openspec store register`

Зарегистрируйте существующую папку локального хранилища. Во время бета-тестирования в хранилищах корень может
быть зарегистрирован до того, как появятся какие-либо изменения, будут применены спецификации или
изменения будут заархивированы; в этом случае `openspec/changes/` , `openspec/specs/` и `openspec/changes/archive/` могут
отсутствовать до тех пор, пока их не создадут обычные команды. Репозиторий только
для конфигурации, в котором объявляется `store: <id>` , остается указателем на другое хранилище
и не регистрируется как корневое хранилище, пока этот указатель не будет удален.

```bash
openspec store register [path] [options]
```

**Параметры:**

|Опция|Описание|
|--------|-------------|
|`--id <id>`|идентификатор хранилища; по умолчанию для хранения метаданных или имени папки|
|`--yes`|подтвердите создание метаданных идентификации хранилища для работоспособного корня OpenSpec.|
|`--json`|Выход JSON|

### `openspec store unregister`

Забудьте о регистрации в локальном хранилище, не удаляя файлы.

```bash
openspec store unregister <id> [--json]
```

Используйте это, когда хранилище было перемещено, клонировано в другое
место или больше не должно отображаться OpenSpec на этом компьютере.

### `openspec store remove`

Забудьте регистрацию в локальном хранилище и удалите его локальную папку.

```bash
openspec store remove <id> [--yes] [--json]
```

`remove` показывает точную папку перед удалением в
интерактивном терминале. Агенты, сценарии и вызывающие программы JSON
должны передать `--yes` для подтверждения удаления. OpenSpec отказывается
удалять папку, которая не содержит соответствующие метаданные хранилища.

### `openspec store list`

список локально зарегистрированных хранилищ.

```bash
openspec store list [--json]
openspec store ls [--json]
```

### `openspec store doctor`

проверьте регистрацию в локальном хранилище, метаданные и наличие Git.

```bash
openspec store doctor [id] [--json]
```

Доктор предназначен только для диагностики; он сообщает об отсутствующих корнях, несоответствии метаданных и недопустимом состоянии локального реестра без изменения хранилища.

<a id="referencing-stores-from-a-project"></a>
### Ссылки на хранилища из проекта

Репозиторий проекта может указывать, какие хранилища используются в `openspec/config.yaml`:

```yaml
schema: spec-driven
references:
  - team-context
```

С этого момента выходные данные `openspec instructions` в этом репозитории (как для каждого артефакта, так и для поверхностей `apply`, JSON и человеческого режима) содержат индекс спецификаций каждого ссылочного хранилища — идентификаторы спецификаций, однострочное резюме из раздела «Назначение» каждой спецификации и команду выборки (`openspec show <spec-id> --type spec --store <id>`). Индекс создается в реальном времени на основе зарегистрированной проверки при каждом запуске; содержимое спецификации никогда не копируется в выходные данные.

ссылки доступны только для чтения. Они никогда не меняют место действия команд: работа остается в корне репозитория, а запись в хранилище, на которое ссылаются, остается явным действием `--store`. Ссылка, которую невозможно разрешить (например, хранилище, не зарегистрированный на этом компьютере), превращается в предупреждение в индексе с точным исправлением, а инструкции по-прежнему генерируются. `openspec doctor` сообщает о работоспособности в одном месте.

<a id="recording-where-a-store-is-cloned-from"></a>
### Запись, из которой клонируется хранилище

Хранилище может записать свой канонический источник клона в свой зафиксированный идентификационный файл, поэтому адаптация никогда не заходит в тупик на этапе «зарегистрировать хранилище»:

```bash
openspec store setup team-context --path ~/openspec/team-context \
  --remote git@github.com:acme/team-context.git
```

Удаленный объект находится в `.openspec-store/store.yaml` внутри первоначального коммита, поэтому каждый клон рождается с этим знанием. Для существующего хранилища отредактируйте `store.yaml` вручную и зафиксируйте. `store doctor` показывает записанный удаленный доступ (и наблюдаемое происхождение Git кассы); руководство по настройке/регистрации общего доступа называет это; и регистр записывает происхождение оформления заказа в локальном реестре компьютера.

ссылочное объявление также может содержать исходный код клона, поэтому товарищ по команде, у которого еще нет хранилища, получает полное вставляемое исправление (`git clone <remote> <path> && openspec store register <path> --id <id>`):

```yaml
references:
  - { id: team-context, remote: "git@github.com:acme/team-context.git" }
```

Запись на удаленном компьютере не синхронизируется: OpenSpec никогда не клонирует, не извлекает и не отправляет самостоятельно.

<a id="declaring-a-default-store"></a>
### Объявление хранилища по умолчанию

Репозиторий, планирование которого полностью экспортировано (без локальных `openspec/specs/` или `openspec/changes/`), может объявить свое хранилище один раз вместо передачи `--store` в каждой команде:

```yaml
# openspec/config.yaml (единственный файл в openspec/)
store: team-context
```

обычные команды затем автоматически преобразуются в объявленное хранилище; корневой баннер и JSON `root` блокируют отчет `source: "declared"` с идентификатором хранилища и напечатанные подсказки по-прежнему содержат `--store <id>`. Это объявление является запасным вариантом, а не переопределением: явный `--store` всегда побеждает, а каталог с реальными папками планирования игнорирует указатель (с предупреждением). Чтобы преобразовать репозиторий указателей в локальный корень OpenSpec, удалите строку `store:` и запустите `openspec init` — init отказывается создавать шаблоны, пока присутствует объявление.

вариант машинного уровня охватывает все репозитории одновременно: `openspec config set defaultStore <id>` (см. Конфигурацию). К нему обращаются только после того, как `--store`, локальный корень и указатель проекта не удалось разрешить; корневой баннер и блок JSON `root` затем сообщают `source: "global_default"`.

<a id="doctor-relationship-health"></a>
## Доктор (здоровье в отношениях)

Один вопрос только для чтения, одно место: исправен ли корень OpenSpec и доступны ли на этом компьютере хранилища, на которые он ссылается?

```bash
openspec doctor [--store <id>] [--json]
```

в отчете разделяется состояние корня, состояние метаданных хранилища (включая примечание, когда записанное удаленное устройство и источник оформления заказа расходятся, а также примечание, когда оформление заказа в хранилище отклоняется от последней полученной ссылки отслеживания восходящего потока) и состояние ссылки (те же инструкции по диагностике показывают, с исправлениями клонирования для неразрешенных ссылок). Выводы о работоспособности любой степени серьезности, выход 0 — агенты читают массивы `status`; только сбои команд (нет рута, неизвестное хранилище) выход 1. Доктор никогда не клонирует, не синхронизирует и не восстанавливает. Чтобы получить сам собранный набор, а не его здоровье, используйте `openspec context`.

<a id="working-context-the-assembled-set"></a>
## Рабочий контекст (собранный набор)

Все, к чему относится эта работа, посредством объявлений OpenSpec в одном рабочем наборе: корень OpenSpec и хранилища, на которые он ссылается.

```bash
openspec context [--store <id>] [--json] [--code-workspace <path> [--force]]
```

Краткое описание JSON является расходным материалом для агентов (каждый доступный хранилище, на который есть ссылка, содержит свой рецепт извлечения; неразрешенные участники имеют те же инструкции по исправлениям и шоу врача). `--code-workspace` дополнительно записывает файл рабочей области VS Code, содержащий корень и доступные ссылочные хранилища (папки `ref:<id>`) — запись, которую выполняет эта команда, отклоняется без `--force`, если файл существует. Сообщается о недоступных участниках, о которых никогда не догадывались.

«Рабочий контекст» — собранный набор; Поле `context:` в `openspec/config.yaml` — это фон проекта, внедренный в инструкции — две разные вещи. `openspec doctor` отвечает, исправен ли аппарат; `openspec context` отвечает, что это за набор.

<a id="personal-worksets"></a>
## Персональные рабочие наборы.

> **Бета-версия.** Рабочие наборы являются частью новой бета-версии; команды, флаги и форматы файлов могут менять форму между выпусками. Подробное описание см. в [руководстве по хранилищам](stores-beta/user-guide.md#worksets-reopen-the-folders-you-work-on-together).

Рабочий набор — это личное именованное представление папок, над которыми вы работаете вместе (корень планирования плюс все остальное, что вы выберете), которое хранится на вашем компьютере и повторно открывается по имени в вашем инструменте. Он является чисто локальным: никогда не фиксируется, никогда не используется совместно, никогда не выводится из деклараций, а его удаление никогда не затрагивает членскую папку.

```bash
openspec workset create [name] [--member <path> | --member <name>=<path>]... [--tool <id>] [--json]
openspec workset list [--json]
openspec workset open <name> [--tool <id>]
openspec workset remove <name> [--yes] [--json]
```

`create` запускает короткий управляемый поток (или принимает флаги `--member` в неинтерактивном режиме; первый член является основным — с него начинаются сеансы). `open` запускает выбранный инструмент: редакторы (VS Code, Cursor) открывают окно с каждым участником и возвращаются; Агенты CLI (Claude Code, кодекс) берут на себя управление этим терминалом как сеанс, к которому подключены все участники, без предварительного заполнения приглашений и завершается при выходе. Папка участника, отсутствующая во время открытия, пропускается с примечанием; остальное открывается. Сохраненные настройки инструмента можно изменить при каждом открытии с помощью `--tool`.

Поддержка нового инструмента — это конфигурация, а не код. Каждый инструмент имеет один из двух стилей запуска — `workspace-file` (запускается с помощью сгенерированного `.code-workspace`) или `attach-dirs` (один флаг подключения для каждого элемента) — а ключ `openers` в глобальном `config.json` (открывается с помощью `openspec config edit`) добавляет инструменты или настраивает встроенные модули для каждого поля:

```json
{
  "openers": {
    "zed": { "style": "workspace-file" },
    "claude": { "attach_flag": "--dir" }
  }
}
```

все состояние рабочего набора находится в папке `worksets/` глобального каталога данных (сохраненные представления плюс сгенерированные файлы `<name>.code-workspace`, восстанавливаемые при каждом открытии); удаление этой папки удаляет все следы.

<a id="validation-commands"></a>
## Команды проверки

### `openspec validate`

проверьте изменения и спецификации на наличие структурных проблем, а также сверьте требования MODIFIED изменения с основными спецификациями, которые они заменят.

```
openspec validate [item-name] [options]
```

изменение с нулевыми изменениями спецификации не проходит проверку, если его `.openspec.yaml` не объявляет `skip_specs: true` (для чистых рефакторингов, инструментов или документации — см. [Рецепт 5](examples.md#recipe-5-a-refactor-with-no-behavior-change)).

**Аргументы:**

|Аргумент|Обязательность|Описание|
|----------|----------|-------------|
|`item-name`|Нет|конкретный элемент для проверки (запрашивается, если опущено).|

**Параметры:**

|Опция|Описание|
|--------|-------------|
|`--all`|проверьте все изменения и спецификации.|
|`--changes`|проверить все изменения.|
|`--specs`|проверьте все спецификации.|
|`--archived`|убедитесь, что в архивных изменениях все задачи выполнены (для анализа перед фиксацией).|
|`--type <type>`|укажите тип, если имя неоднозначно: `change` или `spec`.|
|`--strict`|включить режим строгой проверки.|
|`--json`|вывод как JSON.|
|`--concurrency <n>`|Максимальное количество параллельных проверок (по умолчанию: 6 или окружение `OPENSPEC_CONCURRENCY`).|
|`--no-interactive`|отключить подсказки.|

`--archived` — это его собственная область действия: он не проверяет изменения спецификаций (уже примененные во время архивирования), он проверяет, что для каждого изменения в `changes/archive/` отмечены все флажки `tasks.md`, выход не равен нулю, если какие-либо из них не отмечены. Это улавливает изменения, которые были заархивированы вместе с незавершенной работой, что удобно при использовании перехватчика перед фиксацией.

**Примеры:**

```bash
# Интерактивная проверка
openspec validate

# проверка конкретного изменения.
openspec validate add-dark-mode

# проверить все изменения.
openspec validate --changes

# проверьте все с помощью вывода JSON (для CI/скриптов).
openspec validate --all --json

# строгая проверка с повышенным параллелизмом.
openspec validate --all --strict --concurrency 12

# ошибка, если какое-либо архивированное изменение все еще содержит непроверенные задачи.
openspec validate --archived
```

**Вывод (текст):**

```
Validating add-dark-mode...
  ✓ proposal.md valid
  ✓ specs/ui/spec.md valid
  ⚠ design.md: missing "Technical Approach" section

1 warning found
```

**Вывод (JSON):**

```json
{
  "version": "1.0.0",
  "results": {
    "changes": [
      {
        "name": "add-dark-mode",
        "valid": true,
        "warnings": ["design.md: missing 'Technical Approach' section"]
      }
    ]
  },
  "summary": {
    "total": 1,
    "valid": 1,
    "invalid": 0
  }
}
```

<a id="lifecycle-commands"></a>
## Команды жизненного цикла

### `openspec archive`

заархивируйте завершенное изменение и объедините дельта-спецификации с основными.

```
openspec archive [change-name] [options]
```

**Аргументы:**

|Аргумент|Обязательность|Описание|
|----------|----------|-------------|
|`change-name`|Нет|перейти в архив (запрашивается, если опущено; требуется, если на запрос ничего не ответить)|

**Параметры:**

|Опция|Описание|
|--------|-------------|
|`-y, --yes`|пропустить запросы на подтверждение. Требуется, когда ничто не может ответить на них — агент AI, задание CI или любой запуск с закрытым стандартным вводом.|
|`--skip-specs`|пропускать обновления спецификаций для одного запуска архива. Изменение, которое постоянно не имеет изменений в спецификациях, вместо этого должно объявить `skip_specs: true` в своем `.openspec.yaml` — оно архивируется без флага.|
|`--no-validate`|пропустить проверку (требуется подтверждение). Также отключает прекращение использования возможностей — без вердикта валидатора ничего не удаляется.|

**Примеры:**

```bash
# Интерактивный архив (спрашивает, какие изменения, затем подтверждает)
openspec archive

# изменение, касающееся архива.
openspec archive add-dark-mode

# Архив без подсказок (агенты, CI, скрипты)
openspec archive add-dark-mode --yes

# заархивируйте изменения инструмента, которые не влияют на характеристики.
openspec archive update-ci-config --skip-specs
```

**Упразднение возможности:** Добавьте маркер прекращения использования в метаданные изменения:

```yaml
# openspec/changes/retire-legacy/.openspec.yaml
schema: spec-driven
retire_capabilities: true
```

Затем заархивируйте изменения обычным способом:

```bash
openspec archive retire-legacy --yes
```

**Сохраняйте свои собственные метаданные:** ключ верхнего уровня, начинающийся с маленькой буквы `x-`
, принадлежит вам. OpenSpec никогда не читает, не записывает и не сообщает
об этом, поэтому `openspec validate --strict` остается зеленым при изменении, несущем данные, специфичные для инструмента:

```yaml
# openspec/changes/add-dark-mode/.openspec.yaml
schema: spec-driven
x-tracker: SB-5497
x-jiraKey: ABC-1
```

Имя после префикса вы можете выбрать в любом регистре и написании,
если оно не пустое и не содержит пробелов. Два ограничения: сам
префикс написан строчными буквами, поэтому `X-Tracker` по-прежнему сообщается, а расширения — только
верхнего уровня — ключ внутри `initiative:` отклоняется, как бы он ни
назывался. Любой другой нераспознанный ключ верхнего уровня по-прежнему считается не имеющим эффекта.

Когда изменение удаляет последнее требование возможности, OpenSpec удаляет свой
действующий `spec.md` . Другие изменения возможностей в том же
изменении по-прежнему обновляют свои основные спецификации. Без маркера архив
останавливается перед изменением каких-либо файлов и предлагает вам добавить их.

**Что он делает:**

1. подтверждает изменение (кроме `--no-validate`).
2. запрашивает подтверждение (кроме `--yes`).
3. запрашивает место назначения архива перед изменением какой-либо основной спецификации.
4. проверяет и объединяет активные дельта-спецификации в `openspec/specs/` — возможность, последнее требование которой удаляет изменение, удаляется, а файл спецификации удаляется, но только тогда, когда `.openspec.yaml` изменения объявляет `retire_capabilities: true` рядом со своим `schema:`.
5. перемещает папку изменений в `openspec/changes/archive/YYYY-MM-DD-<name>/`.
6. если мутация спецификации или окончательное перемещение завершаются неудачей до того, как весь архив будет защищен, спецификации восстанавливаются и оставляются или возвращаются изменения по активному пути.
7. если проверенная резервная копия завершается, но очистка промежуточного исходного кода завершается неудачно, сохраняется полный архив и состояние зафиксированной спецификации для восстановления.

**Без терминала**: агент AI, задание CI или любой запуск с закрытым стандартным вводом
не может ответить на шаг 2, поэтому архив останавливается, прежде чем что-либо коснуться, завершает
работу 1 и называет команду для повторного запуска — `openspec archive <name> --yes` , неся любые
другие переданные вами флаги. Передайте `--yes` (и имя изменения) заранее, чтобы пропустить обратный путь.

<a id="workflow-commands"></a>
## Команды рабочего процесса

эти команды поддерживают рабочий процесс OPSX, управляемый артефактами. Они полезны как для людей, проверяющих прогресс, так и для агентов, определяющих следующие шаги.

### `openspec new change`

создайте каталог изменений и дополнительные возвращенные метаданные в разрешенном корне OpenSpec.

```bash
openspec new change <name> [options]
```

Имена изменений должны использовать строчные буквы «кебаб»: строчные буквы,
цифры и одиночные дефисы. Они не могут содержать пробелы, символы
подчеркивания, прописные буквы, последовательные дефисы, а также начальные/конечные дефисы.
Допускается начальное число, поэтому вы можете добавлять префикс к имени
для изменения порядка или уровня, например `100-add-feature` или `00001-add-auth` .

**Параметры:**

|Опция|Описание|
|--------|-------------|
|`--description <text>`|описание, которое нужно добавить в `README.md`.|
|`--goal <text>`|дополнительные метаданные цели, которые нужно сохранить вместе с изменением.|
|`--schema <name>`|используемая схема рабочего процесса.|
|`--store <id>`|идентификатор хранилища, который будет использоваться в качестве корня OpenSpec (хранилище — это зарегистрированный вами автономный репозиторий OpenSpec)|
|`--json`|Выход JSON|

Примеры:

```bash
openspec new change add-billing-api
openspec new change add-billing-api --store team-context --json
```

### `openspec status`

отображение статуса завершения артефакта для изменения.

```
openspec status [options]
```

**Параметры:**

|Опция|Описание|
|--------|-------------|
|`--change <id>`|Изменить имя (запрашивается, если опущено)|
|`--schema <name>`|переопределение схемы (автоматически определяется из конфигурации изменения)|
|`--json`|вывод как JSON.|

**Примеры:**

```bash
# Интерактивная проверка статуса.
openspec status

# Статус конкретного изменения.
openspec status --change add-dark-mode

# JSON для использования агентом.
openspec status --change add-dark-mode --json
```

**Вывод (текст):**

```
Change: add-dark-mode
Schema: spec-driven
Progress: 2/4 artifacts complete

[x] proposal
[x] specs
[ ] design
[-] tasks (blocked by: design)
```

[Русское пояснение подписей и сообщений](../EXAMPLE_NOTES.md#example-035).


изменение, объявляющее `skip_specs: true`, показывает его стадию спецификации как `[~] specs (skipped: change declares skip_specs)` и исключает ее из подсчета прогресса.

**Вывод (JSON):**

```json
{
  "changeName": "add-dark-mode",
  "schemaName": "spec-driven",
  "isPlanningComplete": false,
  "isComplete": false,
  "applyRequires": ["tasks"],
  "artifacts": [
    {"id": "proposal", "outputPath": "proposal.md", "status": "done", "requires": []},
    {"id": "specs", "outputPath": "specs/**/*.md", "status": "done", "requires": ["proposal"]},
    {"id": "design", "outputPath": "design.md", "status": "ready", "requires": ["proposal"]},
    {"id": "tasks", "outputPath": "tasks.md", "status": "blocked", "requires": ["specs", "design"], "missingDeps": ["design"]}
  ]
}
```

`isPlanningComplete` сообщает, существуют ли все непропущенные артефакты планирования;
пропущенные артефакты считаются удовлетворенными, но не были созданы.
Он не сообщает, выполнены ли задачи внедрения. `isComplete`
сохраняется как псевдоним совместимости с тем же значением.

Артефакты перечислены в порядке зависимостей - зависимость никогда не появляется после
чего-то, что требует ее - и артефакты, которые становятся готовыми одновременно
(управляемые спецификацией `specs` и `design` , оба нуждаются только в `proposal` ),
сохраняют порядок, в котором они объявлены схемой, а не в алфавитном
порядке. Итак, первая запись `ready` — это артефакт, который нужно записать следующим.

### `openspec instructions`

получите подробные инструкции по созданию артефакта или применению задач. Используется агентами ИИ, чтобы понять, что создавать дальше.

```
openspec instructions [artifact] [options]
```

**Аргументы:**

|Аргумент|Обязательность|Описание|
|----------|----------|-------------|
|`artifact`|Нет|идентификатор артефакта или поверхность ввода рабочего процесса: `apply` или `archive`.|

**Параметры:**

|Опция|Описание|
|--------|-------------|
|`--change <id>`|изменить имя (обязательно в неинтерактивном режиме)|
|`--schema <name>`|переопределение схемы|
|`--json`|вывод как JSON.|

**Особые случаи:** Используйте `apply` для получения инструкций по реализации задачи. Используйте `archive`
для получения текущих архивных входных данных, доступных только для чтения (`context` и
`operationGuidance` ), для внесения действительных изменений; он ничего не архивирует и не изменяет.

**Примеры:**

```bash
# Получите инструкции для следующего артефакта.
openspec instructions --change add-dark-mode

# получите инструкции по конкретным артефактам.
openspec instructions design --change add-dark-mode

# Получите инструкции по применению/реализации.
openspec instructions apply --change add-dark-mode

# получение текущих входных данных операции архивирования без архивирования.
openspec instructions archive --change add-dark-mode --json

# JSON для потребления агента
openspec instructions design --change add-dark-mode --json
```

**Вывод включает в себя:**

- содержимое шаблона для артефакта.
- контекст проекта из конфигурации.
- контент из артефактов зависимостей.
- правила для каждого артефакта из конфигурации.
- Текущий контекст проекта и руководство по сопоставлению для `apply`/`archive`.

входные данные операции считываются из разрешенного репозитория или выбранного хранилища
при каждом вызове. Контекст проекта — это обязательный ввод на
уровне подсказки: агенты читают его и применяют соответствующие факты, соглашения и
ограничения проекта. Руководство по эксплуатации является дополнительным дополнительным советом: агенты
учитывают каждую запись и следуют только записям, которые применимы и совместимы
со встроенным рабочим процессом. Оба поля остаются отделенными от явного
выбора пользователя, состояния, контролируемого CLI, встроенных инструкций и правил артефактов. Сообщается
о противоречивом контексте; противоречивые или неприменимые рекомендации не выполняются, а
причина объясняется. Это поведенческие контракты для сгенерированных агентов, а не принудительно
выполняемые проверки CLI. `instructions archive` возвращает только выбранное изменение, дополнительные входные
данные и корневые метаданные; он не включает рабочий процесс статического архивирования.

для артефакта, пропущенного через `skip_specs: true`, выводятся только предупреждения (JSON добавляет поля `skipped`/`warning`) — артефакт не должен создаваться.

<a id="configuration-commands"></a>
## Команды настройки

### `openspec config`

просмотр и изменение глобальной конфигурации OpenSpec.

```
openspec config <subcommand> [options]
```

**Подкоманды:**

|Подкоманда|Описание|
|------------|-------------|
|`path`|показать расположение файла конфигурации.|
|`list`|Показать все текущие настройки.|
|`get <key>`|получить конкретное значение.|
|`set <key> <value>`|Установите значение.|
|`unset <key>`|удалить ключ.|
|`reset`|Сброс к настройкам по умолчанию.|
|`edit`|Открыть в `$EDITOR`.|
|`profile [preset]`|настройка профиля рабочего процесса в интерактивном режиме или с помощью предустановок.|

**Примеры:**

```bash
# Показать путь к файлу конфигурации.
openspec config path

# список всех настроек.
openspec config list

# получить конкретное значение.
openspec config get telemetry.enabled

# установите значение (отключить анонимную телеметрию использования).
openspec config set telemetry.enabled false

# явно задайте строковое значение.
openspec config set user.name "My Name" --string

# удалить пользовательскую настройку.
openspec config unset user.name

# установка хранилища по умолчанию на уровне компьютера (резервный корень, если нет --store,
# локальный корень или хранилище проектов: указатель разрешается)
openspec config set defaultStore team-plans

# Сбросить всю конфигурацию.
openspec config reset --all --yes

# отредактируйте конфигурацию в своем редакторе.
openspec config edit

# настройка профиля с помощью мастера на основе действий.
openspec config profile

# Быстрая предустановка: переключение рабочих процессов на основной (сохраняет режим доставки).
openspec config profile core
```

**Отказ от телеметрии:** `telemetry.enabled` по умолчанию включен, если не настроен (модель с отказом
от участия). Установите значение `false` , чтобы отключить анонимную статистику использования и проверку
версии `openspec update` . Переменные среды имеют приоритет над конфигурацией: `OPENSPEC_TELEMETRY=0` , `DO_NOT_TRACK=1` и
истинное значение `CI` (например, `true` /`1`/`yes`) всегда отключают телеметрию независимо от значения конфигурации.

`openspec config profile` начинается со сводки текущего состояния, затем позволяет выбрать:
- изменение формы установки и рабочих процессов.
- изменить только форму установки
- изменение только рабочих процессов
- сохранить текущие настройки (выход)

Если вы сохраните текущие настройки, никакие изменения не запишутся и не появится запрос на обновление. Если изменений конфигурации нет, но текущие
файлы проекта не синхронизированы с вашим глобальным профилем/формой установки, OpenSpec выдаст предупреждение и предложит `openspec update` . Нажатие `Ctrl+C` также полностью отменяет поток
(без трассировки стека) и завершает работу с кодом `130` . В контрольном списке рабочего процесса `[x]` означает, что рабочий процесс выбран
в глобальной конфигурации. Чтобы применить эти настройки к файлам проекта, запустите `openspec update` (или выберите `Apply changes to this project now?` при появлении соответствующего запроса внутри проекта).

**Интерактивные примеры:**

```bash
# обновление только для доставки.
openspec config profile
# выберите: Изменить только доставку
# выберите доставку: только навыки

# обновление только для рабочих процессов.
openspec config profile
# выберите: Изменить только рабочие процессы.
# переключите рабочие процессы в контрольном списке, затем подтвердите.
```

### `openspec feedback`

Отправьте отзыв о OpenSpec. Создает проблему GitHub.

### `openspec completion`

Управление завершением оболочки для OpenSpec CLI.

```
openspec completion <subcommand> [shell]
```

**Подкоманды:**

|Подкоманда|Описание|
|------------|-------------|
|`generate [shell]`|сценарий завершения вывода на стандартный вывод|
|`install [shell]`|завершение установки вашей оболочки.|
|`uninstall [shell]`|Удалить установленные дополнения.|

**Поддерживаемые оболочки:** `bash`, `zsh`, `fish`, `powershell`

**Примеры:**

```bash
# завершение установки (оболочка обнаруживается автоматически)
openspec completion install

# установка для конкретной оболочки.
openspec completion install zsh

# создать сценарий для ручной установки (bash).
openspec completion generate bash > ~/.bash_completion.d/openspec

# Удалить
openspec completion uninstall
```

**Windows (PowerShell):** Завершения установки для текущего хоста PowerShell:

```powershell
$env:PROFILE = $PROFILE
openspec completion install powershell
. $PROFILE
```

`$env:PROFILE` сообщает OpenSpec, какой профиль настроить в этом сеансе.
Установщик создает недостающие каталоги профилей и добавляет управляемый блок,
загружающий `OpenSpecCompletion.ps1` . Перезагрузка профиля позволяет немедленно выполнить завершение.

Чтобы удалить с текущего хоста, запустите:

```powershell
$env:PROFILE = $PROFILE
openspec completion uninstall powershell
```

перезапустите PowerShell после удаления, чтобы удалить завершения текущего сеанса.

Доработки по желанию. CLI упоминает их один раз в
stderr, когда вы впервые запускаете команду в интерактивном терминале, и
никогда больше — он также остается тихим, если у вас
уже установлены дополнения. Установите `OPENSPEC_NO_COMPLETIONS=1` для полного подавления этой подсказки.

<a id="environment-variables"></a>
## Переменные среды

|переменная|Описание|
|----------|-------------|
|`OPENSPEC_TELEMETRY`|установите значение `0`, чтобы отключить телеметрию и проверку версии `openspec update` (переопределяет `telemetry.enabled` в глобальной конфигурации).|
|`DO_NOT_TRACK`|установите значение `1`, чтобы отключить телеметрию и проверку версии `openspec update` (стандартный сигнал DNT; переопределяет конфигурацию).|
|`OPENSPEC_CONCURRENCY`|параллелизм по умолчанию для массовой проверки (по умолчанию: 6).|
|`EDITOR` или `VISUAL`|Редактор для `openspec config edit`.|
|`NO_COLOR`|отключить цветной вывод, если установлено.|
|`OPENSPEC_NO_ANIMATION`|отключить анимацию приветствия `openspec init`, если она установлена.|
|`OPENSPEC_NO_COMPLETIONS`|установите значение `1`, чтобы отключить одноразовую подсказку о завершении оболочки.|
|`OPENSPEC_NO_UPDATE_CHECK`|отключить проверку `openspec update` на наличие более нового опубликованного CLI, если оно установлено (любое значение, включая пустое). Также пропускается, если установлен `CI` (кроме `false`/`0`/`no`/`off`) или `NODE_ENV=test`.|
|`npm_config_registry`|Зарегистрируйтесь, запрашивается проверка версии `openspec update`. Должен быть URL-адрес `http(s)`, иначе он вернется к `https://registry.npmjs.org`. Файл `.npmrc` не читается|
