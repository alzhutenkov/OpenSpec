<a id="openspec-on-a-team"></a>
# OpenSpec в команде

В других руководствах все работает одинаково, независимо от того, играете ли вы в одиночку или в команде из двадцати человек. Что меняется в команде, так это вопросы по краям: где хранятся спецификации, как товарищи по команде проверяют план и как все это соответствует уже имеющемуся потоку запросов на включение?

Короткий ответ: изменение — это только файлы, а OpenSpec никогда не касается git. Таким образом, он соответствует вашему существующему рабочему процессу, а не заменяет его. На этой странице описаны соглашения, которые хорошо работают.

<a id="one-rule-openspec-doesnt-touch-git"></a>
## одно правило: OpenSpec не касается git.

OpenSpec читает и записывает обычный Markdown под `openspec/`. Он никогда не фиксирует, не разветвляет, не отправляет и не извлекает ваш проект, а также никогда не клонирует и не синхронизирует [хранилище](stores-beta/user-guide.md) самостоятельно. Это означает:

- **Вы фиксируете `openspec/`, как и любой другой источник.** Спецификации, активные изменения и архив являются частью истории вашего проекта. (Да, зафиксировать всю папку — см. [FAQ](faq.md#should-i-commit-the-openspec-folder-to-git).)
- **Изменение — это папка, в которой вы создаете версию кода.** `openspec/changes/add-dark-mode/` — это просто файлы в ветке.
- **Все, что указано ниже, является соглашением, а не принуждением.** OpenSpec не будет заставлять вас делать это таким образом; он просто идеально подходит.

<a id="the-everyday-loop"></a>
## Повседневный цикл

Хорошо работающий рабочий процесс сопоставляет изменение с веткой и запросом на включение:

```
git switch -c add-dark-mode        start a branch, as usual
   │
/opsx:propose add-dark-mode        draft the plan (proposal + specs + tasks)
   │
REVIEW THE PLAN                    you read it before any code — see Reviewing a Change
   │
/opsx:apply                        build it; artifacts + code change together
   │
git commit && open a PR            the PR contains the spec delta AND the code
   │
teammate reviews, merges
   │
/opsx:archive                      fold the delta into specs/, move the change to archive/
```

[Русское пояснение подписей и сообщений](../EXAMPLE_NOTES.md#example-061).


План и код живут бок о бок в одной ветке, поэтому ваши товарищи по команде просматривают их вместе, и шесть месяцев спустя заархивированная спецификация все еще объясняет, почему код выглядит именно так.

<a id="reviewing-specs-in-a-pull-request"></a>
## просмотр спецификаций в запросе на включение

Именно здесь команда чувствует отдачу. Когда PR включает в себя дельта-спецификацию изменения, рецензент получает то, что никогда не дает ему необработанный дифф: **ясное изложение того, что должно делать это изменение**, прежде чем он прочитает хотя бы одну строку кода.

Хороший порядок обзора для рецензента:

1. **Читайте `proposal.md`** — это правильная проблема и масштаб?
2. **Прочитайте дельту под `specs/`** — правильно ли определено слово «готово»? (Это двухминутный пропуск [Просмотр изменения](reviewing-changes.md), который сейчас происходит в PR.)
3. **Затем прочитайте разницу кода** — соответствует ли он именно этим требованиям?

Рецензент, который не согласен с *подходом*, может высказать свое мнение против этого предложения, задешево, вместо того, чтобы заново обсуждать его в 300 строках кода. Разместите дельта-спецификацию в верхней части описания PR или укажите рецензентам на папку изменений, чтобы они начали оттуда.

<a id="when-to-archive"></a>
## Когда архивировать

Архивирование складывает изменения изменений в ваш основной `openspec/specs/` и перемещает папку изменений в `openspec/changes/archive/YYYY-MM-DD-<name>/`. Поскольку `specs/` — это **общий источник истины**, в команде время имеет значение. Два работоспособных соглашения:

- **Архивировать после слияния PR (рекомендуется).** Ветка содержит активное изменение; как только он будет объединен с вашей основной веткой, заархивируйте его (часто это небольшая последующая фиксация или запланированная очистка). Благодаря этому общий `specs/` будет продвигаться вперед только с уже выполненной работой.
- **Архив внутри PR.** Упрощено для небольших команд: тот же PR, который добавляет код, также синхронизирует и архивирует. Компромисс заключается в том, что ваш дифференциал `specs/` и ваш дифференциал кода совпадают, что может сделать PR более шумным.

Выберите один и будьте последовательны. В любом случае `/opsx:archive` проверяет выполнение задач и предлагает сначала синхронизироваться, чтобы случайно ничего не слилось наполовину незавершенным.

<a id="two-people-parallel-changes"></a>
## Два человека, параллельные изменения

Поскольку изменения находятся в отдельных папках, они не конфликтуют:

- **Разные изменения, разные люди — без проблем.** `add-dark-mode` и `rate-limit-login` — это разные папки в разных ветках; они никогда не касаются друг друга, пока оба не архивируются.
- **Одно изменение, один владелец.** Два человека, редактирующие одну и ту же папку изменений, конфликтуют точно так же, как два человека, редактирующие один и тот же файл. Оставьте изменение одному автору или разделите его на два изменения (еще одна причина использовать [правильный размер](writing-specs.md#right-size-the-change)).
- **Конфликты проявляются только в `specs/`.** Если два изменения изменяют *одно и то же* требование, архивирование второго приведет к конфликту в `openspec/specs/…/spec.md` — разрешите его, как любой конфликт слияния, сохраняя требование, отражающее реальность. Это редкость, и это особенность: git сообщает вам, что два изменения не согласны с тем, как должна вести себя система.

<a id="when-planning-outgrows-one-repo"></a>
## Когда планирование перерастает одно репо

Все вышеизложенное предполагает, что план находится в собственной папке `openspec/` репозитория кода, которая является правильной по умолчанию. Когда ваше планирование действительно охватывает несколько репозиториев или групп — одна функция затрагивает три службы или требования, которыми владеет одна команда и потребляют другие — именно для этого и нужна бета-функция **stores**: планирование получает собственное репозиторий, на который может указать любой репозиторий кода. Начните с [Руководства пользователя хранилищ](stores-beta/user-guide.md).
