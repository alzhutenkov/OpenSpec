# Рабочий процесс OPSX

> Приветствуются отзывы в [Discord (английский)](https://discord.gg/YctCnvvshC).

<a id="what-is-it"></a>
## Что это такое?

OPSX теперь является стандартным рабочим процессом для OpenSpec.

Это **гибкий, итеративный рабочий процесс** для изменений OpenSpec. Больше никаких жестких этапов — просто действия, которые вы можете предпринять в любое время.

<a id="why-this-exists"></a>
## Почему это существует

Устаревший рабочий процесс OpenSpec работает, но он **заблокирован**:

- **Инструкции жестко запрограммированы** — спрятаны в TypeScript, их нельзя изменить.
- **Все или ничего** — одна большая команда создает все, не может тестировать отдельные части.
- **Фиксированная структура** — один и тот же рабочий процесс для всех, без настройки.
- **Черный ящик** — если результаты ИИ плохие, вы не можете настроить подсказки.

**OPSX открывает его.** Теперь любой может:

1. **Поэкспериментируйте с инструкциями** — отредактируйте шаблон и посмотрите, сработает ли ИИ лучше.
2. **Детальное тестирование** — проверяйте инструкции каждого артефакта независимо.
3. **Настройте рабочие процессы** — определите свои собственные артефакты и зависимости.
4. **Быстрая итерация** — измените шаблон, немедленно протестируйте, без перестройки.

```
Legacy workflow:                      OPSX:
┌────────────────────────┐           ┌────────────────────────┐
│  жестко закодировано в пакете │ │ schema.yaml │◄── Вы редактируете это
│  (невозможно изменить) │ │ templates/*.md │◄── Или это
│        ↓               │           │        ↓               │
│  Wait for new release  │           │  Instant effect        │
│        ↓               │           │        ↓               │
│  Hope it's better      │           │  Test it yourself      │
└────────────────────────┘           └────────────────────────┘
```

**Это для всех:**
- **Команды** — создавайте рабочие процессы, соответствующие вашей реальной работе.
- **Опытные пользователи** — настройте подсказки, чтобы улучшить результаты ИИ для вашей кодовой базы.
- **Соавторы OpenSpec** — экспериментируйте с новыми подходами без релизов.

Мы все еще учимся тому, что работает лучше всего. OPSX позволяет нам учиться вместе.

<a id="the-user-experience"></a>
## Пользовательский опыт

**Проблема с линейными рабочими процессами:** Вы находитесь «на этапе планирования», затем «на этапе реализации», а затем «готово». Но настоящая работа работает не так. Вы
что-то реализуете, понимаете, что ваш дизайн был неправильным, вам нужно обновить спецификации и продолжить реализацию. Линейные фазы противоречат тому, как на самом деле происходит работа.

**Подход OPSX:**
- **Действия, а не этапы** — создавать, внедрять, обновлять, архивировать — выполнять любое из них в любое время.
- **Зависимости являются движущей силой** — они показывают, что возможно, а не то, что требуется дальше.

```
  proposal ──→ specs ──→ design ──→ tasks ──→ implement
```

<a id="setup"></a>
## Настройка

```bash
# Убедитесь, что у вас установлена openspec — навыки генерируются автоматически.
openspec init
```

Это создает навыки в `.claude/skills/` (или его эквиваленте), которые помощники по кодированию AI автоматически обнаруживают.

по умолчанию OpenSpec использует профиль рабочего процесса `core` (`propose`, `explore`, `apply`, `update`, `sync`, `archive`). Если вам нужны расширенные команды рабочего процесса (`new`, `continue`, `ff`, `verify`, `bulk-archive`, `onboard`), настройте их с помощью `openspec config profile` и примените с помощью `openspec update`.

Во время установки вам будет предложено создать **конфигурацию проекта** (`openspec/config.yaml`). Это необязательно, но рекомендуется.

<a id="project-configuration"></a>
## Конфигурация проекта

Конфигурация проекта позволяет вам устанавливать значения по умолчанию и внедрять контекст, специфичный для проекта, во все артефакты.

<a id="creating-config"></a>
### Создание конфигурации

Конфигурация создается во время `openspec init` или вручную:

```yaml
# openspec/config.yaml
schema: spec-driven

context: |
  Tech stack: TypeScript, React, Node.js
  API conventions: RESTful, JSON responses
  Testing: Vitest for unit tests, Playwright for e2e
  Style: ESLint with Prettier, strict TypeScript

rules:
  proposal:
    - включить план отката.
    - Определите затронутые команды.
  specs:
    - использовать формат «Дано/Когда/То» для сценариев.
  design:
    - включить диаграммы последовательности для сложных потоков.
```

<a id="config-fields"></a>
### Поля конфигурации

|Поле|Тип|Описание|
|-------|------|-------------|
|`schema`|строка|схема по умолчанию для новых изменений (например, `spec-driven`).|
|`context`|строка|контекст проекта внедряется во все инструкции артефакта.|
|`rules`|объект|правила для каждого артефакта, определяемые идентификатором артефакта.|

<a id="how-it-works"></a>
### Как это работает

**Приоритет схемы** (от самого высокого к самому низкому):
1. флаг CLI (`--schema <name>`)
2. изменить метаданные (`.openspec.yaml` в каталоге изменений)
3. Конфигурация проекта (`openspec/config.yaml`)
4. по умолчанию (`spec-driven`)

**Внедрение контекста:**
- Контекст добавляется к инструкциям каждого артефакта.
- заключен в теги `<context>...</context>`.
- помогает ИИ понять правила вашего проекта.

**Внедрение правил:**
- правила внедряются только для сопоставления артефактов.
- заключен в теги `<rules>...</rules>`.
- появляется после контекста, перед шаблоном.

<a id="artifact-ids-by-schema"></a>
### Идентификаторы артефактов по схеме

**на основе спецификации** (по умолчанию):
- `proposal` — Изменить предложение
- `specs` — Технические спецификации
- `design` — Технический проект
- `tasks` — Задачи реализации

<a id="config-validation"></a>
### Проверка конфигурации

- неизвестные идентификаторы артефактов в `rules` выдают предупреждения.
- имена схем проверяются на соответствие доступным схемам.
- размер контекста ограничен 50 КБ.
- сообщается о недопустимом YAML с номерами строк.

<a id="troubleshooting"></a>
### Устранение неполадок

**"Неизвестный идентификатор артефакта в правилах: X"**
- проверьте, соответствуют ли идентификаторы артефактов вашей схеме (см. список выше).
- запустите `openspec schemas --json`, чтобы просмотреть идентификаторы артефактов для каждой схемы.

**Конфигурация не применяется:**
- убедитесь, что файл находится по адресу `openspec/config.yaml` (а не `.yml`).
- проверьте синтаксис YAML с помощью валидатора.
- изменения конфигурации вступают в силу немедленно (перезапуск не требуется).

**Слишком большой контекст:**
- размер контекста ограничен 50 КБ.
- вместо этого суммируйте или ссылайтесь на внешние документы.

<a id="commands"></a>
## Команды

|Команда|Что он делает|
|---------|--------------|
|`/opsx:propose`|создание изменений и создание артефактов планирования за один шаг (быстрый путь по умолчанию).|
|`/opsx:explore`|Продумывайте идеи, исследуйте проблемы, уточняйте требования.|
|`/opsx:new`|Запуск нового шаблона изменений (расширенный рабочий процесс).|
|`/opsx:continue`|создайте следующий артефакт (расширенный рабочий процесс).|
|`/opsx:ff`|артефакты ускоренного планирования (расширенный рабочий процесс)|
|`/opsx:apply`|реализация задач, обновление артефактов по мере необходимости.|
|`/opsx:update`|пересмотреть артефакты планирования изменений и обеспечить их согласованность.|
|`/opsx:verify`|проверка реализации на наличие артефактов (расширенный рабочий процесс).|
|`/opsx:sync`|объединить дельта-спецификации с основными спецификациями (необязательно).|
|`/opsx:archive`|Архивировать по завершении.|
|`/opsx:bulk-archive`|архивирование нескольких выполненных изменений (расширенный рабочий процесс).|
|`/opsx:onboard`|пошаговое руководство по комплексному изменению (расширенный рабочий процесс).|

<a id="usage"></a>
## Использование

<a id="explore-an-idea"></a>
### Изучить идею
```
/opsx:explore
```
Обдумывайте идеи, исследуйте проблемы, сравнивайте варианты. Никакой структуры не требуется – только думающий партнер. Когда понимание выкристаллизуется, перейдите к `/opsx:propose` (по умолчанию) или `/opsx:new`/`/opsx:ff` (расширенный).

<a id="start-a-new-change"></a>
### Начать новое изменение
```
/opsx:propose
```
создает изменение и создает артефакты планирования, необходимые перед реализацией.

Если вы включили расширенные рабочие процессы, вместо этого вы можете использовать:

```text
/opsx:new        # scaffold only
/opsx:continue   # create one artifact at a time
/opsx:ff         # create all planning artifacts at once
```

<a id="create-artifacts"></a>
### Создание артефактов.
```
/opsx:continue
```
показывает, что можно создать на основе зависимостей, затем создает один артефакт. Используйте повторно, чтобы постепенно наращивать изменения.

```
/opsx:ff add-dark-mode
```
создает все артефакты планирования одновременно. Используйте его, когда у вас есть четкое представление о том, что вы строите.

<a id="implement-the-fluid-part"></a>
### Орудие (жидкостная часть)
```
/opsx:apply
```
выполняет задачи, проверяя их по ходу выполнения. Если вы жонглируете несколькими изменениями, вы можете запустить `/opsx:apply <name>`; в противном случае он должен сделать вывод из разговора и предложить вам сделать выбор, если он не может сказать.

<a id="updating-a-change"></a>
### Обновление изменения
```
/opsx:update add-dark-mode - we're storing the theme in a cookie now
```
пересматривает существующие артефакты планирования изменения и сохраняет их согласованность в любом направлении (редактирование дизайна может вернуться к предложению). Он никогда не редактирует код. Каждое редактирование сначала подтверждается вами. См. [ссылку на обновление](commands.md#opsxupdate), чтобы узнать, как он обрабатывает отсутствующие файлы без запуска нового артефакта.

Если изменение уже реализовано, рекомендуется использовать `/opsx:apply`, чтобы код соответствовал пересмотренному плану. Если ваша редакция меняет *намерение* изменения, вместо этого начните заново. См. [Когда обновлять или начинать заново](#when-to-update-vs-start-fresh).

<a id="sync-delta-specs"></a>
### Синхронизация дельта-спецификаций
```text
/opsx:sync
```
объединяет дельта-спецификации текущего изменения с вашим основным `openspec/specs/` без архивирования — изменение остается активным. Он применяет всю дельту: требование `## REMOVED` удаляется из основной спецификации, а переименованное требование получает новое название, а контент, не упомянутый в дельте, остается нетронутым. Синхронизация не является обязательной — сначала архив предложит вам синхронизироваться, если вы этого не сделали. Используйте его, когда вы хотите обновить основные спецификации перед архивированием, когда параллельное изменение должно основываться на только что добавленных спецификациях или когда вы хотите просмотреть объединенную основную спецификацию перед архивированием.

<a id="finish-up"></a>
### Завершить
```
/opsx:archive   # Move to archive when done (prompts to sync specs if needed)
```

<a id="when-to-update-vs-start-fresh"></a>
## Когда обновлять или начинать заново

Вы всегда можете отредактировать свое предложение или спецификации перед реализацией. Но когда переработка станет «это другая работа»?

<a id="what-a-proposal-captures"></a>
### Что отражает предложение

Предложение определяет три вещи:
1. **Намерение** — Какую проблему вы решаете?
2. **Область** — Что находится за пределами границ?
3. **Подход** — Как вы будете решать эту проблему?

Вопрос: что изменилось и насколько?

<a id="update-the-existing-change-when"></a>
### Обновить существующее изменение, если:

**Тот же замысел, улучшенное исполнение**
- вы обнаруживаете крайние случаи, которые не учли.
- подход нуждается в доработке, но цель остается неизменной.
- реализация показывает, что дизайн был немного неправильным.

**Объем сужается**
- Вы понимаете, что полный объем слишком велик, и хотите сначала выпустить MVP.
- «Добавить темный режим» → «Добавить переключатель темного режима (системные настройки в версии 2)»

**Исправления, основанные на обучении**
- Кодовая база структурирована не так, как вы думали.
- зависимость работает не так, как ожидалось.
- «Использовать переменные CSS» → «Вместо этого использовать префикс dark: Tailwind»

<a id="start-a-new-change-when"></a>
### Начать новое изменение, когда:

**Намерение принципиально изменилось**
- Сама проблема теперь другая.
- «Добавить темный режим» → «Добавить комплексную систему тем с настраиваемыми цветами, шрифтами и интервалами»

**Прицел взорван**
- Изменения настолько разрослись, что это по сути другая работа.
- после обновлений исходное предложение станет неузнаваемым.
- «Исправить ошибку входа» → «Переписать систему аутентификации»

**Оригинал можно завершить**
- исходное изменение можно пометить как «выполнено».
- Новая работа — это самостоятельная работа, а не усовершенствование.
- Завершено «Добавить темный режим MVP» → Архив → Новое изменение «Улучшение темного режима»

<a id="the-heuristics"></a>
### Эвристика

```
                        ┌─────────────────────────────────────┐
                        │     Is this the same work?          │
                        └──────────────┬──────────────────────┘
                                       │
                    ┌──────────────────┼──────────────────┐
                    │                  │                  │
                    ▼                  ▼                  ▼
             Same intent?      >50% overlap?      Can original
             Same problem?     Same scope?        be "done" without
                    │                  │          these changes?
                    │                  │                  │
          ┌────────┴────────┐  ┌──────┴──────┐   ┌───────┴───────┐
          │                 │  │             │   │               │
         YES               NO YES           NO  NO              YES
          │                 │  │             │   │               │
          ▼                 ▼  ▼             ▼   ▼               ▼
       UPDATE            NEW  UPDATE       NEW  UPDATE          NEW
```

[Русское пояснение подписей и сообщений](../EXAMPLE_NOTES.md#example-051).


|Тест|Обновление|Новое изменение|
|------|--------|------------|
|**Личность**|«То же самое, только уточненное»|«Другая работа»|
|**Перекрытие областей действия**|перекрытие >50 %.|перекрытие <50 %.|
|**Завершение**|невозможно «сделать» без изменений.|Можно завершить оригинальную работу, новая работа стоит отдельно.|
|**История**|Цепочка обновлений рассказывает последовательную историю.|Патчи скорее запутают, чем прояснят.|

<a id="the-principle"></a>
### Принцип

> **Обновление сохраняет контекст. Новое изменение вносит ясность.**
>
> Выбирайте обновление, если история ваших мыслей имеет ценность.
> Выбор нового при запуске заново будет более понятным, чем установка исправлений.

Думайте об этом как о ветках git:
- продолжайте работать над той же функцией.
- запускайте новую ветку, когда это действительно новая работа.
- иногда объединяйте частичный объект и начинайте заново для этапа 2.

<a id="whats-different"></a>
## В чем разница?

| |Наследие (`/openspec:proposal`)|OPSX (`/opsx:*`)|
|---|---|---|
|**Структура**|Один большой документ с предложением.|дискретные артефакты с зависимостями.|
|**Рабочий процесс**|Линейные фазы: план → реализация → архив.|Гибкие действия — делайте что угодно в любое время.|
|**Итерация**|Неудобно возвращаться.|обновляйте артефакты по мере обучения.|
|**Кастомизация**|фиксированная структура.|управляемый схемой (определите свои собственные артефакты)|

**Ключевая мысль:** работа не является линейной. OPSX перестает притворяться.

<a id="architecture-deep-dive"></a>
## Подробный обзор архитектуры

В этом разделе объясняется, как OPSX работает изнутри и как он соотносится с устаревшим рабочим процессом. В примерах этого раздела
используется расширенный набор команд (`new`, `continue` и т. д.); Пользователи `core` по умолчанию могут сопоставить тот же поток с `propose → apply → sync → archive` .

<a id="philosophy-phases-vs-actions"></a>
### Философия: этапы против действий

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         LEGACY WORKFLOW                                      │
│                    (Phase-Locked, All-or-Nothing)                           │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   ┌──────────────┐      ┌──────────────┐      ┌──────────────┐             │
│   │ ПЛАНИРОВАНИЕ │ ───► │ ВНЕДРЕНИЕ │ ───► │ АРХИВИРОВАНИЕ │ │
│   │    PHASE     │      │    PHASE     │      │    PHASE     │             │
│   └──────────────┘      └──────────────┘      └──────────────┘             │
│         │                     │                     │                       │
│         ▼                     ▼                     ▼                       │
│   /openspec:proposal   /openspec:apply      /openspec:archive              │
│                                                                             │
│   • Creates ALL artifacts at once                                          │
│   • Can't go back to update specs during implementation                    │
│   • Phase gates enforce linear progression                                  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘


┌─────────────────────────────────────────────────────────────────────────────┐
│                            OPSX WORKFLOW                                     │
│                      (Fluid Actions, Iterative)                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│              ┌────────────────────────────────────────────┐                 │
│              │           ACTIONS (not phases)             │                 │
│              │                                            │                 │
│              │ новое ◄──► продолжить ◄──► применить ◄──► архивировать │ │
│              │    │          │           │           │    │                 │
│              │    └──────────┴───────────┴───────────┘    │                 │
│              │              any order                     │                 │
│              └────────────────────────────────────────────┘                 │
│                                                                             │
│   • Create artifacts one at a time OR fast-forward                         │
│   • Update specs/design/tasks during implementation                        │
│   • Dependencies enable progress, phases don't exist                       │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

<a id="dependency-graph-model"></a>
### Модель графа зависимостей

Артефакты образуют ориентированный ациклический граф (DAG). Зависимости — это **возможности**, а не ворота:

```
                              proposal
                             (root node)
                                  │
                    ┌─────────────┴─────────────┐
                    │                           │
                    ▼                           ▼
                 specs                       design
              (requires:                  (requires:
               proposal)                   proposal)
                    │                           │
                    └─────────────┬─────────────┘
                                  │
                                  ▼
                               tasks
                           (requires:
                           specs, design)
                                  │
                                  ▼
                          ┌──────────────┐
                          │ APPLY PHASE  │
                          │ (requires:   │
                          │  tasks)      │
                          └──────────────┘
```

**Переходы состояний:**

```
   BLOCKED ────────────────► READY ────────────────► DONE
      │                        │                       │
   Missing                  All deps               File exists
   dependencies             are DONE               on filesystem
```

<a id="iteration-model"></a>
### Итерационная модель

**Устаревший рабочий процесс** — неудобно повторять:

```
  ┌─────────┐     ┌─────────┐     ┌─────────┐
  │/proposal│ ──► │ /apply  │ ──► │/архив │
  └─────────┘     └─────────┘     └─────────┘
       │               │
       │               ├── «Подожди, дизайн неправильный»
       │               │
       │               ├── Опции:
       │               │   • Edit files manually (breaks context)
       │               │   • Abandon and start over
       │               │   • Push through and fix later
       │               │
       │               └── Официального механизма возврата нет.
       │
       └── Creates ALL artifacts at once
```

**OPSX** — естественная итерация:

```
  /opsx:new ───► /opsx:continue ───► /opsx:apply ───► /opsx:archive
      │                │                  │
      │                │ ├── «Дизайн неправильный»
      │                │                  │
      │                │                  ▼
      │                │            Just edit design.md
      │                │            and continue!
      │                │                  │
      │                │                  ▼
      │                │         /opsx:apply picks up
      │                │         where you left off
      │                │
      │                └── Создает ОДИН артефакт, показывает, что разблокировано.
      │
      └── Scaffolds change, waits for direction
```

<a id="custom-schemas"></a>
### Пользовательские схемы

Создавайте собственные рабочие процессы с помощью команд управления схемой:

```bash
# создание новой схемы с нуля (интерактивно).
openspec schema init my-workflow

# Или создайте существующую схему в качестве отправной точки.
openspec schema fork spec-driven my-workflow

# проверьте структуру схемы.
openspec schema validate my-workflow

# посмотреть, откуда разрешается схема (полезно для отладки).
openspec schema which my-workflow
```

схемы хранятся в `openspec/schemas/` (локальный для проекта, с контролем версий) или `~/.local/share/openspec/schemas/` (глобальный пользовательский).

**Структура схемы:**
```
openspec/schemas/research-first/
├── schema.yaml
└── templates/
    ├── research.md
    ├── proposal.md
    └── tasks.md
```

**Пример schema.yaml:**
```yaml
name: research-first
artifacts:
  - id: research        # Added before proposal
    generates: research.md
    requires: []

  - id: proposal
    generates: proposal.md
    requires: [research]  # Now depends on research

  - id: tasks
    generates: tasks.md
    requires: [proposal]
```

[Русское пояснение подписей и сообщений](../EXAMPLE_NOTES.md#example-054).


**График зависимостей:**
```
   research ──► proposal ──► tasks
```

<a id="summary"></a>
### Резюме

|Аспект|Наследие|OPSX|
|--------|----------|------|
|**Шаблоны**|жестко закодированный TypeScript|Внешний YAML + Markdown|
|**Зависимости**|Нет (все сразу)|DAG с топологической сортировкой.|
|**Состояние**|Ментальная модель на основе фаз.|существование файловой системы|
|**Кастомизация**|изменить исходный код, перестроить|создать файл schema.yaml.|
|**Итерация**|фазовая синхронизация|Жидкость, редактируйте что угодно.|
|**Поддержка редактора**|Конфигуратор/адаптеры для конкретного инструмента.|Каталог отдельных навыков.|

<a id="schemas"></a>
## Схемы

схемы определяют существующие артефакты и их зависимости. На данный момент доступны:

- **на основе спецификаций** (по умолчанию): предложение → спецификации → дизайн → задачи.

```bash
# список доступных схем.
openspec schemas

# просмотреть все схемы с источниками разрешения.
openspec schema which --all

# интерактивное создание новой схемы.
openspec schema init my-workflow

# Форк существующей схемы для настройки.
openspec schema fork spec-driven my-workflow

# проверьте структуру схемы перед использованием.
openspec schema validate my-workflow
```

<a id="tips"></a>
## Советы

- используйте `/opsx:explore`, чтобы обдумать идею, прежде чем вносить изменения.
- `/opsx:ff`, когда знаешь, чего хочешь, `/opsx:continue`, когда исследуешь
- Во время `/opsx:apply`, если что-то не так — исправьте артефакт, затем продолжайте
- Задачи отслеживают ход выполнения с помощью флажков в `tasks.md`.
- Проверить статус в любое время: `openspec status --change "name"`
