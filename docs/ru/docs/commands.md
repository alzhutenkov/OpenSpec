# Команды

это ссылка на слэш-команды OpenSpec. Эти команды вызываются в интерфейсе чата вашего помощника по кодированию AI (например, Claude Code, Cursor, Devin Desktop).

Сведения о шаблонах рабочих процессов и о том, когда использовать каждую команду, см. в разделе [Рабочие процессы](workflows.md). Информацию о командах CLI см. в [CLI](cli.md).

на этих страницах в качестве канонического имени используется `/opsx:<command>` .
Некоторые инструменты пишут это по-разному — Cursor и GitHub Copilot регистрируют
`/opsx-propose` , Codex использует `$openspec-propose` — поэтому проверьте [Как вызвать](supported-tools.md#how-to-invoke)
для вашего инструмента. Файлы, которые генерирует OpenSpec, уже имеют правильную форму.

## Краткий справочник

<a id="default-quick-path-core-profile"></a>
### Быстрый путь по умолчанию (профиль `core`)

|Команда|Назначение|
|---------|---------|
|`/opsx:propose`|внесите изменения и сгенерируйте артефакты планирования за один шаг.|
|`/opsx:explore`|Продумайте идеи, прежде чем вносить изменения.|
|`/opsx:apply`|Реализация задач из изменения.|
|`/opsx:update`|пересмотреть артефакты планирования изменений и обеспечить их согласованность.|
|`/opsx:sync`|объединить дельта-спецификации с основными спецификациями.|
|`/opsx:archive`|Архивировать завершенное изменение.|

<a id="expanded-workflow-commands-custom-workflow-selection"></a>
### расширенные команды рабочего процесса (выбор пользовательского рабочего процесса)

|Команда|Назначение|
|---------|---------|
|`/opsx:new`|Запуск нового каркаса изменений.|
|`/opsx:continue`|создать следующий артефакт на основе зависимостей.|
|`/opsx:ff`|ускоренная перемотка вперед: создание всех артефактов планирования одновременно.|
|`/opsx:verify`|проверка соответствия реализации артефактам.|
|`/opsx:bulk-archive`|одновременно архивировать несколько изменений.|
|`/opsx:onboard`|пошаговое руководство по всему рабочему процессу.|

глобальный профиль по умолчанию — `core`. Чтобы включить расширенные команды рабочего процесса, запустите `openspec config profile`, выберите рабочие процессы, затем запустите `openspec update` в своем проекте.

## Справочник команд

### `/opsx:propose`

Создайте новое изменение и сгенерируйте артефакты планирования за один шаг. Это команда запуска по умолчанию в профиле `core`.

**Синтаксис:**
```text
/opsx:propose [change-name-or-description]
```

**Аргументы:**
|Аргумент|Обязательность|Описание|
|----------|----------|-------------|
|`change-name-or-description`|Нет|название случая кебаба или описание изменения открытым текстом.|

**Что он делает:**
- Создает `openspec/changes/<change-name>/`.
- генерирует артефакты, необходимые перед реализацией (для `spec-driven`: предложение, спецификации, дизайн, задачи).
- останавливается, когда изменение готово для `/opsx:apply`.

**Пример:**
```text
Вы: /opsx:propose add-dark-mode

AI: Создано openspec/changes/add-dark-mode/
     ✓ Offer.md
     ✓ specs/ui/spec.md
     ✓ design.md
     ✓ Tasks.md
     Готово к внедрению. Запустите /opsx:apply.
```

**Советы:**
- используйте это для самого быстрого сквозного пути.
- Если вам нужен пошаговый контроль артефактов, включите расширенные рабочие процессы и используйте `/opsx:new` + `/opsx:continue`.

### `/opsx:explore`

> **Если вы не уверены, начните здесь.** Explore — это партнер, мыслящий без каких-либо ставок: он читает вашу кодовую базу, сравнивает варианты и превращает нечеткую идею в конкретный план еще до того, как будет написан какой-либо код. Он поставляется в профиле по умолчанию. Полный случай и дополнительные примеры см. в руководстве [Сначала изучить](explore.md).

Продумайте идеи, изучите проблемы и уточните требования, прежде чем вносить изменения.

**Синтаксис:**
```
/opsx:explore [topic]
```

**Аргументы:**
|Аргумент|Обязательность|Описание|
|----------|----------|-------------|
|`topic`|Нет|Что вы хотите изучить или исследовать|

**Что он делает:**
- открывает ознакомительный разговор без необходимости структуры.
- исследует кодовую базу, чтобы ответить на вопросы.
- сравнение вариантов и подходов.
- Создает визуальные диаграммы для прояснения мышления.
- записывает исследование, когда вы спрашиваете или когда вы говорите «да» на его предложение: формирует изменение с помощью `openspec new change` и записывает названные вами артефакты планирования или обновляет артефакты существующих изменений.
- возможен переход на `/opsx:propose` (по умолчанию) или `/opsx:new` (расширенный рабочий процесс), когда выкристаллизовывается понимание.

**Пример:**
```text
Вы: /opsx:explore

AI: Что бы вы хотели изучить?

Вы: Как нам следует обрабатывать аутентификацию в мобильном приложении?

AI: Позвольте мне изучить вашу текущую настройку аутентификации...
     [Analyzes codebase]

     Я вижу, вы используете аутентификацию на основе сеанса для веб-приложения.
     Для мобильных устройств у нас есть три основных варианта:

     1. токены JWT (без сохранения состояния, работают в автономном режиме)
     2. OAuth2 (если вам нужен сторонний вход)
     3. продлить текущие сеансы (проще, но требует подключения).

     На вашем API уже настроен CORS. Какое направление вас интересует?

Вы: Давайте использовать JWT.

AI: Это решение стоит сохранить. Хотите, чтобы я начал изменение под названием
     добавить-jwt-auth? Только папка изменений, больше ничего.

Вы: Да.

AI: Запустил openspec/changes/add-jwt-auth/. Скажи слово и я
     напишите предложение, спецификации и задачи из того, что мы только что разработали.
```

**Советы:**
- используйте, когда требования неясны или вам необходимо провести расследование.
- Он никогда не пишет код и ничего больше не пишет, пока вы не спросите или не скажете «да», когда он предложит.
- подходит для сравнения нескольких подходов перед принятием решения.
- может читать файлы и выполнять поиск в кодовой базе.

### `/opsx:new`

Запустите новый каркас изменений. Создает папку изменений и ждет, пока вы создадите артефакты с помощью `/opsx:continue` или `/opsx:ff`.

эта команда является частью расширенного набора рабочих процессов (не включена в профиль `core` по умолчанию).

**Синтаксис:**
```
/opsx:new [change-name] [--schema <schema-name>]
```

**Аргументы:**
|Аргумент|Обязательность|Описание|
|----------|----------|-------------|
|`change-name`|Нет|имя папки изменений (запрашивается, если не указано).|
|`--schema`|Нет|используемая схема рабочего процесса (по умолчанию: из конфигурации или `spec-driven`).|

**Что он делает:**
- Создает каталог `openspec/changes/<change-name>/`.
- Создает файл метаданных `.openspec.yaml` в папке изменений.
- показывает первый шаблон артефакта, готовый к созданию.
- запрашивает имя и схему изменения, если они не указаны.

**Что он создаёт:**
```
openspec/changes/<change-name>/
└── .openspec.yaml    # Изменить метаданные (схему, дату создания)
```

**Пример:**
```
You: /opsx:new add-dark-mode

AI:  Created openspec/changes/add-dark-mode/
     Schema: spec-driven

     Ready to create: proposal
     Use /opsx:continue to create it, or /opsx:ff to create all artifacts.
```

[Русское пояснение подписей и сообщений](../EXAMPLE_NOTES.md#example-038).


**Советы:**
- используйте описательные имена: `add-feature`, `fix-bug`, `refactor-module`.
- избегайте общих имен, таких как `update`, `changes`, `wip`.
- Схему также можно установить в конфигурации проекта (`openspec/config.yaml`).

### `/opsx:continue`

создайте следующий артефакт в цепочке зависимостей. Создает по одному артефакту за раз для постепенного прогресса.

**Синтаксис:**
```
/opsx:continue [change-name]
```

**Аргументы:**
|Аргумент|Обязательность|Описание|
|----------|----------|-------------|
|`change-name`|Нет|какое изменение продолжить (выводится из контекста, если не указано)|

**Что он делает:**
- запрашивает график зависимостей артефактов.
- показывает, какие артефакты готовы, а какие заблокированы.
- Создает первый готовый артефакт.
- считывает файлы зависимостей для контекста.
- показывает, что становится доступным после создания.

**Пример:**
```
You: /opsx:continue

AI:  Change: add-dark-mode

     Artifact status:
     ✓ proposal    (done)
     ◆ specs       (ready)
     ◆ design      (ready)
     ○ tasks       (blocked - needs: specs, design)

     Creating specs...

     [Reads proposal.md, creates specs based on requirements]

     ✓ Created openspec/changes/add-dark-mode/specs/ui/spec.md

     Now available: design
     Run /opsx:continue to create the next artifact.
```

[Русское пояснение подписей и сообщений](../EXAMPLE_NOTES.md#example-039).


**Советы:**
- используйте, если вы хотите просмотреть каждый артефакт, прежде чем продолжить.
- подходит для сложных изменений, требующих контроля.
- одновременно могут быть готовы несколько артефактов.
- вы можете редактировать созданные артефакты, прежде чем продолжить.

---

### `/opsx:ff`

ускоренная перемотка вперед при создании артефакта. Создает все артефакты планирования одновременно.

**Синтаксис:**
```
/opsx:ff [change-name]
```

**Аргументы:**
|Аргумент|Обязательность|Описание|
|----------|----------|-------------|
|`change-name`|Нет|какое изменение на перемотку вперед (выводится из контекста, если не указано)|

**Что он делает:**
- создает все артефакты в порядке зависимости.
- прогресс отслеживается через список дел.
- останавливается, когда все артефакты `apply-required` завершены.
- считывает каждую зависимость перед созданием следующего артефакта.

**Пример:**
```
You: /opsx:ff add-dark-mode

AI:  Fast-forwarding add-dark-mode...

     ✓ Creating proposal.md
     ✓ Creating specs/ui/spec.md
     ✓ Creating design.md
     ✓ Creating tasks.md

     All planning artifacts complete!
     Ready for implementation. Run /opsx:apply to begin.
```

[Русское пояснение подписей и сообщений](../EXAMPLE_NOTES.md#example-040).


**Советы:**
- используйте, когда у вас есть четкое представление о том, что вы создаете.
- быстрее, чем `/opsx:continue`, для простых изменений.
- впоследствии вы все равно сможете редактировать артефакты.
- подходит для небольших и средних функций.

### `/opsx:apply`

Реализация задач из изменения. Работает со списком задач, пишет код и проверяет элементы.

**Синтаксис:**
```
/opsx:apply [change-name]
```

**Аргументы:**
|Аргумент|Обязательность|Описание|
|----------|----------|-------------|
|`change-name`|Нет|какое изменение реализовать (выводится из контекста, если он не указан)|

**Что он делает:**
- читает `tasks.md` и определяет незавершенные задачи.
- выполняет задачи одну за другой.
- пишет код, создает файлы, запускает тесты по мере необходимости.
- помечает задачи завершенными флажками `[x]`.

**Пример:**
```
You: /opsx:apply

AI:  Implementing add-dark-mode...

     Reading tasks.md:
     - [ ] 1.1 Create ThemeContext
     - [ ] 1.2 Add CSS custom properties
     - [ ] 1.3 Implement localStorage persistence

     Working on 1.1: Create ThemeContext...
     [Creates src/context/ThemeContext.tsx]

     ✓ 1.1 Complete

     Working on 1.2: Add CSS custom properties...
     [Updates src/styles/globals.css]

     ✓ 1.2 Complete
     ...
```

[Русское пояснение подписей и сообщений](../EXAMPLE_NOTES.md#example-041).


**Советы:**
- можно продолжить с того места, где вы остановились, если его прервали.
- используется для параллельных изменений путем указания имени изменения.
- состояние завершения отслеживается в флажках `tasks.md`.

### `/opsx:update`

Пересмотрите существующие артефакты планирования изменений и обеспечьте их согласованность друг с другом. Планирование только артефактов — код никогда не редактируется.

**Синтаксис:**

```text
/opsx:update [change-name]
```

**Аргументы:**

|Аргумент|Обязательность|Описание|
|----------|----------|-------------|
|`change-name`|Нет|какое изменение обновить (выводится из контекста, если не указано)|

**Что он делает:**

- считывает артефакты изменения через `openspec status --change <name> --json`.
- применяет запрошенную вами редакцию или проверяет артефакты на наличие противоречий, если вы их не указали.
- согласовывает другие существующие артефакты в любом направлении (редактирование дизайна может вернуться к предложению).
- подтверждает каждое редактирование перед записью, по одному артефакту за раз.
- Заканчивается рекомендацией следующего шага: `/opsx:continue` (незапущенные артефакты), `/opsx:apply` (перенос пересмотренного плана в код) или `/opsx:archive` (все готово).

**Отсутствуют файлы:**

- для артефакта glob, такого как `specs/**/*.md`, с хотя бы одним существующим файлом, обновление может предложить отсутствующий сопутствующий файл. Он использует инструкции схемы и просит вас подтвердить конкретный путь перед его созданием.
- Артефакты без файлов остаются в `/opsx:continue`. Намеренно пропущенные артефакты остаются нетронутыми.
- Новые файлы должны оставаться в каталоге изменений. Если файл появляется по подтвержденному пути перед созданием, обновление прекращается, а не перезаписывается.

**Пример:**

```text
Вы: /opsx:update add-dark-mode — теперь мы сохраняем тему в файле cookie, а не в localStorage.

AI: Чтение артефактов добавления темного режима...

     Проект ссылается на localStorage в двух местах; задачи 1.3 охватывают
     сохранение локального хранилища; в предложении не упоминается хранилище.

     Предлагаемые изменения:
     1. design.md — замените решение localStorage на хранилище файлов cookie.
     2. Tasks.md — перефразировать задачу 1.3 на сохранение файлов cookie.

     Применить версию 1? (design.md)
```

**Советы:**

- Артефакт без существующих файлов не запускается. Для этого включите `/opsx:continue` или используйте `openspec status` и `openspec instructions`, если этот дополнительный рабочий процесс не установлен.
- Если изменение уже было реализовано, дополните его `/opsx:apply`, чтобы код соответствовал пересмотренному плану.
- Если ваша редакция меняет *намерение* изменения, вместо этого начните заново с новым изменением (см. [Когда обновлять или начинать заново](opsx.md#when-to-update-vs-start-fresh))

### `/opsx:verify`

убедитесь, что реализация соответствует вашим артефактам изменений. Проверяет полноту, правильность и связность.

**Синтаксис:**
```
/opsx:verify [change-name]
```

**Аргументы:**
|Аргумент|Обязательность|Описание|
|----------|----------|-------------|
|`change-name`|Нет|какое изменение необходимо проверить (выводится из контекста, если он не указан)|

**Что он делает:**
- проверяет три аспекта качества реализации.
- ищет в базе кода доказательства реализации.
- сообщает о проблемах, отнесенных к категориям КРИТИЧЕСКИЕ, ПРЕДУПРЕЖДЕНИЯ или ПРЕДЛОЖЕНИЯ.
- не блокирует архив, но выявляет проблемы.

**Проверочные размеры:**

|Размер|Что он проверяет|
|-----------|-------------------|
|**Полнота**|Все задачи выполнены, все требования реализованы, сценарии рассмотрены.|
|**Правильность**|реализация соответствует замыслу спецификации, обработаны крайние случаи.|
|**Связность**|проектные решения отражены в коде, шаблоны согласованы.|

**Пример:**
```
You: /opsx:verify

AI:  Verifying add-dark-mode...

     COMPLETENESS
     ✓ All 8 tasks in tasks.md are checked
     ✓ All requirements in specs have corresponding code
     ⚠ Scenario "System preference detection" has no test coverage

     CORRECTNESS
     ✓ Implementation matches spec intent
     ✓ Edge cases from scenarios are handled
     ✓ Error states match spec definitions

     COHERENCE
     ✓ Design decisions reflected in code structure
     ✓ Naming conventions consistent with design.md
     ⚠ Design mentions "CSS variables" but implementation uses Tailwind classes

     SUMMARY
     ─────────────────────────────
     Critical issues: 0
     Warnings: 2
     Ready to archive: Yes (with warnings)

     Recommendations:
     1. Add test for system preference detection
     2. Update design.md to reflect Tailwind usage, or refactor to use CSS variables
```

[Русское пояснение подписей и сообщений](../EXAMPLE_NOTES.md#example-042).


**Советы:**
- запустить перед архивированием, чтобы заранее обнаружить несоответствия.
- предупреждения не блокируют архив, но указывают на потенциальные проблемы.
- подходит для проверки работы ИИ перед принятием решения.
- может выявить расхождение между артефактами и реализацией.

---

### `/opsx:sync`

**Необязательная команда.** Объединить дельта-спецификации из изменения в основные спецификации. При необходимости Archive предложит выполнить синхронизацию, поэтому обычно вам не нужно запускать ее вручную.

**Синтаксис:**
```
/opsx:sync [change-name]
```

**Аргументы:**
|Аргумент|Обязательность|Описание|
|----------|----------|-------------|
|`change-name`|Нет|какое изменение синхронизировать (выводится из контекста, если он не указан)|

**Что он делает:**
- считывает дельта-спецификации из папки изменений.
- анализирует разделы ADDED/MODIFIED/REMOVED/RENAMED.
- объединяет изменения в основной каталог `openspec/specs/`.
- сохраняет существующий контент, не упомянутый в дельте.
- не архивирует изменение (остается активным).

**Пример:**
```text
Вы: /opsx:sync

AI: Синхронизация дельта-спецификаций дополнительного темного режима...

     Чтение: openspec/changes/add-dark-mode/specs/ui/spec.md
     Цель: openspec/specs/ui/spec.md

     Изменения, которые необходимо применить:
     ✓ ADDED: требования к выбору темы (2 сценария).
     ✓ ADDED: Требование доступности (1 сценарий)

     Объединение...
     ✓ обновлен openspec/specs/ui/spec.md.

     Изменение остается активным. Запустите /opsx:archive, когда будете готовы к завершению.
```

**Когда использовать вручную:**

|сценарий|Использовать синхронизацию?|
|----------|-----------|
|долгосрочное изменение, перед архивированием необходимо внести спецификации в основной файл.|Да|
|Для нескольких параллельных изменений требуются обновленные базовые спецификации.|Да|
|Хотите просмотреть/проверить слияние отдельно|Да|
|Быстрая смена, переход прямо в архив.|Нет (архив справляется с этим)|

**Советы:**
- Синхронизация — это интеллектуальная функция, а не копирование и вставка.
- можно добавлять сценарии к существующим требованиям без дублирования.
- изменение остается активным после синхронизации (не архивируется).
- Большинству пользователей никогда не понадобится вызывать это напрямую — при необходимости заархивируйте подсказки.

---

### `/opsx:archive`

Архивируйте завершенное изменение. Завершает изменение и перемещает его в папку архива.

**Синтаксис:**
```
/opsx:archive [change-name]
```

**Аргументы:**
|Аргумент|Обязательность|Описание|
|----------|----------|-------------|
|`change-name`|Нет|какое изменение в архив (выводится из контекста, если не указано)|

**Что он делает:**
- проверяет статус завершения артефакта.
- проверяет завершение задачи (предупреждает, если задача не завершена).
- предлагает синхронизировать разностные спецификации, если они еще не синхронизированы.
- перемещает папку изменений в `openspec/changes/archive/YYYY-MM-DD-<name>/`.
- сохраняет все артефакты для контрольного журнала.

**Пример:**
```text
Вы: /opsx:archive

AI: Архивирование дополнительного темного режима...

     Статус артефакта:
     ✓ Offer.md существует.
     ✓ спецификации/ существует
     ✓ design.md существует.
     ✓ Tasks.md существует (выполнено 8/8 задач)

     Спецификации Delta: еще не синхронизированы.
     → Синхронизировать сейчас? (рекомендуется)

Вы: Да

AI: ✓ Синхронизированы спецификации с openspec/specs/ui/spec.md.
     ✓ Перенесено в openspec/changes/archive/2025-01-24-add-dark-mode/.

     Изменение успешно заархивировано.
```

**Советы:**
- Архив не блокирует незавершенные задачи, но предупреждает
- спецификации Delta можно синхронизировать во время архивирования или заранее.
- Архивированные изменения сохраняются в истории.
- сначала используйте `/opsx:verify`, чтобы выявить проблемы.

### `/opsx:bulk-archive`

одновременно архивируйте несколько завершенных изменений. Управляет конфликты спецификаций между изменениями.

**Синтаксис:**
```
/opsx:bulk-archive [change-names...]
```

**Аргументы:**
|Аргумент|Обязательность|Описание|
|----------|----------|-------------|
|`change-names`|Нет|Особые изменения в архиве (предлагает выбрать, если не указано)|

**Что он делает:**
- список всех выполненных изменений.
- проверяет каждое изменение перед архивированием.
- обнаруживает конфликты спецификаций между изменениями.
- разрешает конфликты, проверяя, что на самом деле реализовано.
- Архивы в хронологическом порядке.

**Пример:**
```
You: /opsx:bulk-archive

AI:  Found 3 completed changes:
     - add-dark-mode (8/8 tasks complete)
     - fix-login-bug (3/3 tasks complete)
     - update-footer (2/2 tasks complete)

     Checking for spec conflicts...
     ⚠ add-dark-mode and update-footer both touch specs/ui/

     Inspecting codebase to resolve...
     Both changes are implemented. Will merge in chronological order:
     1. add-dark-mode (created Jan 20)
     2. update-footer (created Jan 22)

     Archive all 3 changes?

You: Yes

AI:  ✓ Archived add-dark-mode
     ✓ Archived fix-login-bug
     ✓ Archived update-footer
     Specs merged: add-dark-mode → update-footer
```

[Русское пояснение подписей и сообщений](../EXAMPLE_NOTES.md#example-043).


**Советы:**
- подходит для параллельных рабочих процессов.
- разрешение конфликтов является агентным (проверяется кодовая база).
- Изменения архивируются в порядке создания.
- Запрос перед перезаписью содержимого спецификации.

### `/opsx:onboard`

Сопровождение по полному рабочему процессу OpenSpec. Интерактивное руководство с использованием вашей фактической базы кода.

**Синтаксис:**
```
/opsx:onboard
```

**Что он делает:**
- описывает полный цикл рабочего процесса с повествованием.
- сканирует вашу кодовую базу на предмет реальных возможностей улучшения.
- Создает фактическое изменение с реальными артефактами.
- реализует реальную работу (небольшие, безопасные изменения).
- архивирует выполненные изменения.
- объясняет каждый шаг по мере его выполнения.

**Фазы:**
1. Приветствие и анализ кодовой базы.
2. Поиск возможностей улучшения
3. Создание изменения (`/opsx:new`)
4. Написание предложения
5. Создание спецификаций
6. Написание дизайна
7. Создание задач
8. Реализация задач (`/opsx:apply`)
9. Проверка реализации
10. Архивирование изменения
11. Краткое описание и дальнейшие действия

**Пример:**
```
You: /opsx:onboard

AI:  Welcome to OpenSpec!

     I'll walk you through the complete workflow using your actual codebase.
     We'll find something small to improve, create a proper change for it,
     implement it, and archive it.

     Let me scan your codebase for opportunities...

     [Analyzes codebase]

     I found a few things we could work on:
     1. Add input validation to the contact form
     2. Improve error messages in the auth flow
     3. Add loading states to async buttons

     Which interests you? (or suggest something else)
```

[Русское пояснение подписей и сообщений](../EXAMPLE_NOTES.md#example-044).


**Советы:**
- лучше всего подходит для новых пользователей, изучающих рабочий процесс.
- используется реальный код, а не игрушечные примеры.
- создает реальные изменения, которые можно сохранить или отменить.
- выполнение занимает 15–30 минут.

<a id="command-syntax-by-ai-tool"></a>
## Синтаксис команд от AI Tool

разные инструменты ИИ используют немного разный синтаксис команд. Используйте формат, соответствующий вашему инструменту:

|командный файл вашего инструмента.|пример синтаксиса|Примеры инструментов|
|--------------------------|----------------|---------------|
|`.../commands/opsx/<id>.*`|`/opsx:propose`, `/opsx:apply`|Claude Code, Gemini CLI, Раздавить|
|`.../opsx-<id>.*`|`/opsx-propose`, `/opsx-apply`|Cursor, Devin Desktop, второй пилот (IDE), Trae, Oh My Pi|
|нет — только навыки|`/openspec-propose`, `/openspec-apply-change`|CodeArts, ForgeCode, Hermes, MiniMax Code, Mistral Vibe, Zed Agent, общий `.agents`|
|нет — Код Кими|`/skill:openspec-propose`|Код Кими|
|нет — Codex CLI|`$openspec-propose`|Codex|

> **Devin Desktop против Devin Local:** файлы `.devin/workflows/opsx-*.md` дают
> Рабочий стол Devin `/opsx-propose`. У Devin Local нет рабочих процессов — используйте навыки
> OpenSpec записывает в `.devin/skills/`, например. `/openspec-propose`, которые работают на
> оба агента.

Назначение одинаковое для всех инструментов, но способ отображения команд может различаться в зависимости от интеграции. [Как вызвать](supported-tools.md#how-to-invoke) содержит список всех поддерживаемых инструментов; в этой таблице показаны только примеры каждой формы.

> **Примечание:** Команды GitHub Copilot (`.github/prompts/*.prompt.md`) доступны только в расширениях IDE (VS Code, JetBrains, Visual Studio). GitHub Copilot CLI в настоящее время не поддерживает пользовательские файлы подсказок — подробности и обходные пути см. в разделе [Поддерживаемые инструменты](supported-tools.md).

<a id="legacy-commands"></a>
## устаревшие команды

эти команды используют старый рабочий процесс «все сразу». Они по-прежнему работают, но рекомендуется использовать команды OPSX.

|Команда|Что он делает|
|---------|--------------|
|`/openspec:proposal`|Создать все артефакты одновременно (предложение, спецификации, дизайн, задачи).|
|`/openspec:apply`|реализовать изменение.|
|`/openspec:archive`|Архивировать изменения.|

**Когда использовать устаревшие команды:**
- существующие проекты, использующие старый рабочий процесс.
- простые изменения, при которых вам не требуется постепенное создание артефактов.
- Предпочтение подходу «все или ничего».

**Миграция на OPSX:** Устаревшие изменения можно продолжить
с помощью команд OPSX. Структура артефакта совместима.

<a id="troubleshooting"></a>
## Устранение неполадок

<a id="change-not-found"></a>
### «Изменение не найдено»

команде не удалось определить, над каким изменением следует работать.

**Решения:**
- явно укажите имя изменения: `/opsx:apply add-dark-mode`.
- Убедитесь, что папка изменений существует: `openspec list`.
- убедитесь, что вы находитесь в правильном каталоге проекта.

<a id="no-artifacts-ready"></a>
### «Артефакты не готовы»

Все артефакты либо завершены, либо заблокированы из-за отсутствующих зависимостей.

**Решения:**
- запустите `openspec status --change <name>`, чтобы увидеть, что блокирует
- проверьте наличие необходимых артефактов.
- сначала создайте недостающие артефакты зависимостей.

<a id="schema-not-found"></a>
### «Схема не найдена»

указанная схема не существует.

**Решения:**
- Список доступных схем: `openspec schemas`.
- проверьте правильность написания имени схемы.
- создайте схему, если она пользовательская: `openspec schema init <name>`.

<a id="commands-not-recognized"></a>
### команды не распознаны

Инструмент AI не распознает команды OpenSpec.

**Решения:**
- убедитесь, что OpenSpec инициализирован: `openspec init`
- Регенерация навыков: `openspec update`.
- убедитесь, что каталог `.claude/skills/` существует (для Claude Code).
- перезапустите инструмент искусственного интеллекта, чтобы освоить новые навыки.

<a id="artifacts-not-generating-properly"></a>
### Артефакты не генерируются должным образом.

ИИ создает неполные или неправильные артефакты.

**Решения:**
- добавить контекст проекта в `openspec/config.yaml`.
- добавьте правила для каждого артефакта для получения конкретных указаний.
- укажите более подробную информацию в описании изменения.
- используйте `/opsx:continue` вместо `/opsx:ff` для большего контроля.
