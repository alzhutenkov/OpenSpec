# Наборы изменений

Этот каталог управляется [Changesets (английский)](https://github.com/changesets/changesets).

<a id="quick-start"></a>
## Быстрый старт

```bash
pnpm changeset
```

Следуйте инструкциям, чтобы выбрать тип обновления версии и описать изменения.

<a id="workflow"></a>
## Рабочий процесс

1. **Выберите путь выпуска**: сопровождающие решают, следует ли PR обычной периодичности выпусков или получает специальное отслеживание выпусков.
2. **Добавьте специальное отслеживание выпусков**: когда сопровождающий запрашивает набор изменений, запустите `pnpm changeset` локально до или после вашего PR.
3. **PR версии**: CI открывает или обновляет PR «Version Packages», когда наборы изменений сливаются в main.
4. **Выпуск**: объединение версии PR запускает публикацию npm и выпуск GitHub.

> **Примечание.** Путь по умолчанию — это обычная частота выпуска. Добавьте набор изменений, если сопровождающему или владельцу выпуска нужны специальные примечания к выпуску и отслеживание версий для PR. Управление версиями (`changeset version`) и публикация в CI происходят автоматически.

<a id="template"></a>
## Шаблон

Используйте эту структуру для содержимого вашего набора изменений:

```markdown
---
"@fission-ai/openspec": патч
---

### Новые возможности

- **Название функции** — что теперь могут делать пользователи

### Исправления ошибок

- исправлена проблема, при которой X происходило, когда Y

### Несовместимые изменения

- `oldMethod()` удален, вместо него используйте `newMethod()`.

### Устаревающие возможности

- `legacyOption` устарел и будет удален в версии 2.0.

### Прочее

- внутренний рефакторинг X для повышения производительности.
```

Включите только те разделы, которые относятся к вашим изменениям.

<a id="version-bump-guide"></a>
## Выбор типа повышения версии

|Тип|Когда использовать|Пример|
|------|-------------|---------|
|`patch`|исправления ошибок, отслеживаемые в выпуске, небольшие улучшения.|исправлен сбой при отсутствии конфигурации.|
|`minor`|Новые функции, некритичные дополнения.|добавлен флаг `--verbose`.|
|`major`|критические изменения, удаленные функции.|переименован `init` в `setup`.|

<a id="when-to-create-a-changeset"></a>
## Когда создавать набор изменений

**Используйте специальное отслеживание выпусков для:**
- выбраны для выпуска новые функции или команды.
- заметные исправления ошибок или исправления, запрошенные сопровождающим/владельцем выпуска.
- критические изменения или прекращение поддержки.
- пользователи заметят улучшения производительности, которые запланированы к выпуску.

**Используйте обычную частоту выпусков для:**
- стандартные исправления ошибок, соответствующие обычному графику выпуска обновлений.
- изменения только в документации.
- Тестовые дополнения/исправления.
- внутренний рефакторинг, сохраняющий поведение пользователя.
- изменения CI/инструментария

<a id="writing-good-descriptions"></a>
## Написание хороших описаний

**Делать:** Пишите для пользователей, а не для разработчиков.
```markdown
- **Автодополнение оболочки** — завершение с помощью табуляции теперь доступно для Bash, Fish и PowerShell.
```

**Не делайте**: записывайте детали реализации.
```markdown
- добавлен класс ShellCompletionGenerator с подклассами Bash/Fish/PowerShell.
```

**Сделать:** Объясните влияние
```markdown
- исправлена загрузка конфигурации для соблюдения `XDG_CONFIG_HOME` в Linux.
```

**Не делайте**: просто укажите исправление.
```markdown
- исправлено № 123.
```
